## 1. Видение и стратегическая ставка

**Что мы строим.** TradeLedger — это **слой подготовки данных к учёту (pre-accounting / reconciliation layer)** между разнородной операционной реальностью бизнеса и его 1С. Это НЕ замена 1С, НЕ ERP, НЕ вторая бухгалтерия. Это «мозг учёта» для стадий, которых в 1С структурно нет: сверка гетерогенного входа, поиск расхождений до попадания факта в учёт, управленческо-налоговая песочница периода.

**Формула продажи.** «TradeLedger делает стадии 2–4 конвейера (сверка → работа с данными → подготовка к учёту), 1С формирует проводки и отчётность». Граница ответственности священна (Решение №4): **мы отвечаем за чистоту ФАКТОВ до 1С; 1С отвечает за ПРОВОДКИ.** Это не маркетинг — это сокращение зоны юридической ответственности.

**Якорь доверия — главный аргумент корректности.** Сверка идёт против ЭТАЛОНА, реплицированного из ЗАКРЫТОГО периода САМОЙ 1С клиента (`ReferenceSnapshot` + `Period.status='closed'`, реализовано). Клиент верит не нам — он верит своей же 1С. Это снимает возражение «откуда я знаю, что ваши цифры правильные».

**Критерий нужности (честное самоограничение).** 1 источник → хватает 1С. 2–3 → 1С с доработкой. **4+ разнородных источников → TradeLedger+1С.** Нет проблемы сверки — продукт не нужен. Это квалифицирует лида и повышает доверие в продажах.

**Стратегическая ставка платформы.** Универсальное ЯДРО (инвариант-конвейер) + МОДУЛИ-конфигурации под вид бизнеса (Решение №5). Тест: новый бизнес = новый конфиг, ноль правок ядра. **Честная оговорка:** на сегодня этот тест НЕ пройден (см. §13) — платформенность пока проектная, а не доказанная. Документ строит путь к её доказательству, а не объявляет её свершившейся.

## 2. Конвейер управленца — 4 стадии

Конвейер из 4 стадий (Решение №6) над тремя слоями данных (Решение №7) — единственная смысловая ось продукта.

```
L1 RAW (immutable) ──► L2 NORMALIZED/ХАБ ──► [потребитель A: аналитика]
                            │                 [потребитель B: подготовка → L3 PREPARED → 1С]
```

### Стадия 1 — СБОР (конструктор источников → L1 RAW)
- **Что делает:** тянет данные из источников (STS, эквайринг, ОФД, ЭДО, корп-карты), пишет сырой ответ в L1 RAW append-only с провенансом.
- **Вход:** настроенные `Source` + `Channel`. **Выход:** `RawBatchRecord` (immutable) + L1 `DataEntry(layer='raw')` с натуральным ключом и content-hash.
- **Ядро:** `ChannelSyncEngine` (детерминированный оркестратор fetch→raw-persist→L1-upsert→checkpoint). **Модуль:** адаптеры источников (`@register_adapter`) + декларация doc_types.
- **Заземление:** каркас `SourceAdapter` + реестр + DTO + STS-адаптер существуют; **оркестратор и `parse()` НЕ реализованы** (`connectors.poll` — TODO, `adapter.parse()` возвращает `[]`). Стадия 1 сегодня = статичные модели без runtime.

### Стадия 2 — СВЕРКА + НОРМАЛИЗАЦИЯ (→ L2 ХАБ)
- **Что делает:** нормализует L1 в каноническую модель L2; сверяет потоки между собой и против эталона; классифицирует расхождения по порогам.
- **Вход:** L1 RAW. **Выход:** L2 `CanonicalDocument`+`CanonicalEvent` со статусами сверки.
- **Ядро:** `NormalizeEngine` + единый параметризуемый `ReconcileEngine`. **Модуль:** правила нормализации, оси сверки, допуски, предикаты каналов.
- **Заземление:** живут две императивные сверки (corp-карты, MSTO); backend doc↔entry scoring работает. Нормализация частично DEMO. Единый движок — проектируемое (см. §6).

### Стадия 3 — РАБОТА С ДАННЫМИ (аналитика поверх L2)
- **Что делает:** дашборды, P&L, payment-mix, cash-flow, дебиторка/кредиторка, НДС, прогноз закрытия — поверх L2, форму данных не меняет.
- **Вход:** L2. **Выход:** агрегаты, нарративы, ответы на вопросы.
- **Ядро:** `AnalyticsEngine` (7 endpoints на SQL над проводками — **реально работает**). **Модуль:** пресеты разрезов (`analyticsGroupBy`), KPI-плитки.

### Стадия 4 — ПОДГОТОВКА К УЧЁТУ (→ L3 PREPARED → 1С)
- **Что делает:** маршрутизатор учёта решает, в какой документ 1С ложится факт и почему; межпериодные корректировки — в advisory ledger; pull-конверт уходит в очередь, расширение БП тянет и квитирует.
- **Вход:** L2 факт. **Выход:** `ExportPacket` (L3) + `routing_decision` + статус ack.
- **Ядро:** `RouteEngine` + `AdvisoryLedger` + `PullAssembler`. **Модуль:** маппинг факт→документ-1С (`RoutingRule`), отраслевые нормы.
- **Заземление:** `ExportPacket` queue/ack/`PullCheckpoint` реализованы; `build_packets_from_clean` существует, но **захардкожен под топливо**; `RoutingRule`/`AdvisoryEntry` НЕ существуют. Export-панель UI — DEMO.

## 3. Платформа: граница ядро/модуль + манифест + тест «новый бизнес = конфиг»

### 3.1 Принцип границы
> **ЯДРО — это глаголы (механизмы). МОДУЛЬ — это существительные и прилагательные (политика как данные).**

- ЯДРО знает КАК: принять байты, привязать lineage, сопоставить две записи скорингом, классифицировать расхождение по порогам, держать период, обеспечить идемпотентность по натуральному ключу, собрать pull-конверт, провести запись через advisory-реестр.
- ЯДРО НЕ знает ЧТО: «смена», «резервуар», «АИ-95», «ТОРГ-12», «41.02», «±0.01 литра», «канал=кр». Это приходит ТОЛЬКО из манифеста.
- МОДУЛЬ декларирует, но не исполняет. Если бизнесу нужен код, которого нет в ядре, — это сигнал обобщить ЯДРО (добавить механизм), а не писать код в модуле.

## 4. Три опорных контракта

### (a) Контракт источника (вход) — `SourceAdapter`
Декларативная часть (метаданные штекера для UI): `source_type`, `label/category`, `setup_schema: SetupField[]`, `available_doc_types: SourceDocType[]`.
Поведенческая часть (3 детерминированных метода): `test_connection()`, `fetch_delta(window) → RawBatch`, `parse() → []` (по умолчанию пусто — нормализация это стадия 2).
Добавки к контракту: `cursor_next` (офлайн-курсор), `idempotency_scope`, `natural_key(item)` — стабильный ключ источника (для STS = `system|station|shift`).
**Заземление:** ABC + DTO + реестр + STS-адаптер реальны; `parse()` пуст; зарегистрирован один адаптер.

### (b) Каноническая модель L2 (середина — главный артефакт) — РЕШЁННАЯ гранулярность
**Решение: ОБА уровня + Document Graph, не «документ vs факт».** Две разные потребности с разной гранулярностью физически нельзя удовлетворить одним зерном:

| Потребность | Зерно | Почему |
|---|---|---|
| Сверка (±0.01л / ±1₽, разрез по топливу/каналу/карте) | **СОБЫТИЕ** (`CanonicalEvent`) | нельзя сверить агрегат смены с пооперационным `/v2/transactions` |
| Выгрузка (идемпотентность, двухфазное проведение) | **ДОКУМЕНТ** (`CanonicalDocument`) | 1С принимает документы; ключ `TL|СМЕНА|65|5|91` — документный |
| Поиск ПРИЧИНЫ расхождения | **ГРАФ** (`DocumentEdge`) | ОРП←ТТН←плотность — путь по рёбрам, не поле |

Документ агрегирует события; событие несёт зерно сверки; ребро объясняет причину.

### (c) Pull-контракт (выход) — версионируемый, идемпотентный, период-aware, профиль-агностичный
```json
{
  "envelope_version": "1.0",          // версия ОБОЛОЧКИ (профиль-агностична)
  "schema": "fuel.shift",             // дискриминатор тела
  "schema_version": "sts-1",          // версия формы ТЕЛА
  "idempotency_key": "TL|СМЕНА|65|5|91",   // = натуральный ключ нативного пути ДОСЛОВНО
  "natural_key": {"system_id":65,"station":5,"shift":91,"ttn":null},
  "period": {"year":2026,"month":5,"status":"open"},
  "source_lineage": {"l2_entry_id":"uuid","raw_refs":["uuid"],"reconciled":true},
  "content_hash": "sha256:...",
  "target_doc_type": "ОРП",
  "operation_type": "ОтчетККМОПродажах",
  "body": { ... STS shift_report как есть ... }
  // НЕТ блока проводок Дт/Кт — 1С проводит сама (Решения №4/№9)
}
```

## 5. Каноническая модель L2 + машина периодов + эталон (схема)

### 5.1 Сущности L2
```
CanonicalDocument (документная грана — единица выгрузки)
  id, company_id, profile_id, doc_class[shift|receipt|sale|purchase|transfer|assembly|writeoff|inventory]
  idem_key UNIQUE       -- 'TL|СМЕНА|65|5|91' (натуральный ключ STS, НЕ внутренний UUID)
  source_natural_key jsonb  -- {system,station,shift} — исходные STS-идентификаторы сохраняются неизменными
  business_date, period_id, is_locked
  organization_ref, counterparty_ref(nullable розница), warehouse_ref(агрегация складов АЗС→АЗС N)
  amount_total(с НДС), vat_total
  target_doc_type, target_operation_type  -- учётная ПОДСКАЗКА, НЕ проводка
  source_id, raw_batch_id, derived_from[]  -- провенанс
  l2_status, recon_status, provenance{normalizer_version, who:code|ai|human}

CanonicalEvent (событийная грана — зерно сверки)
  id, document_id(CASCADE), event_kind[fuel_dispense|payment|receipt_line|...]
  station_code, fuel_ref(GUID, не имя!), pay_channel, card_last4
  quantity, amount, price, density, occurred_at  -- то, что сверяем с допуском
  external_ref(id транзакции источника), meta

DocumentEdge (рёбра графа)
  from_id/kind, to_id/kind, edge_type[lineage|aggregate|reconcile|supersede|chain|explains]
  confidence(0..100), payload(score-детали/формула расхождения)

AdvisoryCorrection (межпериодный реестр — первый класс)
  document_id, original_period_id(closed), target_period_id(open)
  reason[late_ttn|density_fix|reclass], delta{amount,vat,quantity}
  npa_ref, status[proposed|approved|applied|rejected], approved_by(ФИО), approved_at
```

### 5.2 Машина периодов (Решение №10)
```
open    → рабочая зона. is_locked=false. Можно нормализовать, пересверять, перестраивать пакеты.
closed  → ЭТАЛОН read-only. is_locked=true каскадом. Закрытие происходит ВНЕ TradeLedger (БП: УстановкаДатЗапрета).
          TradeLedger ДЕТЕКТИРУЕТ закрытие при репликации (closure_source='from_bp'),
          ставит status='closed', снимает ReferenceSnapshot(checksum + document_refs).

ПЕРЕХОД open→closed: sync детектит дату запрета → status='closed' → каскад is_locked
          → снимок эталона → сверка в строгий режим (rounding→minor, minor→material).

ПРАВКА В ЗАКРЫТОМ ПЕРИОДЕ: запрещена. Любое уточнение → AdvisoryCorrection в target_period(open)
          с reason+npa_ref+персональным approve.
```

### 5.3 Эталон (репликация из 1С)
`OneCSyncService` (odata|com|http-agent): `sync_catalogs` (НСИ с `external_ref`=Ref_Key), `sync_documents` (AccountingDoc L4-snapshot), `sync_policy` (OneCPolicy), `period_closure` (детект → ReferenceSnapshot). Эталон ≠ дубль НСИ: фиксирует ВЕРСИЮ (checksum) и СПИСОК Ref_Key документов периода, чтобы сверка была воспроизводима.

**Риск-якорь:** для построчной эталонной сверки `ReferenceSnapshot` хранит summary+document_refs, но НЕ строки документов. Решение — обогащать снимок построчным срезом критичных документов ОДИН раз при закрытии периода, а не тянуть из 1С на каждую сверку (нагрузка COM-агента).

## 6. Движок сверки + матрица-как-конфиг

### 6.1 Целевая архитектура — ОДИН `ReconcileEngine`
```
ReconRule (данные) ──► load_streams → key_partition → fuzzy_match → field_compare → classify → provenance ──► ReconResult
```
Ядро не знает «топливо», «корп.карта», «ИНН». Знает: потоки записей с общим словарём (canonical L2), правило как бить на корзины, как фаззи-матчить, какие поля сравнивать с какими допусками, как классифицировать severity, как собрать lineage. Доменное — в `ReconRule`.

### 6.2 ReconRule (декларативный разрез)
```yaml
id: corp-fuel
module: fuel
streams: [{tf, anchor}, {corp, external}, {shift, control}]
filter: { tf.pay_channel: {in: [corp]} }       # предикат «мой канал» вместо 'кр' в коде
key: { fields: [station, fuel] }
match: { time_tolerance: 90s, pick: nearest_time,
         bonus_fields: [{card_last4,w:50,eq},{amount,w:30,tol:1.0},{volume,w:20,tol:0.01}] }
compare: [{field: volume, tolerance_abs: 0.01, unit: л}]
severity: { thresholds:{none:0.005,rounding:0.05,minor:1.0,material:100.0},
            critical_fields:[inn], period_promote:{rounding:minor,minor:material} }
```

### 6.3 Матрица топлива = 7 строк конфига ОДНОГО модуля
| Разрез | external | key | допуски | статус |
|---|---|---|---|---|
| online | msto | station,fuel | 1л/10₽/30мин | ✅ работает |
| corporate | corp | station,fuel | 0.01л/1₽/90с | ✅ движок есть |
| acquiring | банк | station,date | amount±1₽ | ⛔ нет источника |
| receipts | ОФД | station,shift | Σчеков | ⛔ нет источника |
| depots | ТТН↔ПТУ | ttn,fuel | volume/density | ⛔ нет движка (данные есть) |
| drains | резервуар↔приём | tank,fuel | приход=Δостаток | ⛔ нет движка |
| transport | tradeframe | station,fuel | volume | ⛔ нет источника |

Депо/сливы запускаются СЕГОДНЯ только конфигом (данные уже в `shift_report`) — первый «бесплатный» новый разрез как доказательство тиражируемости.

### 6.4 ВАЖНАЯ ОГОВОРКА (адверсариальная)
Три движка имеют ТРИ разных gate-ключа, а не один параметризуемый: backend — gate по ИНН (документная пара); fuel — gate по station+fuel+time (тройка external↔TF↔смена). Это **разные топологии матчинга**, а не один алгоритм с разными числами. Поэтому:
- Схлопывание — НЕ «материализация существующего типа», а **переписывание** трёх работающих движков. `ReconcileRule` в коде (`match_field: str`, плоский `compare_fields`, один `tolerance`) НЕ выражает `criteria[]`/`channelPredicate`/`severity_thresholds` — это **замена схемы, а не надмножество**.
- **Дисциплина рефакторинга:** сначала вынести только числа/предикаты в данные при сохранении трёх движков; снять golden-набор результатов corp+MSTO на боевых данных ГИГ; только потом унифицировать топологию, сверяя байт-в-байт против golden. Backend doc↔entry (ИНН-gate) держать ОТДЕЛЬНОЙ осью — не пытаться слить с литровой.

### 6.5 Эталон = тот же движок
`ReferenceSnapshot` подключается как поток `{reference, anchor, mode:read-only}`; `severity.period_promote` обязателен. Две функции: контроль дрейфа (ловит ручные правки в 1С) + база для advisory-корректировок.

## 7. ИИ-агенты по стадиям (функциональная роль — КОРРЕКТНОСТЬ и ДОВЕРИЕ)

### 7.1 Принцип распределения
```
ДЕТЕРМИНИРОВАННЫЙ КОД → всё, где есть формула/схема/порог/справочник
```

### 7.3 Три класса защит от галлюцинаций
1. **Числовой firewall.** ИИ не производит и не правит ни одной суммы/проводки. Все деньги — детерминированный код. ИИ работает только со СЛОВАМИ. Расхождение арифметики ИИ↔кода = находка отклоняется.
2. **Grounding-обязательство (citation-or-abstain).** Каждая находка обязана нести `grounding[]` с реальными entry_id; для A7/A8 — `citation` на НПА. Находка без основания не принимается. Не может сослаться → возвращает «не уверен».
3. **Эталон-как-якорь.** ИИ-рекомендации сверяются с `ReferenceSnapshot`; противоречие эталону = жёсткая блокировка.

### 7.4 Человек-в-петле (привязка к реальным артефактам)
| Точка | Артефакт |
|---|---|
| После A1/A2 | `EntryStatus: recognized→verified`, `VerificationForm` |
| После A4 | `audit_events` (принять/отклонить) |
| После A5 | `ReconcileMapping` (закрепить → станет детерминированным правилом) |

### 7.5 152-ФЗ: PII-маскер
**КРИТИЧНО (заземление):** маскирование в коде ОТСУТСТВУЕТ (`grep mask|pii|обезлич server/ = 0`; Fernet шифрует только креды). Маскер — обязательный gate ПЕРЕД любой отправкой в облако:
```
masked_text = mask(raw_text):
   слой 1: regex (ИНН/КПП/паспорт/телефон/email/ФИО)
   слой 2: NER (natasha/spaCy) — имена/организации/адреса
   слой 3: allowlist (по умолчанию НЕ уходит ничего вне whitelist)
   pii_map (токен→оригинал) хранится ТОЛЬКО локально
```
В облако уходит: masked_text + посчитанные кодом агрегаты + метаданные. НЕ уходит: оригиналы, ПДн, креды, данные L2.

### 7.6 БЛОКЕРЫ монетизации ИИ (адверсариальные, подтверждены кодом)

## 8. Подготовка к учёту: маршрутизатор + advisory ledger + граница

### 8.1 Маршрутизатор учёта — что решает и чего НЕ решает
| Решает (РОУТИНГ) | НЕ решает (ПРОВОДКИ — это 1С) |
|---|---|
| `doc_type` 1С (ОРП/ПТУ/ПКО/Перемещение/Комплектация) | Дт/Кт |
| `ВидОперации` (контейнер семантики НДС) | суммы проводок, выделение НДС |
| `period_id` факта | план счетов |
| идемпотентный `routing_key` | метод МПЗ (FIFO/средняя) |
| расщепление (смена→ОРП+Перемещения+ПКО) | себестоимость |
| это корректировка прошлого периода? → advisory | дата запрета |

### 8.2 RoutingRule (данные ядра, близнец PostingTemplate)
```
RoutingRule:
  company_id(NULL=системное), profile_id, priority
  source_doc_type, match(jsonb предикат над L2-фактом)   # ВХОД
  target_doc_type, operation_type, packet_kind            # ВЫХОД: ярлык контейнера
  split(jsonb), phase[NULL|ПЕРЕМ|КОМПЛ]                   # расщепление и фазы
  key_template('TL|СМЕНА|{system}|{station}|{shift}')     # идемпотентность = нативный ключ
  rationale_template, npa_ref                             # объяснение
```
Результат материализуется в `ExportPacket.payload.routing_decision` (с `rationale` + `rule_chain` для объяснимости) — отдельная таблица решений не нужна.

### 8.3 Advisory ledger (`AdvisoryEntry` — первый класс)
FSM: `proposed → approved → (ExportPacket kind='correction') → applied`. Идемпотентность по `(company, origin, source_entry|reconcile_ref, origin_period)`. Approved-запись проецируется в ТОТ ЖЕ L3-pull — ни одной новой трубы. Защита от двойного учёта: маршрутизатор сверяет с `ReferenceSnapshot.document_refs` перед предложением корректировки.

### 8.4 РЕШЕНИЕ: сколько политики в нас (тонко vs толсто)
**Маршрутизатор ТОНКИЙ по проводкам (ноль Дт/Кт), ТОЛСТЫЙ по роутингу (контейнер+период+идемпотентность+расщепление).**

| Аспект | Где живёт | У нас |
|---|---|---|
| Дт/Кт, суммы, НДС-арифметика | 1С (штатная БП при проведении) | ТОНКО (ноль) |
| Выбор `doc_type` + `ВидОперации` | RoutingRule (данные ядра) | ТОЛСТО |
| Период факта + детект закрытия | PeriodMachine | ТОЛСТО |
| Идемпотентность (natural key) | RoutingRule.key_template | ТОЛСТО |
| Расщепление факта на N документов | RoutingRule.split | ТОЛСТО |
| Рекомендация корректировки | AdvisoryEntry | СРЕДНЕ (рекомендуем, решает человек) |

### 8.5 РЕШЕНИЕ: где маппинг факт→документ-1С
```
ЯДРО (backend): МЕХАНИЗМ route()/PeriodMachine/advisory FSM (код, инвариант)
                ДАННЫЕ RoutingRule (system + per-company) — политика учёта компании
   │ ExportPacket.payload{target_doc_type, operation_type, routing_decision}
   ▼
.cfe (БП ГИГ): «глупый исполнитель ярлыка» — диспетчер по packet_kind,
                заполняет ВидОперации ИЗ ЯРЛЫКА (не из своего хардкода), проводит штатно
ПРОФИЛЬ-МОДУЛЬ: ТОЛЬКО строки RoutingRule + PostingTemplate. Кода не несёт.
```
**Технический долг (Стадия 4 устраняет):** сейчас ВидОперации захардкожен в обработчиках .cfe (`ОбработатьСмену` ставит `ОтчетККМОПродажах` сам). Политика раздвоена ядро/.cfe. Целевое: .cfe читает `operation_type` из payload.

## 9. Pull-контракт + пере-источивание .cfe + дисциплина cutover

### 9.1 Где проходит граница контракта (по коду)
- `TL_Загрузка` (форма): вызывает `TL_ApiКлиент.*`, кладёт сырой JSON в `ВнешниеДанные.ДанныеJSON`, строит ключ `TL|СМЕНА|65|5|91` (`Module.bsl:1297`) и `TL|ТТН|...` (стр.1378).
- `TL_СозданиеДокументов.ОбработатьСмену/ОбработатьТТН`: разбирают ЭТОТ ЖЕ JSON по полям STS (`sales[].pay_type/service_code/release`, `density`, `doc.amount/cost/volume`).
- Идемпотентность: `ПолучитьСтатус(ключ)` по РС `TL_СтатусыЗагрузки`.

**Контракт = (а) сигнатуры получения данных, (б) JSON-форма STS shift_report/receipts, (в) тройка натуральных идентификаторов.** Проведение (двухфазное ПЕРЕМ→КОМПЛ), розничная ОРП-модель, ВидОперации=Комплектация, регистры — ЗА границей, переисточиванием не затрагиваются.

### 9.2 Пере-источивание (адаптер с теми же сигнатурами)
Новый общий модуль `TL_TradeLedgerКлиент` с функциями, сигнатурно идентичными `TL_ApiКлиент`. Возврат `ПолучитьСменныйОтчёт` = `envelope.body` (= тот же объект, что отдаёт STS shift_report). Диспетчер `TL_Источник` по настройке `TL_ИсточникНефтепродукты = STS|TradeLedger`. В форме — замена `TL_ApiКлиент.` → `TL_Источник.` в ~12 точках (Edit, не логика).

### 9.3 БЛОКЕР CUTOVER №1 — расхождение ключей (опровергнуто кодом)
**Центральный тезис «idempotency_key побайтово = нативный КлючЗагрузки» СЕГОДНЯ ЛОЖЕН:**
- Нативный ключ: `TL|СМЕНА|{system}|{station}|{shift_number}` (`Module.bsl:1297`).
- Export-маркер: `f"shift_orp:{station}:{day}"` (`export_packets_router.py:220`).

Расхождения: (1) TradeLedger ключует по ДАТЕ, .cfe — по НОМЕРУ СМЕНЫ; (2) TradeLedger опускает system_id; (3) TradeLedger группирует все смены дня в один пакет, .cfe ведёт документ на каждый номер; (4) для ТТН TradeLedger опускает код топлива. Усугубление: `FuelShift.source_uuid` = `uuid4` (синтетический, не натуральный), `sts_system_code` NULLABLE, `ExportPacket` не имеет колонки `idem_key`.

**Следствие:** на КАЖДОЙ переключённой смене `ПолучитьСтатус` не найдёт STS-документ → задвоение + склейка многосменных дней → искажение 41.02/90.01.1/68.02 на ЖИВОЙ бухгалтерии.

**Обязательные фиксы ДО cutover:**
1. Пересобрать export-маркер под точную строку `TL|СМЕНА|{sts_system_code}|{station.code}|{shift_number}`; группировку перевести с `(station,date)` на `(system,station,shift_number)`; добавить колонку `idem_key UNIQUE`.
2. `sts_system_code` → NOT NULL, заполнить по всем станциям; «нет system_code → пакет не строится».
3. Materialize `natural_key` как обязательное неизменяемое поле L1/L2 из исходных STS-идентификаторов; агрегацию складов делать на уровне выбора склада в .cfe, НЕ в ключе.

### 9.4 Прочие high-блокеры (подтверждены)
- **Нет контент-хэша:** `ПолучитьСтатус` проверяет только факт ключа, не содержимое → «тот же ключ, другой контент» молча игнорируется. Добавить `content_hash` в `TL_СтатусыЗагрузки` + явное предложение перепровести при дрейфе (только в открытом периоде).
- **Нет гарда закрытого периода на стороне записи** (`grep ДатаЗапрета/period_status NefteUchet = 0`). Добавить проверку `period.status='closed'` перед `ОбработатьСмену` → ack `period_closed` → факт в advisory.
- **L2 хранит агрегаты, а не гарантированно сырой `sales[]`/density.** Зафиксировать, что L2 хранит STS shift_report целиком (или TradeLedger дотягивает из L1 RAW), иначе розничная модель делит на ноль и Комплектация не пересчитает тонну→литр.
- **Рассинхрон маппинга pay_type/service_code:** незамапленный pay_type сейчас пропускается с warning (не block) → молчаливое занижение сумм. На период cutover — РЕЖИМ СТРОГОГО ОТКАЗА.

### 9.5 Дисциплина cutover (фазы)
| Фаза | Источник | Что | Критерий перехода |
|---|---|---|---|
| 0 Baseline | STS | зафиксировать множество ключей за месяц | список снят |
| 1 **Shadow** | оба | TradeLedger тянет, но НЕ создаёт документы — `СверитьБезЗаписи` пишет в `TL_СверкаПакета` | **100% совпадение ключей + 0 расхождений сумм/литров** ≥1 неделя |
| 2 Canary | TradeLedger на 1 станции (ГИГ, sys 65, АЗС 5) | реальное создание, STS off для станции | месяц закрыт без расхождений |
| 3 Rollout | TradeLedger по станциям по очереди | по одной station_code | все станции |
| 4 Decommission | TradeLedger | STS остаётся dormant fallback в диспетчере | — |

**Откат = одна настройка `TL_ИсточникНефтепродукты=STS`, посменно обратим.** Документы из TradeLedger остаются валидными (ключи стабильны, проводки нативные). Накатка .cfe — ТОЛЬКО интерактивный Конфигуратор по RDP (DESIGNER из bash → битый header), обязательный `DumpConfigToFiles` до загрузки (иначе затрётся Form.bin). Перед накаткой — COM-дамп боевого бинаря и сверка с src (версия `TradeLedger.cfe` vs `TradeLedger1.cfe`/v6.0.1 не зафиксирована).

## 10. Интерфейс менеджера вокруг 4 стадий

### 10.1 Двухуровневая ось вместо 7 плоских режимов
Сегодня: 7 плоских `coreMode`, статичная раскладка Raw/Core/Export, вход гейтится STS-кредами. Целевое:
```
СТАДИЯ                под-режимы
1 СБОР                Инбокс · Источники · Верификация
2 СВЕРКА              Матрица расхождений · Разрешение
3 РАБОТА С ДАННЫМИ    Дашборд · Управленческий · Финансовый · Налоговый

```
`management/financial/accounting/tax` → под-вкладки стадии 3; `normalize` → фоновый шаг СБОРа.

### 10.2 Лента конвейера (главный навигатор)
```
[Период: Май 2026 ▾ open]  [Объект: Смены АЗС ▾]  [⟳]
①СБОР ──→ ②СВЕРКА ──→ ③РАБОТА ──→ ④ПОДГОТОВКА
142 ✓      128 ✓        —          96 готово
6 ⚠        14 ⚠                    8 ⏳ / 2 ✗ отклонено 1С
```
Принципы «понятно и удобно»: прогресс done/total виден всегда; один сигнал `attention` агрегирует решения ИМЕННО этой стадии; клик по `⚠` ведёт к отфильтрованному списку застрявших (минимум кликов); стрелки подсвечиваются при потоке.

### 10.3 Раскладка зависит от стадии (не фиксирована)
- СБОР: Источники(статус) · Инбокс(все источники) · Верификация(поля профиля).
- СВЕРКА: Матрица(7 осей, заглушки честно помечены «нужна интеграция» ≠ «0 расхождений») · Разрешение(тройка external↔TF↔смена, [Принять]/[Эскалировать]→advisory).
- РАБОТА: вкладки-разрезы на `/api/analytics/*` (реально работает).
- ПОДГОТОВКА: Предпросмотр(«в какой документ 1С и почему») · Advisory backlog(«Утверждаю A/B»+ФИО) · Статус pull(queue/sent/ack/rejected).

### 10.4 Объект-навигатор + гейт по профилю
Период (open=рабочая/closed=эталон read-only) + операционный объект профиля заменяют станционный фильтр. Вход в стол: `≥1 настроенный источник профиля`, а не STS-креды (иначе не-топливный профиль не войдёт; онбординг = первый шаг конвейера).

### 10.5 Единый список «Требует внимания»
Drawer из шапки: `СБОР 6 (не верифицированы) · СВЕРКА 14 (material/critical) · ПОДГОТ 8 (в очереди/отклонено 1С)`. Сортировка по severity. Менеджер начинает день с одного списка, а не обходит 4 стадии.

### 11.2 Почему платят
1С — приёмник проводок, в ней нет сверки гетерогенного входа, поиска расхождений до учёта, управленческой песочницы. Якорь доверия — сверка против эталона из собственной 1С клиента. Ценность реальна ТОЛЬКО при 4+ разнородных источниках.

### 11.3 Switching cost (растёт со временем)
1. Привыкание к чистым данным (возврат к Excel-сверке психологически невозможен).
2. Накопленные mapping-таблицы под конкретную 1С клиента (`ReconcileMapping`, `external_ref`, привязки станция→склад) — месяцы настройки, уход = потеря всей карты.
3. Накопленный advisory ledger — институциональная память «как мы квалифицировали этот тип расхождения».

### 11.4 Моат — ЧЕСТНО
Технология (движок сверки) воспроизводима за месяцы. Защищаемые активы: **(1)** правильная каноническая модель L2 под отрасль (нормативы плотности/акцизов/Комплектация — отраслевая экспертиза); **(2)** библиотека профилей + network-effect паттернов расхождений (слаб на первых клиентах!); **(3)** рабочий .cfe-приёмник под НЕтиповую 1С сетей АЗС — но это **барьер интегратора (услуга 25к разово), а не SaaS-моат**. На 1–3 клиентах моата нет; держится на first-mover. Стратегия — быстро нарастить плотность в ОДНОЙ вертикали (ГСМ) до 5–7 клиентов.

### 11.5 Multi-tenant vs on-premise
`company_id` FK присутствует на ~30+ таблицах — row-isolation заложена. Реестр сейчас = 1 компания (ГИГ), `CompanyContext` — заглушка. **«Умная коробка + облачный мозг»:** парсинг/UI/PostgreSQL/PII-маскер — в контуре клиента (152-ФЗ); AI/Skills/веса — в облаке (защита IP + обязательность подписки). Один Docker-образ, две топологии. SaaS-облако = массовый сегмент; on-prem+local LLM = крупные сети/госсектор (Enterprise). **Риск:** якорный сегмент моата (крупные сети) требует именно on-prem+local — самой дорогой и недостроенной схемы.

### 11.6 Тарифы (подписка, не лицензия — ст.1235 ГК)
Start 3к (200 док, Кейс 1, облако) · Business 12к (1000 док, Кейс 1+2) · Pro 30к (5000 док, Кейс 1+2+3, облако/on-prem) · Enterprise от 70к (безлимит, on-prem+local LLM). Разовые: онбординг 15к, кастомный профиль 10к, интеграция с нетиповой 1С 25к (монетизация моата №3 как услуги).

### 11.7 GTM
1. **Вертикаль за вертикалью** от ГСМ (глубина важнее ширины). 2-я вертикаль — e-commerce/маркетплейсы (та же боль сверки эквайринг+ОФД+МП+банк).
2. **White-label бухаутсорсу — приоритетный канал №1** (там сверка — ежедневная боль БЕЗ внутреннего саботажника; multi-tenant технически готов).
3. **1С-франчайзи — вторичный** (риск каннибализации их часов доработки; 20% комиссия).
4. **Shadow Mode — killer-пресейл:** клиент грузит закрытый квартал, за 10–15 мин — дашборд потерь и ROI, нулевой риск. **Блокер:** требует реальной репликации проводок из боевой БП — если pull не гонялся, Shadow покажет пустоту.
5. Продавать СОБСТВЕННИКУ (продукт = инструмент контроля; операционное звено саботирует прозрачность).

### 11.8 Путь от GIG ко 2-му профилю
- **Этап A (сейчас):** довести fuel-профиль до зрелости — замкнуть `normalize→export` на живых данных (сейчас DEMO-моки), стабилизировать L2 и pull-контракт.

Это единственное честное доказательство тиражируемости и проверка multi-tenant в бою.
- **Этап C:** когда движок сверки вынесен в конфиг — 2-й профиль без кода. Платформу объявлять ТОЛЬКО после 2-го платящего профиля.

## 12. Дорожная карта

### 12.1 ПЕРВАЯ несущая петля (горизонт фокуса)
**Одна АЗС (ГИГ, sys 65, АЗС 5), один месяц, замкнутый круг:**
```
эталон (репликация закрытого периода из БП) → рабочая зона (открытый период)
  → сверка против эталона → подготовка pull → проводки в 1С (через .cfe) → ack
```
Критерий «петля несёт»: за один месяц на одной станции конвейер прошёл все 4 стадии на ЖИВЫХ данных, документы созданы без задвоения (Shadow дал 100% совпадение ключей), бухгалтер принял по отчёту эквивалентности.

### 12.2 Блокеры в строгом порядке
- **Блокер №0:** ввести Alembic (сейчас только `create_all`, нет ALTER) — без него любая новая таблица/колонка на проде = ручной DDL.
- **Блокер №1 (cutover):** пересобрать export-маркер под STS-тройку + `sts_system_code` NOT NULL (§9.3).
- **Блокер №2 (ИИ/152-ФЗ):** PII-маскер как технический gate + grounding-валидация webhook (§7.5–7.6).
- **Блокер №3 (граница):** зафиксировать ОДНИМ решением «факты, не проводки» и сверить с боевым .cfe.

### 12.3 Расширение после первой петли
1. Вынести протечки §3.3 в данные (export-сборка, пороги, НДС/счета → манифест) — ДО объявления платформы.
2. Оживить DEMO-стадии (normalize/export) на реальных L2/L3 ИЛИ снять Pro/Enterprise-кейсы из КП.
3. Депо/сливы — первый «бесплатный» новый разрез конфигом.
4. 2-й профиль через intake-ветку (1-й платящий не-GIG клиент).

### 12.4 Что ЗАМОРОЗИТЬ как «горизонт» (не делать сейчас)
**Обобщение ядра (RoutingRule/ReconRule/WorkspaceProfile/operationalObjects/CanonicalEvent) — ЗАМОРОЗИТЬ до появления 2-го РЕАЛЬНОГО платящего профиля.** Соблюсти правило проекта «обобщать по факту 2-го канала». Иначе — месяцы на абстракции при нуле выручки вне одного клиента. Сначала добить fuel-петлю, потом обобщать.
