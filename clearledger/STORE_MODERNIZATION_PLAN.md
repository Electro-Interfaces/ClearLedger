## 1. Резюме и принципы

Раздел «Магазин» построен полностью и по методической части местами богаче типовой 1С (GMROI, ABC×XYZ, инжиниринг меню Kasavana-Smith, партионная себестоимость на остатках). Но аудит вскрыл системное расхождение между **декларацией и кодом** и структурный дефицит **управляемости**. Движемся по трём осям одновременно.

**Тезисы:**

1. **Сначала достоверность, потом красота.** Две главные системные ошибки маржи — двойное вычитание НДS из закупки (возможное) и «две базы себестоимости» (окно закупок vs FIFO-партии) — обесценивают всю аналитику цен/ассортимента/общепита. Чиним первыми, до любого обогащения.

2. **Капитализировать заявленное ФИФО-преимущество.** `StockOnHand.cost_unit` (партионная удельная себестоимость) уже грузится, но используется только в снимке остатков. Перевести на неё COGS всех продаж — это и есть конкурентное преимущество из §3/§10 карты, сейчас невидимое на витрине.

3. **Сдвиг от «аналитики фактов» к «слою политик».** Сегодня раздел — статичный срез: KPI без плана, без светофора-к-цели, без сквозного drill-down (ровно то, что §5 карты называет анти-паттерном). Поверх готовых фактов малой ценой ложится слой политик: план продаж, ассортиментная матрица со статусами, ценовые правила, контроль МРЦ табака, ОП-17 для кухни.

4. **Раскрыть уже посчитанное, но зарытое.** `by_station`, `returns`, честная разбивка оплат по `ФормаОплатыКанон`, `top_surplus` — данные считаются или доступны, но не показаны. Самый дешёвый выигрыш.

5. **Единый UX-фундамент вместо копи-паста.** KPI в 3 реализациях, `Seg` ×3, сортируемый заголовок ×3, модалка ×6, loading/error ×11. Вынести общие компоненты — это разблокирует Δ%-тренды, a11y, тему и экспорт «прицепом» на всех панелях сразу.

6. **Экспорт — крупнейшее дешёвое отставание.** Инфраструктура (`analytics/ExportButton.tsx` + `services/chargeExport.ts`) готова и работает в «Продажах» ЭЗС; в «Магазине» — ноль. Разметка `data-*` + кнопка.

7. **От ручных пул-скриптов к каналу; от снимка к журналу.** Товародвижение наполняется вручную (`pull_cb_*_dev.py`, хардкод `gig`, delete+insert, top-капы). Целевое — регулярный ingest каналом (как продажи через `cb_intake`), а стратегически — складской журнал `StockMovement` (режим C), открывающий «Ledger → продюсер документов в БП». Это последний, самый рисковый слой — только после регуляторного P0.

## 2. Корректировки (сначала чинить)

Сгруппировано по типу. Формат: **суть → где → как → приоритет**.

### 2.1. Достоверность себестоимости и маржи (критично, корень выбросов)

- **К-1. Двойное вычитание НДС из закупки.** COGS-net везде считается `Сумма − СуммаНДС` с допущением «Сумма брутто». Для ОРП (продажи) верно, но для `ПоступлениеТоваровУслуг.Товары` в УТ 10.3 `Сумма` обычно **без НДС** → маржа завышена систематически. Где: `goods_dashboard.py:232, 427, 658, 680`. Как: probe-скрипт на 20 строках ПТУ (сверить `Сумма` vs `Цена×Количество` vs `СуммаНДС` + флаг `СуммаВключаетНДС`), затем условное вычитание. **P0** (дешёвая проверка, смещает всю маржу магазина).

- **К-2. Две базы себестоимости → рассогласование экранов + выбросы.** Маржа продаж = средневзвешенная закупка *за окно* (`sku_analytics:239`), а остаток — FIFO-партии `cost_unit`. Тонкая партия в окне → маржа «улетает» (Kent Nano −103%); SKU без закупки в окне → `margin=None`. Где: `sku_analytics`, `pricing_analysis`, `assortment_analysis`, `sku_detail:437`, `catering_menu`. Как: единый каскад COGS — (1) `StockOnHand.cost_unit` по GUID → (2) фолбэк средняя-закупка (расширить lookback до ~90 дн) → (3) `None`. **P0** (закрывает выбросы, рассогласование, `margin=None` разом; данные уже грузятся).

- **К-3. Нефлагированные выбросы наценки/маржи.** `100·margin/cogs` без ограничителей: при `cogs≈0` наценка взрывается до тысяч %. Где: `sku_analytics:257-258`. Как: clamp/winsorize отображаемых значений + явный флаг «себест. ненадёжна» (когда `purch_qty ≪ sold_qty` или cogs из 1 строки); ненадёжные исключать из групповой маржи. **P1** (после К-2 частично рассосётся).

- **К-4. Единицы покупка↔продажа не сверяются.** COGS = `avg_cost(закупка) × qty(продажа)`; при закупке в кг/блоках и продаже в г/пачках множитель расходится в 100–1000× (сигареты блок↔пачка, весовые). Где: маржа продаж, нет ни одной проверки. Как: при матче GUID сверять базовую единицу/коэффициент из НСИ; при конфликте — не считать COGS (`cost_unit_conflict`), а не выдавать выброс; весовые (`weighed`) — отдельная ветка + лог. **P1**.

- **К-5. Общепит: `cost_known` при одном совпавшем ингредиенте.** Блюдо из 5 ингредиентов, где в окне куплен 1 → себест. по 1 позиции → занижен food-cost, завышена маржа, неверный класс меню, но попадает в `dishes_costed` как полное. Где: `catering_menu:782-784`, `pricing_analysis:328/333`, `sku_detail:416`. Как: ввести `coverage%` (доля покрытых ингредиентов по стоимости/числу), `costed` только при ≥ порога (≥90–100%), иначе класс «предварительно/❔» и не в агрегаты маржи; показать `coverage%` в модалке. **P0** (для общепита — родовой источник выбросов).

## 3. Обогащение (новые механизмы)

Из §7/§8 карты 1С. Формат: **что даёт руководителю → реализуемость на наших данных (УТ 10.3) → приоритет**.

### 3.1. Слой политик (главный gap — управляемость)

- **О-1. План-факт-светофор / менеджерский монитор (§5, §8.2).** Руководителю: карты `факт / план / % / 🟢🟡🔴 / тренд к ППГ / спарклайн` — разблокирует директорский контур, которого сейчас нет. Реализуемость: нужна новая сущность плана продаж (категория/период/АЗС) + расширение `Kpi` (`plan`, `traffic`) + ветка в `compute()`; факт-сторона готова, спарклайн — из `charts.daily`; ППГ — заложить контракт, включится с накоплением истории (пока только апрель). **P0** (самый большой рычаг).

- **О-2. Ассортиментная матрица со статусами (§7.1, §8).** Руководителю: жизненный цикл SKU (В ассортименте/Вводится/Выводится/Выведен-Неликвид/Сезонный) + план-факт «вне матрицы»/«отсутствуют»/нарушения min-max. Реализуемость двухфазно: **Фаза A** — «предлагаемый статус» выводим из наших метрик (ABC/XYZ/остаток/тренд/CV), 0 миграций, бейдж-колонка рядом с ABC×XYZ, сразу; **Фаза B** — таблица `assortment_matrix(company, nomenclature_ref, warehouse, status, min_qty, max_qty, quota_category, valid_from)` + CRUD → управляемый план-факт. Факт-сторона (dead/oos/overstock) готова. **P0 (Фаза A) / P1 (Фаза B)**.

- **О-3. Контроль МРЦ табака + «цена ниже себестоимости» (§7.2, регуляторика).** Руководителю: регуляторный контроль (нарушение = продажа выше МРЦ) + защита маржи. Реализуемость: **«ниже себест.»** — сразу, `StockOnHand.retail_price` vs `cost_unit`, флаг в action-list, без новых данных; **МРЦ** — новая таблица `tobacco_mrc(company, nomenclature_ref, mrc, valid_from)`, табак идентифицируем по `nom_kind`+`marked`, сравнение тривиально, узкое место — источник МРЦ (старт с ручного CSV-импорта, далее ЧЗ-фид). **P0** (регуляторный; «ниже себест.» — быстрый выигрыш).

- **О-4. Ценовые правила + контроль отклонений (§7.2).** Руководителю: отчёт «нарушители правила» (наценка ниже нормы/ниже себест.). Реализуемость: таблица `price_rule(company, scope[kind|category|price_group], target_markup_pct, min_markup_pct, enforce_mrc)`; эффективную наценку по SKU/группе уже считаем → deviation-отчёт. Классификатор ценовых групп — из `kind_ref/group_ref` через `CbRef` (О-5). Автоценообразование (генерация «Установка цен» → БП) — позже, вне аналитики. **P1**.

- **О-5. Классификатор ценовых групп (Табак/Алкоголь/Фреш).** Ключ для О-3/О-4 и группировок наценки. Реализуемость: маппинг `group_ref/kind_ref` → группы через `CbRef`. **P1** (ЛОВ, дёшево).

- **О-6. Виджеты-исключения на Обзоре (§5 п.5).** Руководителю: «работа по исключениям» — незакрытые смены, отклонение от плана >X%, позиции вне матрицы, подходит срок годности, продажа ниже МРЦ/себест. Реализуемость: питается О-1/О-2/О-3 + читаемыми данными. **P1** (после О-1/О-2).

### 3.2. Общепит (закрыть родовую дыру «комплектации»)

- **О-7. Аналог ОП-17 — план-факт расхода сырья (§10, P0).** Руководителю: единственный отсутствующий структурно контроль кухни — перерасход/недовложение/воровство (модель комплектации даёт только стандарт-кост). Реализуемость: **норма** = рецептура × порции = уже есть (`ing.qty_total`); **факт** = `нач.остаток + закупки − кон.остаток` по ингредиенту (`StockOnHand` + `_load_purchases` + `CbInventoryDoc`); выдать отклонение в ед. и ₽ + свод по кухне, отдельная вкладка. **P0** (родовая дыра модели).

- **О-8. FIFO-себестоимость ингредиентов** вместо периодной средней — `StockOnHand.cost_unit` в `_avg_cost`. Точнее food-cost, чинит К-5/хрупкость окна. **P1** (часть К-2).

- **О-9. Прозрачность покрытия + сегментные таргеты food-cost.** `coverage%` в модалке, «провизорный» бейдж, индикатор `unknown` в KPI; сегментные пороги food-cost (кофе ~10–15%, еда ~30–35%) вместо единого 40%. **P1-P2** (реализация К-5 как фичи).

- **О-10. Брутто→нетто→выход (%ХО/%ГО) + калькуляционная карта ОП-1.** Сначала **верификация**: хранит ли ЭЛСИ.АЗК в `Ингредиенты` брутто или нетто (если нетто — себест. занижена). Карта ОП-1 (сырьевой набор + учётные цены + %наценки → продажная) — данные почти есть, в основном форма. **P1-P2** (условно).

- **Осознанно НЕ тащить:** многоуровневые рецептуры/полуфабрикаты, «Выпуск продукции» + склад ГП, ОП-23/бракераж/ЕГАИС/Меркурий, пищевая ценность — избыточно для формата «кофе + хот-дог».

Путь (б) прокси-сейчас: «выручка/час» из `Закрытие−Открытие` (datetime уже есть, только BE+FE). **P1** (прокси сразу; полный — после 1С-верификации).

## 7. Открытые вопросы / развилки для МАГа

1. **Режим C vs чтение.** Складской журнал (`StockMovement`, Волна 4) — стратегическая цель «Ledger → продюсер документов в БП», но самый крупный/рисковый блок. Стартуем его вообще в этом цикле, или пока остаёмся read-only зеркалом ЦБ? От ответа зависит, тянуть ли Волну 4.
