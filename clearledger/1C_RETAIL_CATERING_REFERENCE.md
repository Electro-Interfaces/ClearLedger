# СПРАВОЧНАЯ КАРТА: 1С:Розница / 1С:Общепит → сопряжение с TradeLedger

> Внутренний рабочий документ команды. Ориентир для сопряжения контура «Магазин + Общепит» TradeLedger с ЦБ «ЭЛСИ.АЗК» (база УТ 10.3) и для развития продукта в сторону замены части товароучёта. Источник — синтез 6 research-направлений (documents / registers / reports / workplaces / catering / manager).
>
> **Ключевая рамка источника:** мы читаем из УТ 10.3, а не из Розницы. Практический вывод, к которому нужно возвращаться в каждом разделе: **УТ 10.3 = богатый партионный/себестоимостный слой (ФИФО, партии по каждому наливу/поставке), но бедный розничный контур** (касса ККМ, эквайринг, лояльность, маркировка, авто-ценообразование, ассортиментная матрица — слабее или отсутствуют). 1С:Розница — зеркально: слабая себестоимость (средневзвешенная), но сильные операционный розничный контур и **управленческие механизмы-политики**. Нам нужно взять из УТ фактические суммы/партии, а модель управления — из Розницы.

## 1. Резюме (главные уроки)

1. **1С продаёт не документооборот, а управление политиками.** Ценность 1С:Розница как системы управления — это набор *рычагов-нормативов* (ассортиментная матрица, виды цен + правила ценообразования, маркетинговые акции, min/max остатки, план-факт, лимиты прав), внутри которых операционный контур исполняет всё автоматически. У нас пока построен только контур *учёта фактов* (читаем документы 1С и строим аналитику). **Главный gap — слой политик.**

2. **Ассортимент как управляемая сущность с жизненным циклом.** У 1С позиция имеет *статус ассортимента* (Вводится / В ассортименте / Выводится / Сезонный / Выведен), привязанный к *формату магазина*, с *квотами на категорию* и *min/max*. Это превращает «что заведено» в «что должно продаваться» и даёт план-факт по матрице. У нас есть ABC×XYZ и action-list, но нет самой матрицы и статусов — то, что делает ассортимент *управляемым*, а не только *анализируемым*.

3. **Цена — производная от правил, а не ручной ввод.** Цепочка Закупочная → +наценка (по ценовой группе) → Розничная, зажатая коридором МРЦ/РРЦ/мин.цена, с авто-переоценкой при поступлении. У нас есть анализ маржи и история цен (модалка), но нет *механизма* ценообразования и ценовых ограничений (критично для табака: МРЦ, блокировка продажи ниже — регуляторный риск).

4. **Монитор целевых показателей (KPI) + drill-down по расшифровке СКД — эталон руководительского контура.** Плитка «факт / план / % / светофор / тренд / спарклайн» → клик → расшифровка по магазинам → drill по дням/категориям/кассирам → до чека. Наш «Обзор» — это статичный набор KPI без плана, без светофора-к-цели и без сквозного drill-down до первички. Перенять именно *план-факт-светофор* и *сквозную расшифровку*.

5. **Партионная себестоимость — наше конкурентное преимущество, которого нет в Рознице.** УТ 10.3 (`ПартииТоваровНаСкладах` / `ПартииТоваровОрганизаций`, ФИФО/ЛИФО/средняя) знает себестоимость каждой партии. Розница держит только среднюю (`СтоимостьТоваров`). Мы уже строим маржу от `ПартииТоваровНаСкладах` — это богаче штатной Розницы, надо это капитализировать (точная маржа по наливу/поставке, FIFO уже отработан на топливе).

6. **Инвентаризация в 1С — двухступенчатая: `Пересчёт товаров` фиксирует расхождения, но НЕ двигает остатки; движение делают отдельные `Оприходование` (излишки) и `Списание` (недостачи).** Мы читаем инвентаризацию как факт↔учёт — надо понимать эту связку документов, чтобы корректно собирать shrinkage и не задваивать движения.

7. **Розничная выручка формируется свёрткой: чеки ККМ → `Отчёт о розничных продажах` при закрытии смены.** Это единственный документ, из которого в БП идут проводки по рознице. У нас источник — `ОтчётОРозничныхПродажах` (мы это уже читаем). Помарочного/почекового слоя в УТ-источнике, вероятно, нет — суммы приходят агрегатами.

8. **Общепит держится на разузловании рецептуры (BOM explosion) + двойном пересчёте масс брутто→нетто→выход и сезонных нормах отходов.** У нас уже есть ТТК, food-cost и меню-инжиниринг (Звёзды/Загадки/Лошадки/Собаки) — это сильно. Добить: многоуровневые полуфабрикаты (разузлование), сезонные % потерь, план-факт расхода сырья (норма×выпуск vs факт — форма ОП-17), контрольную калькуляцию ОП-1.

**4 практических следствия для нас (УТ 10.3 → модель магазина):**
1. Партионная себестоимость доступна и богаче Розницы — строить маржу от партий (уже делаем).
2. `ТоварыНаСкладах` / `ТоварыОрганизаций` — надёжный мост остатков.
3. Розничная касса/эквайринг/лояльность/маркировка в УТ слабее/отсутствуют — фактические суммы приходят агрегатами (аналог ОРП), модель поведения брать из Розницы.
4. Общепит-слой (рецептуры/фудкост) в УТ 10.3 отсутствует как штатный — накладываем сами (у нас уже есть ТТК).

- Взаиморасчёты с поставщиками (долг, просрочка) — **НЕТ**
- Анализ цен поступления (динамика закупок) — **ЧАСТИЧНО** (в модалке закупок)
- Отчёт по заказам поставщикам (% исполнения) — **НЕТ**

### Инвентаризация
- Инвентаризация / Излишки и недостачи — **ЕСТЬ** (факт↔учёт, shrinkage)
- Пересортица — **НЕТ**
- Списание (причины) — **ЕСТЬ**
- ИНВ-3/ИНВ-19/ИНВ-26 (печатные формы) — **НЕТ**

### Ценообразование
- Цены номенклатуры / анализ цен — **ЧАСТИЧНО** (история цен в модалке)
- Переоценка — **ЕСТЬ** (Переоценка)
- Соблюдение мин.цен / МРЦ — **НЕТ** (регуляторный gap для табака)

### Маркетинг и лояльность
- Продажи по дисконтным картам / RFM / акции / бонусы / сертификаты — **НЕТ** (нет данных лояльности в УТ-источнике)

### Общепит
- Калькуляция ОП-1 — **ЧАСТИЧНО** (состав ТТК с себест. на порцию; печатная ОП-1 — нет)
- Расчёт себестоимости блюд — **ЕСТЬ** (фудкост, себест. на порцию)
- Расход продуктов норма vs факт / ОП-17 — **НЕТ** (нет план-факта расхода сырья)
- Разузлование (полуфабрикаты) — **НЕТ**
- Анализ реализации блюд (**фудкост %, валовая прибыль по блюду**) — **ЕСТЬ** (Общепит)
- Инжиниринг меню (Звёзды/Загадки/Лошадки/Собаки) — **ЕСТЬ** (наше преимущество — в базовой 1С этого нет, только ABC/XYZ)

> Замечание: практически все отчёты 1С — на **СКД**, что даёт пользователю без программирования: произвольные группировки/кросс-таблицы, отборы, Топ-N, вычисляемые поля («Маржа %», «Дни запаса»), условное оформление (светофор), сохранение *вариантов отчёта* и **расшифровку (drill-down) до документа**. Наш аналог — сортируемые таблицы + модалки. Для паритета нам не хватает: сохраняемых пользовательских вариантов, кросс-таблиц и сквозного drill-down до первички.

## 5. Рабочее место руководителя и дашборды

### Как устроено у 1С
- **Каркас «Такси»:** роль → доступные разделы (командный интерфейс фильтруется правами) + **начальная страница** (набор форм-виджетов в 1-2 колонки) + для операций — отдельный полноэкранный **АРМ** (эталон — РМК кассира: «одно окно = вся роль»).
- **Монитор целевых показателей** (штатно — в УТ11/КА/ERP и «Монитор руководителя» УНФ; в самой Рознице роль монитора играют отчёты + начальная страница с отчётами-виджетами). Плитка-индикатор = Название + **факт (крупно)** + **план** + **% выполнения** + **светофор** (🟢≥100 / 🟡 90–99 / 🔴<90, настраиваемые пороги; для «меньше=лучше» шкала инвертируется) + **тренд ↑↓→ к базе (пред.период / ППГ)** + **спарклайн**.
- **Навигация «сводка → детали» (drill-down)** — то, что отличает монитор от картинки:
  1. Монитор (сеть): плитка «Выручка» красная, −12% к плану →
  2. клик → расшифровка (СКД, тот же период/отбор), уровень 1 — по магазинам →
  3. drill по строке — по дням/категориям/кассирам/часам →
  4. до первичного документа — чек ККМ / ОРП →
  5. обратно вверх, сравнение с сетью и ППГ.
- **Проактивность:** мобильный монитор (push при пробое порога), рассылка отчётов по расписанию (email), «утренняя сводка директору в Telegram» (доработка через HTTP-сервисы/боты — **у нас это органично, экосистема ElsyPlus уже на Telegram-ботах**).

### Что перенять в наш менеджерский контур (конкретные идеи)
1. **Ввести слой ПЛАНА.** Сейчас «Обзор» = статичные KPI без цели. Добавить справочник целевых показателей + значения плана по периодам/категориям → KPI-карты получают `факт / план / % / светофор`.
2. **Светофор и тренд к ППГ на каждой KPI-карте** «Обзора». Пороги настраиваемые, направление «хорошо=больше/меньше» (для оборачиваемости-в-днях, возвратов, неликвидов — инвертировать).
3. **Спарклайн динамики** на карте (мини-график за подпериоды) — у нас уже есть графики, вынести компактно на карточку.
4. **Сквозной drill-down** от KPI-плитки → таблица по категориям/дням → модалка документа (Приёмка/ОРП/Списание). Частично есть (модалки), нужно связать «плитка → расшифровка с тем же фильтром».
5. **Виджеты-исключения** («работа по исключениям»): «Незакрытые смены», «Отклонение от плана > X», «Товары с продажей ниже мин.цены», «Позиции вне матрицы», «Подходит срок годности». Это ровно то, чем живёт директор магазина.
6. **Средний чек / глубина чека / чеки в час** — базовые KPI руководителя, которых у нас нет из-за агрегатного источника. Проверить, отдаёт ли ЦБ число чеков/позиций в ОРП; если да — добавить.
7. **Сравнение точек** (когда АЗС станет >1) — заложить разрез «по объекту/АЗС» в архитектуру KPI уже сейчас (у нас паттерн ЭЗС «по станциям» уже отработан).
8. **Ролевые варианты дашборда** (собственник / директор АЗС / категорийщик) — разный набор плиток под роль (у нас уже есть RBAC-модель, 10 модулей-ключей — есть на что опереться).

## 6. Общепит

### Модель 1С (ТТК → выпуск → калькуляция → меню-инжиниринг)
- **НСИ рецептур:** справочник `Рецептуры` (виды: Блюдо / Заготовка-полуфабрикат / Разделка / Комплект). Шапка: номенклатура, **выход порции (г)**, кол-во порций в расчёте (1 или 100), технолог, ссылка на Сборник рецептур. ТЧ «Состав»: ингредиент, **Брутто → %ХО → Нетто → %ГО → Выход**.
- **Двойной пересчёт масс:** `Нетто = Брутто×(1−%ХО/100)`; `Выход = Нетто×(1−%ГО/100)`. Обратный расчёт от выхода к брутто.
- **Сезонные нормы отходов** (периодический регистр %потерь): напр. картофель 25%→30%→35%→40% по кварталам; или сезонные варианты рецептур.
- **Взаимозаменяемость** ингредиентов (таблица аналогов с коэф. эквивалентности) — подстановка при отсутствии сырья.
- **Многоуровневые рецептуры + разузлование (BOM explosion):** блюдо → полуфабрикат (своя рецептура) → сырьё; развёртка полной потребности по всей глубине.
- **ТК/ТТК:** раскладка + технология + органолептика + физ-хим + **пищевая/энергетическая ценность** (из справочника «Химический состав продуктов»).
- **Документы производства:** `Приготовление`/`Выпуск продукции` (списание сырья по рецептуре + оприходование ГП), `Отчёт производства за смену`, `Разделка` (ОП-23), `Комплектация`.
- **Калькуляция:** `Расчёт цен (калькуляция)` → **ОП-1**: сырьевой набор + учётные цены + **%наценки общепита** → продажная цена. **Контрольно-калькуляционная карточка** — пересчёт при изменении цен сырья.
- **Себестоимость:** сырьевая (плановая) = Σ ингредиентов по рецептуре; фактическая — ФИФО/средняя, регламентно «Расчёт себестоимости»; для полуфабрикатов — снизу вверх.
- **Контроль:** норма (рецептура×выпуск) vs факт (списание) = **ОП-17** «Контрольный расчёт расхода продуктов»; ОП-13 (специи/соль).
- **Food cost %** = Себест. сырьевого набора / Цена продажи × 100 (таргет 25–35%).
- **Меню-инжиниринг** (Stars/Plowhorses/Puzzles/Dogs) — в базовой 1С обычно только через ABC/XYZ; полная матрица — в отраслевых надстройках и iiko/r_keeper.

### Что у нас уже есть
- ТТК (23 блюда), состав с себестоимостью на порцию, **food-cost**, динамика.
- **Меню-инжиниринг Звёзды/Загадки/Рабочие лошадки/Собаки** — то, чего в базовой 1С нет. Сильная точка.

### Что добить (по приоритету)
1. **Разузлование многоуровневых рецептур** (полуфабрикаты со своей ТТК) — сейчас, вероятно, плоские рецептуры.
2. **Двойной пересчёт брутто→нетто→выход с %ХО/%ГО** — если сейчас берём только нетто, себестоимость сырья занижается.
3. **План-факт расхода сырья (ОП-17):** норма×кол-во проданных порций vs фактическое списание → отклонения (перерасход/экономия). Это главный управленческий контроль кухни.
4. **Сезонные %отходов** (периодические нормы) — для овощей.
5. **Калькуляционная карточка ОП-1** как печатная/экранная форма (для соответствия и для замены 1С).
6. **Взаимозаменяемость ингредиентов** — ниже приоритет.
7. **Пищевая/энергетическая ценность** блюда (маркетинг + требования) — по возможности.

## 7. Механизмы управления (что критично «руководителю магазина» и чего нам не хватает)

Это **главный стратегический gap**: у нас построен *учёт фактов*, у 1С — *управление политиками*. Шесть контуров:

### 7.1 Ассортимент (gap — высокий)
- **Ассортиментная матрица** (`Ассортимент`): не список SKU, а *правила* — категории × роли товара × квоты, привязка к **формату магазина**.
- **Статусы позиции** (жизненный цикл): Вводится / В ассортименте / Выводится / Сезонный / Выведен — автоматически влияют на снабжение (разрешить/блокировать заказ) и контроль.
- **Квоты на категорию** (глубина ассортимента), **min/max остатки** (страховой запас / потолок).
- **Контроль соблюдения:** отчёты «Товары не в ассортименте», «Отсутствующие позиции матрицы» = план-факт по матрице.
- **У нас:** есть ABC×XYZ, оборачиваемость, дефицит/неликвиды/затоварка, action-list. **Нет самой матрицы, статусов, квот, min/max, формата.** Наша аналитика *анализирует* ассортимент, но не даёт им *управлять*.

### 7.2 Ценообразование (gap — высокий, есть регуляторный риск)
- **Виды цен** (Закупочная/Розничная/РРЦ/Мин/Себестоимость) со способом задания (вручную / формула от др. вида / по поступлению).
- **Правила ценообразования + ценовые группы** (Табак/Алкоголь/Фреш/Магниты) — наценка адресуется группе.
- **Автоценообразование:** `Установка цен` формируется авто при поступлении/по расписанию.
- **Коридор МРЦ/РРЦ/мин.цена:** ⚠ **продажа табака ниже МРЦ блокируется на кассе — регуляторное требование.** Защита от торговли в убыток (не ниже себест.+порог).
- **У нас:** есть анализ маржи, история цен, факт переоценки. **Нет механизма ценообразования и ценовых ограничений.** Для замены товароучёта — обязательный контроль МРЦ табака.

### 7.3 Маркетинг и лояльность (gap — средний, но нет данных в источнике)
- Маркетинговые акции (условие+действие+период+приоритет), скидки (авто/ручные/по карте/по купону), бонусы, сертификаты, **сегменты покупателей (RFM)**.
- **У нас:** нет (в УТ 10.3 движка акций нет, данных лояльности нет). Низкий приоритет, пока нет источника.

### 7.4 Снабжение (gap — высокий, прямая ценность)
- **Автозаказ:** по min/max ИЛИ по оборачиваемости (`норма = среднедн.продажи × срок поставки × коэф.страховки`), с учётом остатка, товара в пути, резервов, открытых заказов.
- **Помощник заказа** (рабочее место закупщика): сводит потребность по поставщику, дефицит, кратность упаковки, мин.сумма, график поставок → пакетное формирование заказов. Закупщик работает «по списку исключений».
- **Параметры поставщика** как рычаг (цена, срок, кратность, основной/альтернативный).
- **У нас:** есть дни запаса и дефицит (диагностика), **нет расчёта заказа и помощника заказа.** Высокая ценность: у нас есть история продаж и остатки — можем считать точку заказа и рекомендованный объём.

### 7.5 Планирование (gap — высокий, замыкает контур руководителя)
- **План продаж** (магазин/категория/период, от истории×коэф. + сезонность + целевой рост).
- **План закупок** (производная от плана продаж + целевого запаса).
- **План-факт** (отклонения абс./%, нарастающим, по срезам) — главный управленческий цикл «вижу отклонение → причина → действие».
- **У нас:** нет плана вообще → «Обзор» показывает цифры, но не «выполнение/отставание». Это блокер для полноценного монитора KPI (§5).

### 7.6 Контроль (gap — частично закрыт нашим RBAC)
- Задачи/напоминания (окончание акции, просрочка заказа, отклонение), согласования (списание сверх лимита, цена ниже мин), **ограничение прав + RLS** (кассир не даст скидку сверх лимита, директор не видит чужой магазин), **KPI сотрудников** (ср.чек, конверсия, маржа, выполнение плана), кассовая дисциплина.
- **У нас:** RBAC-модель (10 модулей, hybrid-роли, аудит AuditEvent) уже есть — фундамент для лимитов прав. Нет: задач/согласований/KPI-сотрудников/кассовой дисциплины.

> **Сквозной принцип 1С, который нам нужно перенять на уровне модели:** руководитель управляет *правилами и нормативами* (матрица, вид цены, акция, min-остаток, план, лимит права), а операционный контур исполняет их автоматически. Замещающему продукту нужно воспроизвести не документооборот, а **слой политик**.

## 8. Дорожная карта сопряжения (приоритизация)

Учтено: мы читаем из ЦБ на базе **УТ 10.3** (партии есть, розничный/управленческий слой беднее), у нас уже построен богатый *аналитический* контур, стратегия — Ledger как продюсер документов в БП.

### P0 — фундамент управления и регуляторика (делать в первую очередь)
1. **Контроль МРЦ табака** (ценовые ограничения) — регуляторный риск, обязательное условие любой замены кассового/товарного контура. Даже как индикатор «продажа ниже МРЦ» в аналитике.
2. **Слой ПЛАНА + план-факт-светофор на «Обзоре»** — превращает статичные KPI в монитор целевых показателей. Разблокирует руководительский контур (§5). Начать с плана продаж по категориям/периодам.
3. **Ассортиментная матрица со статусами позиции** (Вводится/В ассортименте/Выводится/Сезонный/Выведен) + план-факт по матрице. Превращает наш ABC/XYZ из *анализа* в *управление*. Опереться на уже готовый action-list.
4. **Сохранить и капитализировать партионную себестоимость** из `ПартииТоваровНаСкладах` (ФИФО) — не деградировать до средней. Уже делаем на топливе и в магазине; закрепить как архитектурный принцип.

### P1 — операционная ценность руководителю
5. **Автозаказ + помощник заказа** (точка заказа по оборачиваемости, min/max, рекомендованный объём, дефицит по списку исключений). У нас есть данные (продажи+остатки) — быстрый выигрыш.
6. **Сквозной drill-down** от KPI-плитки → расшифровка по категориям/дням → модалка первички (Приёмка/ОРП/Списание). Довести существующие модалки до сквозной цепочки с сохранением фильтра.
7. **Общепит: разузлование многоуровневых рецептур + двойной пересчёт брутто→нетто→выход + план-факт расхода сырья (ОП-17).** Устраняет занижение себестоимости и даёт контроль кухни.
8. **Взаиморасчёты с поставщиками** (долг, просрочка) + рейтинг поставщиков — читаем из УТ, у нас уже есть справочник поставщиков.
9. **Средний чек / глубина чека / чеки в час** — если ЦБ отдаёт число чеков/позиций в ОРП. Базовые KPI руководителя.

### P2 — расширение и полнота
10. **Виджеты-исключения** («незакрытые смены», «срок годности», «вне матрицы», «ниже мин.цены») на дашборде — «работа по исключениям».
11. **Возвраты поставщику + Возвраты от покупателя** как отдельные читаемые реестры.
12. **Маркировка ЧЗ (табак)** — приёмка по КМ, вывод из оборота при продаже. Технически объёмно; приоритет по мере готовности источника.
13. **Сезонные %отходов, взаимозаменяемость ингредиентов, ОП-1/ОП-17 как печатные формы** — доводка общепита.
14. **Ролевые варианты дашборда** (собственник/директор/категорийщик) на базе нашего RBAC.
15. **Сравнение точек (по объекту/АЗС)** и утренняя Telegram-сводка директору — заложить архитектурно; Telegram-канал у нас органичен (экосистема на ботах).

### Не приоритет / вне текущего источника
- Маркетинговые акции, бонусы, сертификаты, RFM-сегменты — движка и данных в УТ 10.3 нет.
- Ордерная схема склала (приходный/расходный ордер) — для одиночного АЗС-магазина избыточна.
- Регламентированные проводки (сч.41/42/90/94) — это уже сторона БП; наша стратегия «продюсер документов в БП» реализует их там, а не в Ledger.

**Смысловой вывод для команды:** мы построили сильный *аналитический* слой (местами богаче типовой 1С — GMROI, меню-инжиниринг, партионная маржа от УТ). Чтобы двигаться к *замене части товароучёта*, нам нужно достроить не документы, а **слой политик** (план, матрица, ценовые правила/МРЦ, автозаказ) и **руководительский монитор с планом-фактом и сквозным drill-down**. Именно это, а не документооборот, делает 1С «системой управления», и именно это отделяет наш продукт-«зеркало 1С» от продукта, который 1С способен заместить.

## 10. Наша особенность: общепит как сопутка через комплектацию (важно)

**Как устроено у нас сейчас (ЭЛСИ.АЗК → TradeLedger):**
Блюда общепита (Капучино, Френч-дог) — это позиции `Справочник.Номенклатура` с признаком «блюдо» и рецептурой (`ЗначенияТТКНоменклатуры`). Продажа блюда идёт в `ОтчётОРозничныхПродажах`, секция `продажа_общепит`, и **в момент продажи разузловывается по ТТК**: строка продажи несёт список `Ингредиенты` [{Номенклатура, Количество}] — фактически **комплектация «на лету»** (sell-time BOM-explosion), без отдельного документа `Выпуск продукции` и без склада полуфабрикатов/готовой продукции. Наш `catering_menu` считает food-cost = Σ(ингредиент × закупочная себест.) прямо из этих `Ингредиенты`.

**Что это даёт (плюсы модели «комплектация»):**
- Простота: нет учёта пре-производства, склада полуфабрикатов и готовой продукции, документов выпуска.
- Естественно для **made-to-order** (кофе из зерна, хот-дог собирается по заказу) — то, что реально на АЗС.
- Прямой и понятный food-cost и списание сырья от факта продаж.

**Что теряем против полного 1С:Общепит:**
| Механизм 1С:Общепит | Что теряем в модели «комплектация» |
|---|---|
| **Выпуск продукции + склад ГП** | Нет учёта партии готовой продукции и её порчи (только на уровне сырья) |
| **ОП-17 план-факт расхода сырья** | Расход = **норма всегда** (рецептура×порции); нет отдельного факт-списания для сравнения → **не ловим перерасход/недовложение/воровство сырья** |
| **Многоуровневые рецептуры (полуфабрикаты)** | Заранее готовимые соусы/тесто/бульоны не отслеживаются как промежуточный запас |
| **Себестоимость ФИФО факт** | Себест. блюда = плановая (рецептура × средняя цена), не фактическая ФИФО-партия |
| **Разделка (ОП-23)** | Разбор сырья (если бы был) не учитывается |
| **ОП-1 / контрольно-калькуляционная карточка** | Нет отраслевой печатной калькуляции (нужна для соответствия/замены 1С) |

**Оценка:** для мини-кафе при АЗС (узкое меню, made-to-order, без заготовочного цеха) модель «комплектация» — **оправданное упрощение**; полный производственный контур 1С:Общепит избыточен. Главная реальная потеря — **отсутствие контроля план-факт расхода сырья** (перерасход/списания).

**Рекомендации (в контексте сопряжения):**
1. **Оставить комплектацию** как базовую модель для made-to-order (не тащить Выпуск продукции без нужды).
2. **P1 — добавить аналог ОП-17 (план-факт сырья) без документа выпуска:** сравнить норму (рецептура × проданные порции) с фактическим расходом сырья, полученным из движения ингредиентов (закупка − остаток по инвентаризации) → отклонения по каждому ингредиенту. Это закрывает главную дыру модели и переиспользует уже читаемые инвентаризацию/остатки.
3. **P2 — многоуровневые рецептуры** ввести только когда появятся заранее-готовимые полуфабрикаты (пока меню плоское — не нужно).
4. **P1 — себестоимость блюда на ФИФО-партиях** ингредиентов (у нас `ПартииТоваровНаСкладах` уже есть) вместо плановой средней — точнее food-cost.
5. **При стратегии «Ledger — продюсер документов в БП»:** решить развилку — порождать в БП **комплектацию/ОРП с разузлованием** (как сейчас ведёт ЭЛСИ.АЗК) или полноценный **Выпуск продукции** (нужен, только если появится склад ГП/полуфабрикатов). Для текущего формата — первый вариант.
