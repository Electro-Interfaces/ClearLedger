# Коннектор к 1С: как завести и наполнить компанию

Один вход вместо тридцати ручных шагов: `connector.py` знает состав наборов, порядок
загрузки и грабли. Порядок здесь — не стиль, а условие правильности: `load-core`
стирает все документы компании, `load-orgs` обязан идти раньше всех, связи и сверка —
последними.

```powershell
# всё сразу: выгрузка → разбор → доставка → загрузка → связи и сверка
py connector.py npk --base "D:\temp\npk-1c" --user Администратор

# по этапам
py connector.py npk --base ... --only pull      # только выгрузка
py connector.py npk --base ... --skip pull      # грузить уже выгруженное
py connector.py npk --base ... --sets queries-tax   # обновить один набор
```

Пароль базы — в `ONEC_PWD`, не в командной строке: она остаётся в истории и в логах.
Клиент-серверная база: `--srvr "1c-srv:1541" --ref buh --user Читатель`.

## Что нужно до первого запуска

1. **Компания заведена в пространстве.** Загрузчики её не создают и падают с внятным
   сообщением. Завести без рестарта стека:

   ```bash
   COMPANY_SLUG=npk COMPANY_NAME='НПК' COMPANY_SHORT='НПК' COMPANY_INN=<инн> \
     COMPANY_PROFILE=office bash ~/.claude/skills/elsy-deploy/scripts/exec-py.sh \
     office first-run/add-company.py
   ```

   Затем дописать её в `ECOSYSTEM_COMPANIES` стека — иначе на чистой базе её не будет.
2. **Доступ к базе 1С.** Выгрузка идёт с Windows-машины, где стоит платформа: COM —
   компонент платформы, файловую базу из контейнера не видно. Только **x86 PowerShell**,
   коннектор вызывает его сам.
3. **Люди.** Новую компанию видит только суперадмин; остальным нужен доступ:
   `COMPANY_SLUG=npk GRANT_EMAILS="..." exec-py.sh office <grant-скрипт>` либо через UI.

## Этапы

| Этап | Где выполняется | Что делает |
|---|---|---|
| `pull` | Windows + 1С | 21 набор запросов через `q1c.ps1`, дампы в `dumps/<slug>/` |
| `parse` | Windows | `parse-first.py` собирает 8 JSON; генераторы `make-*.py` — 5 загрузчиков с данными внутри |
| `push` | ssh на ВМ | JSON и `resolve_org.py` в контейнер (в образе его нет) |
| `load` | контейнер | 10 загрузчиков в жёстком порядке + 5 сгенерированных |
| `finish` | контейнер | связи проводок, `relink`, слияние дублей, СВЕДЕНИЕ СУБКОНТО, сверка |

Дампы и JSON — данные клиента (в зарплатных наборах ФИО, ИНН, СНИЛС, даты рождения),
поэтому `dumps/` закрыт `.gitignore`.

## Что коннектор забирает

Ядро: план счетов, проводки, контрагенты, номенклатура, реализации, поступления,
договоры, банк. Документы: счета, счета-фактуры, регламентные и ручные операции.
Справочники: склады, подразделения, статьи затрат и ДДС, физлица, банки, счета, единицы.
Аналитика: обороты с субконто, сальдо, оплата счетов, журнал счетов-фактур,
ВИДЫ СУБКОНТО ПО СЧЕТАМ (`queries-subconto`) — без них аналитика оборота остаётся
строкой, и связать её со справочником невозможно в принципе.
Зарплата: начисления, ведомости, сотрудники, НДФЛ и взносы. Налоги: календарь, сданная
отчётность, ЕНС, уведомления, помесячные сальдо. Добор: КУДиР и расходы при УСН, кадры,
НМА, уставный капитал, виды субконто и НДФЛ-справочники, реквизиты первичных документов.

Чего нет и почему: основные средства и лизинг (у клиентов пусты), ЭДО (пробный набор),
классификаторы платформы — ОКОФ, ТНВЭД, новости, производственный календарь: это
поставка 1С, а не учёт компании.

**Проверить полноту на новой базе:** `census.ps1` печатает все непустые объекты
конфигурации, `meta-of.ps1` — состав нужных объектов списком из файла. Так найден
пробел у РТИ: у компании на УСН главная книга — КУДиР, которой у ОСНО нет вовсе.

## Грабли, стоившие времени

- **Только x86 PowerShell**: `comcntr.dll` лежит в `Program Files (x86)`.
- **Организация — ПОСЛЕДНЯЯ колонка** каждого запроса: разбор позиционный.
  У табличной части своей организации нет — только `Т.Ссылка.Организация`.
- **Несуществующее поле роняет ВЕСЬ запрос** с «Object reference not set»: ошибка 1С
  маскируется под ошибку PowerShell. Имена искать `meta-of.ps1`, не угадывать.
- **У пары объектов русское имя таблицы не резолвится вовсе**
  (`Справочник.ВидыВычетовНДФЛ`, `ПланВидовХарактеристик.ВидыСубконтоХозрасчетные`) —
  работает только английский синтаксис; `parse-first` читает и `КАК`, и `AS`.
- **Дата: `/Date(ms)/` от эпохи UTC, время в базе московское.** Без `tz=+3` всё, что
  лежит в 00:00–02:59, уезжает на предыдущий день.
- **`COMPANY_SLUG` обязателен и без дефолта**: забытая переменная подписывает данные
  одной компании другой — молча.
- **`LAYER_SOURCE` у загруженной компании не меняют**: загрузчик стирает только свой
  `source`, записи со старой пометкой останутся рядом и обороты удвоятся.
- **`/tmp` и `/app` контейнера эфемерны** — выкат соседней сессии сносит и данные, и
  `resolve_org.py`; этап `push` повторяется свободно.
- **Загрузчики с данными внутри не проходят через `exec-py.sh`** (base64 в аргументе
  команды) — коннектор везёт их через `scp`.
- **Уникальный индекс справочника — (компания, вид, код, имя)**: имя обязано различать
  строки, иначе записи схлопываются молча.
- **Повторные сдачи отчёта** различаются только датой подписи, а иногда и вовсе лишь
  ссылкой в 1С — такие нумеруются, а не выбрасываются.

## После загрузки

`verify-first.py` сверяет слой с источником: состав, обороты всего и по годам, ключевые
обороты продаж, ось юрлица, периоды. Не сошлось — дальше нельзя, разойдутся витрины.

Дополнительно стоит посмотреть глазами: реестр документов (виды и участки), оборотку,
взаиморасчёты, «Качество данных». Метки новых видов документов живут в
`books_router.DOC_LABELS` — вид без метки покажется кодом.

## Сведение аналитики оборотов

Субконто приходит ПРЕДСТАВЛЕНИЕМ («АЗИМУТ ООО», «№ 06/21 от 22.06.2021»), а что
именно записано в первой позиции — зависит от счёта: у 62.01 контрагент, у 20.01
номенклатурная группа, у 51 банковский счёт. Карта видов лежит в плане счетов 1С
(табличная часть «ВидыСубконто»), в слое — в `gl_accounts.subconto`.

```
load-subconto.py   # карта видов по счетам (набор queries-subconto)
enrich-contracts.py # представление договора и срок действия БЕЗ перезагрузки договоров
link-subconto.py   # ссылки: контрагент и договор колонками, остальное в sub_links
```

Что получилось на трёх компаниях: контрагенты сведены **на 100 %**, договоры на
98–100 %, банковские счета, статьи затрат и ДДС, склады, номенклатура и работники —
на 100 %. «Разрывов связей» в модели данных: РТИ 826 → **0**, ПРОМИЗОЛ 3068 → 55,
НПК 17 929 → 600 (из них 483 — документы физлиц без ИНН).

Грабли этого шага:

- **Договоры нельзя перезагружать** ради новых реквизитов: `load-contracts` делает
  delete/insert, а на договорах висят ссылки документов (у НПК шесть тысяч). Добор
  идёт `enrich-contracts.py` — обновлением по ключу «контрагент + наименование».
- **Ключ договора — наименование, а не «номер + дата»**: у клиентов половина
  договоров без номера, и ключ «номер + дата» бьёт по всем «б/н» разом.
- **Виды без своего справочника** («Виды платежей в бюджет» — перечисление
  платформы, «Счета-фактуры» и «Партии» показываются документом, номенклатурных
  групп в слое нет) считаются отдельно: «искать негде» ≠ «не нашли».
- **Сальдо сводится тем же проходом**, но только по счетам, где ПЕРВОЕ субконто —
  контрагент: иначе в несведённые попадают НМА на 04.01 и банковский счёт на 51.
