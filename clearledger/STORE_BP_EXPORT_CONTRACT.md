# Контракт пакета Edge/Ledger → БП ГИГ

> Статус: **референс-контракт** (по факту кода `TL_ЭкспортБП.cfe` / `TradeLedger.cfe`) + дорожная карта, чтобы Ledger стал корректным **продюсером пакетов**, не нарушая существующий приёмник в бухгалтерии.
>
> Источники (истина): `ext-cb-export/src/CommonModules/TL_ЭкспортБП_Сервер.bsl` (строит пакет), `TL_ЭкспортБП_JSON.bsl` (сериализация), `ext-bp/src/CommonModules/TL_МаппингЦБ.bsl` (маппинг НДС/видов операций), `TL_СопуткаСервис.bsl` (приёмник). Контракт-док 1С: `OneDrive\GIG Ledger\...\09_Контракт_HTTP_ЦБ_БП.md` (ревизия 0.2, англ. псевдонимы — **в реальном JSON ключи русские**).
>
> Связано: навык `gig-1c` → `references/data-exchange.md`; память `store-modernization-progress`, `sts-shift-ttn-channels-design`.

---

## 0. Принцип и цель

Сейчас смены из **ЦБ ЭЛСИ.АЗК** выгружаются в **БП ГИГ** так:
```
ЦБ (azs_centre) ──[TL_ЭкспортБП.cfe: пакет=смена, JSON]──► каталог C:\TL_BP_Export\
                                                              │
                                                              ▼
БП ГИГ ──[TradeLedger.cfe: TL_СопуткаСервис.ОбработатьПакетИзСтроки]──► документы БП ──► проводки
```
(Текущий прод-контур — прямой COM-синхронизатор `tl_sync_cb_bp.py`, который **строит тот же пакет** и зовёт `ОбработатьПакетИзСтроки`. Файловый каталог — эквивалентный путь.)

**Цель Ledger:** заменить `TL_ЭкспортБП` как продюсера — выгружать данные ЦБ, хранить в слоях L1→L4, и **эмитить байт-в-байт совместимый пакет** в каталог. Приёмник `TradeLedger.cfe` и правила проводок **не меняются**. Ключевой инвариант: **приёмник читает строго по русским именам полей и делает fail-fast по НДС** — воспроизводить дословно.

# ЧАСТЬ I. КОНТРАКТ ПАКЕТА

## 1. Верхний уровень

JSON, UTF-8 без BOM, отступ таб. **Русские ключи.** Дискриминатор типа документа — `Тип` (значения — англ. строки).

| Ключ | Тип / значение | Источник |
|------|----------------|----------|
| `ВерсияФормата` | Строка, всегда `"2"` | константа |
| `ВремяВыгрузки` | ISO `yyyy-MM-ddTHH:mm:ss+03:00` | текущее время |
| `ИдентификаторПакета` | Детерминированный UUID v5 от компании, источника и смены | повтор той же версии фактов не создаёт новый пакет |
| `Источник` | Строка, `"ЭЛСИ.АЗК ЦБ"` | константа (у нас — своё имя источника) |
| `Смена` | Структура (шапка, §2) | ОРП |
| `Документы` | Массив документов (все kind) | сборщики |
| `НСИ` | Массив записей НСИ (§5) | из кэша UUID |
| `ХешПакета` | hex-64 (SHA-256 по канонизации); при сборке `""`, дозаполняется | §6 |

**Инвариант:** `Документы.Количество() > 0 И НСИ.Количество() = 0` → **исключение**. Пустая НСИ ломает автосоздание карточек в БП.

**Имя файла:** `АЗС{КодАЗС}_{ГГГГ-ММ-ДД}_смена-{НомерСмены}_{ИдентификаторПакета}.json`
(`КодАЗС` формата `ЧЦ=3`; дата = первые 10 символов `Смена.Открытие`; `НомерСмены` очищен от `<>:"/\|?*`). Каталог — `Справочник.TL_НастройкиВыгрузки.КаталогВыгрузки`, дефолт `C:\TL_BP_Export\`.

## 2. Шапка смены (`Смена`)

Источник — `Документ.ОтчетОРозничныхПродажах` (ОРП).

| Ключ | Тип | Источник в ОРП |
|------|-----|----------------|
| `КодАЗС` | Число (208/8/5/…) | `Число(СокрЛП(Склад.Код))`, ошибка → `0` |
| `СкладUUID` | UUID | `Склад.УникальныйИдентификатор()` |
| `ОрганизацияUUID` | UUID | `Организация` |
| `НомерСмены` | Строка (`"2082082804202601"`) | `СокрЛП(ОРП.Номер)` |
| `НомерСменыВнутр` | Число (опц.) | `ОРП.НомерСмены` |
| `Открытие` | ISO+03:00 | `ДатаВремяОткрытия` |
| `Закрытие` | ISO+03:00 | `ДатаВремяЗакрытия` |
| `Оператор` | Строка, **всегда `""`** | реквизита в шапке нет |
| `Касса` | Строка | `КассаККМ` |
| `ОСЭНомер` | Строка | = `НомерСмены` |

## 3. Документы — по типам

Общие плоские поля item у всех kind: `Тип`, `ИсточникUUID` (UUID документа ЦБ — **ключ идемпотентности**), `Номер`, `Дата` (ISO+03:00), `Проведен`, `ПометкаУдаления`. Валюта во всех — `ВалютаДокумента="RUB"`. `Единица` в строках — имя базовой единицы номенклатуры.

**Порядок в `Документы[]` (критичен):** `recipe → purchase → production_release → retail_sale_sidegoods → return_purchase → inventory → gain → writeoff → transfer`. Сначала блюдо собирается из ингредиентов по ТТК, затем продаётся как сопутствующий товар по НДС 22%.

### 3.1. `recipe` (ТТК) — первым
Источник: `Документ.ТТК` (актуальная по `РС.ЗначенияТТКНоменклатуры`, приоритет — склад смены; ресурс `Брутто` на порцию; строки `Учитывать=Ложь`/`Брутто=0` пропускаются).
- item: `Тип="recipe"`, `ИсточникUUID`(UUID ТТК), `БлюдоUUID`, `БлюдоНаименование`,
  `ВидРецептуры`, `ВерсияТТК`, `ВерсияНабораТТК`, `Выход`, `ЕдиницаВыхода`, `Ингредиенты[]`.
- line: `НоменклатураUUID`, `Количество`(=Брутто), `Единица`.
- Приёмник (модель B) создаёт `Справочник.СпецификацииНоменклатуры`.
- Ledger хранит карту в контексте смены и версии набора: повторная сборка старой
  смены не имеет права подменить её текущей рецептурой.

### 3.2. `purchase` (поступление сопутки)
Отбор ЦБ: `ПоступлениеТоваровУслугНаАЗК`, `Склад=смены`, дата ∈ [Открытие..Закрытие], `ВидОперации=ОтПоставщика`; документы с непустыми `Услуги`/`ВозвратнаяТара` пропускаются.
- item: `Тип`, `ИсточникUUID`, `Номер`, `Дата`, `Проведен`, `ПометкаУдаления`, `Организация`(UUID), `Контрагент`(UUID), `ДоговорКонтрагента`(UUID или `""`), `Склад`(UUID), `ВидОперации`(имя перечисления), `СуммаДокумента`, `ВалютаДокумента`, `СуммаВключаетНДС`(булево), `НДСНеВыделять`(булево), `НДСВключенВСтоимость`(`Ложь`), `НомерВходящегоДокумента`, `ДатаВходящегоДокумента`(`yyyy-MM-dd`/`""`), `СуммаНДС`(Σ), `Товары[]`.
- line: `НомерСтроки`, `Номенклатура`(UUID), `Количество`, `Единица`, `Цена`, `Сумма`, `СтавкаНДС`(канон. имя), `СуммаНДС`.
- Проводки БП: B2B — Дт 41.02 Кт 60.01 + Дт 19.03, Σ Кт 60.01 = СуммаДок.

### 3.3. `retail_sale_sidegoods` (розница) — один на смену
Пропуск, если `Товары` и `ВозвращенныеТовары` пусты.
- item: `Тип`, `ИсточникUUID`(UUID ОРП), `Номер`, `Дата`, `Проведен`, `ПометкаУдаления`, `Организация`(UUID), `Склад`(UUID), `Подразделение`(`""`), `СуммаДокумента`, `ВалютаДокумента`, `СуммаВключаетНДС`(дефолт Истина), `Товары[]`, `ВозвращенныеТовары[]`, `СуммаНДС`(Σ), `Оплаты[]`.
- line (`Товары`/`ВозвращенныеТовары`): `НомерСтроки`, `Номенклатура`(UUID), `Единица`, `Количество`, `Цена`, `Сумма` — **С НДС**, `СтавкаНДС`, `СуммаНДС`, `КлассSKU`(`"Сопутка"`/`"Общепит"`), `ЭтоБлюдо`(булево).
- `Оплаты`: `ВидОплаты`(имя; «нал» → `"Наличные"`), `Сумма`. Наличные → касса 50.01, в ТЧ Оплата БП не пишутся.
- Проводки БП: розничная модель — Кт 90.01.1 = СуммаДок **С НДС**, Кт 68.02 = выделение НДС, Σ Дт 62.Р = СуммаДок.

### 3.4. `production_release` (выпуск блюд ОПЗС)
Отбор: `ВыпускПродукции`, `Склад=смены`, дата в интервале.
- item: `Тип`, `ИсточникUUID`, `Номер`, `Дата`, `Проведен`, `ПометкаУдаления`, `Организация`(UUID), `Склад`(UUID), `ВалютаДокумента`, `ВыпускБлюд[]`, `СуммаДокумента`(Σ), `Ингредиенты[]`.
- `ВыпускБлюд`: `НомерСтроки`, `Идентификатор`(ключ связки), `Номенклатура`(UUID), `Количество`, `Единица`, `Цена`, `Сумма`.
- `Ингредиенты`: `НомерСтроки`, `ИдентификаторПродукция`(↔`ВыпускБлюд.Идентификатор`), `Номенклатура`(UUID), `Количество`, `Единица`.

### 3.5. `return_purchase` (возврат поставщику)
Отбор: `ВозвратТоваровПоставщикуНаАЗК`/`ВозвратТоваровПоставщику`, `Склад=смены`, дата в интервале.
- item: как purchase + `ПервичнаяПТУ_UUID`(UUID основания или `""`); без `ВидОперации`/входящего.
- line: `НомерСтроки`, `Номенклатура`(UUID), `Количество`, `Единица`, `Цена`, `Сумма`, `СтавкаНДС`(из строки, иначе `Номенклатура.СтавкаНДС`), `СуммаНДС`(из строки, иначе `РассчитатьНДСОтСуммы`).

### 3.6. `inventory` (инвентаризация)
Отбор: `ИнвентаризацияТоваровНаСкладе`, `Склад=смены`, дата, не помечен.
- item: `Тип`, `ИсточникUUID`, `Номер`, `Дата`, `Проведен`, `ПометкаУдаления`, `Организация`(UUID), `Склад`(UUID), `Комментарий`, `ДатаЗаполнения`(ISO/`""`), `Товары[]`, `СуммаДокумента`(Σ).
- line: `НомерСтроки`, `Номенклатура`(UUID), `Единица`, `Количество`(факт), `КоличествоУчет`, `Цена`, `Сумма`, `СуммаУчет`. Носитель факта, без проводок.

### 3.7. `gain` (оприходование)
Отбор: `ОприходованиеТоваров`, `Склад=смены`, дата, не помечен.
- item: `Тип`, `ИсточникUUID`, `Номер`, `Дата`, `Проведен`, `ПометкаУдаления`, `Организация`(UUID), `Склад`(UUID), `Подразделение`, `ИнвентаризацияUUID`(/`""`), `МестоОприходования`(/`""`), `СуммаДокумента`, `ВалютаДокумента`, `СуммаВключаетНДС`, `НДСНеВыделять`, `НДСВключенВСтоимость`, `Товары[]`, `СуммаНДС`(Σ).
- line: `НомерСтроки`, `Номенклатура`(UUID), `Единица`, `Количество`, `Цена`, `Сумма`, `СтавкаНДС`, `СуммаНДС`(/fallback), `МестоОприходования`(/`""`).

### 3.8. `writeoff` (списание)
Отбор: `СписаниеТоваров`, `Склад=смены`, дата, не помечен.
- item: `Тип`, `ИсточникUUID`, `Номер`, `Дата`, `Проведен`, `ПометкаУдаления`, `Организация`(UUID), `Склад`(UUID), `Подразделение`, `ИнвентаризацияUUID`(/`""`), `СуммаДокумента`, `НДСвСтоимостиТоваров`(имя перечисления), `ВалютаДокумента`, `Товары[]`.
- line: `НомерСтроки`, `Номенклатура`(UUID), `Единица`, `Количество`, `Цена`, `Сумма`. **НДС в строках нет** (проводка на 94).

### 3.9. `transfer` (перемещение)
Отбор: `ПеремещениеТоваров`, где `СкладОтправитель=смены` ИЛИ `СкладПолучатель=смены`, дата, не помечен.
- item: `Тип`, `ИсточникUUID`, `Номер`, `Дата`, `Проведен`, `ПометкаУдаления`, `Организация`(UUID), `СкладОтправитель`(UUID), `СкладПолучатель`(UUID), `Подразделение`, `ВидОперации`(имя), `Направление`(`"Исходящее"`/`"Входящее"`/`"Транзит"`), `Товары[]`, `СуммаДокумента`(Σ Кол×Цена).
- line: `НомерСтроки`, `Номенклатура`(UUID), `Единица`, `Количество`, `Цена`, `Себестоимость`.

### 3.10. НЕ выгружаются
`ingredients_writeoff` — списание сырья идёт внутри `production_release.Ингредиенты[]` / через `recipe`. `return_sale` — в коде экспорта **нет вовсе** (только в комментариях маппинга приёмника). Если понадобятся — контракта на них в ЦБ пока нет.

## 4. НДС

**14 канонических имён** (`СтавкаНДС` строкой): `НДС0, БезНДС, НДС5, НДС5_105, НДС7, НДС7_107, НДС10, НДС10_110, НДС18, НДС18_118, НДС20, НДС20_120, НДС22, НДС22_122`.

**Нормализация при экспорте:** ЦБ `НДС05`→`НДС5`, `НДС05_105`→`НДС5_105`; пустое→пустое.

**Fail-fast:** пустое/неизвестное имя → `СтавкаНДС.ПустаяСсылка()` + запись `СтавкаНДС_НеСопоставлена` в журнал → **документ НЕ создаётся**. Тихого fallback на НДС20 нет (с 16.05.2026).

**`РассчитатьНДСОтСуммы(Сумма, ИмяСтавки)`** — выделяет НДС из суммы **С НДС**, `Окр(,2)`: `НДС20→×20/120`, `НДС10→×10/110`, `НДС22→×22/122`, `НДС5→×5/105`, `НДС7→×7/107`, `НДС18→×18/118`, иначе `0`. Fallback для `СуммаНДС` в `return_purchase`/`gain`; в purchase/retail — берётся из ТЧ как есть.

## 5. НСИ-секция

Массив, дискриминатор `Тип`, ключ связки/автосоздания — `ИсточникUUID`.

- **Организация**: `Тип="Организация"`, `ИсточникUUID`, `Наименование`, `НаименованиеПолное`, `ИНН`, `КПП`, `ОГРН`, `ОКПО`, `ЮрФизЛицо`(имя), `ПометкаУдаления`.
- **Контрагент**: `Тип="Контрагент"`, `ИсточникUUID`, `Наименование`, `НаименованиеПолное`, `ИНН`, `КПП`, `ВидКонтрагента`(имя), `ПометкаУдаления`.
- **Договор**: `Тип="Договор"`, `ИсточникUUID`, `ВладелецКонтрагент`(UUID/`""`), `Организация`(UUID/`""`), `Наименование`, `Номер`, `Дата`(`yyyy-MM-dd`), `ВидДоговора`(имя), `ВалютаВзаиморасчётов`(код, дефолт `"RUB"`), `ПометкаУдаления`.
- **Склад**: `Тип="Склад"`, `ИсточникUUID`, `Наименование`, `Код`, `ВидСклада`(имя), `ПометкаУдаления`.
- **Номенклатура**: `Тип="Номенклатура"`, `ИсточникUUID`, `КодЦБ`(=Код), `Наименование`, `НаименованиеПолное`, `Артикул`, `СтавкаНДС`(канон.), `Единица`(база), `ВидНоменклатуры`(строка), `КлассSKU`(`"Общепит"` если ВидНоменклатуры=`"Набор - комплект"`, иначе `"Сопутка"`), `ШтрихКоды[]`(массив строк, только если `TL_НастройкиВыгрузки.ВключатьШтрихкоды=Истина`), `ПометкаУдаления`.

## 6. Хеш идемпотентности

`ХешПакета` = SHA-256 (hex-64) по **канонизированному** JSON (сортировка ключей — `КанонизоватьJSON`). Считается при `ХешПакета=""`, затем дозаполняется.
⚠ **Модуль `TL_ЭкспортБП_Идемпотентность` (`ВычислитьХешПакета`/`КанонизоватьJSON`) отсутствует в репозитории** — точный алгоритм канонизации (порядок ключей, обработка чисел/дат) нужно достать из ЦБ-базы (расширение установлено там) ИЛИ восстановить сверкой хешей на образцах пакетов. Без точного совпадения хеша приёмник не распознает «тот же пакет» и возможны дубли.

Идемпотентность приёмника — `РС.TL_СоответствиеИсточников` (`Тип`+`ИсточникUUID` → `ПриёмникСсылка`+`ХешПоследнегоПакета`): тот же хеш — пропуск, другой — перезапись.

## 7. Чек-лист производителя (что ОБЯЗАН заполнить Ledger)

1. Верх: `ВерсияФормата="2"`, валидный `ИдентификаторПакета`, `Источник`, `ВремяВыгрузки`, `Смена{}`, `Документы[]`, `НСИ[]`, `ХешПакета`. Русские ключи, дискриминатор `Тип`.
2. **НСИ не пуста** и содержит записи по **всем UUID** из документов (ИсточникUUID/Организация/Контрагент/Договор/Склад/Номенклатура).
3. Стабильный `ИсточникUUID` у каждого документа (ключ дедупликации).
4. **НДС строго канонический** (14 имён после нормализации); неизвестное → документ не создаётся.
5. Розница — суммы **С НДС** (валовые, как на ККМ).
6. Правила автосоздания приёмника: **Организация не автосоздаётся** (ищется по UUID/ИНН → передавать `ИНН`); **Склад не автосоздаётся** (по UUID/номеру АЗС в имени → передавать `Наименование` с «АЗС 208»); Контрагент/Договор/Номенклатура автосоздаются (обязательно `Наименование`; для номенклатуры желательно `КодЦБ`+`СтавкаНДС`+`Единица`, иначе дубли/непроведение).
7. Обязательные реквизиты документа: `Тип`, `ИсточникUUID`, `Номер`, `Дата`, `Проведен`, `ПометкаУдаления`, `Организация`, `Склад`(или `СкладОтправитель`/`СкладПолучатель`), `ВалютаДокумента`, `СуммаДокумента`, строки. Для purchase/return_purchase — `Контрагент`+`ДоговорКонтрагента`.
8. Порядок: `recipe`/`production_release` ДО `retail_sale_sidegoods`. Если хотя
   бы для одного проданного блюда нет выпуска этой смены, пакет не собирается.

# ЧАСТЬ II. GAP-АНАЛИЗ (Ledger vs контракт)

Основной источник — `EdgePacket` → `DataEntry(source=edge, layer=clean)`. Номенклатура,
признак блюда, построчный НДС и штрихкоды берутся из мастер-НСИ `edge.item`/`edge.barcode`;
ТТК — из `DataEntry(doc_type_id=recipe)`. Старый `oneC`-контур остаётся переходным fallback.
Edge-документы связываются с пакетом по внутреннему номеру смены, а при его
отсутствии — по точному полуинтервалу `[Открытие, Закрытие)`, не по календарному дню.

Ручной пакет всегда содержит непроведённые документы (`Проведен=false`): бухгалтер
сам загружает, проверяет и проводит их в БП. Для общепита пакет содержит ТТК,
`production_release` со связанными строками сырья и ОРП: выпуск собирает блюдо,
после чего ОРП продаёт его как сопутствующий товар строго по НДС 22%.

| Блок | Ledger | Пробел |
|------|--------|--------|
| Шапка смены | 🟢 `meta.Смена` (все поля) | Проверить: Склад/Организация в meta — UUID (не код) |
| retail_sale (строки+СтавкаНДС+КлассSKU+ЭтоБлюдо) | 🟢 полно | — |
| Оплаты | 🟢 | ВидОплаты канон-имя (у нас ФормаОплатыКанон) |
| purchase | 🔴 частично | Организация, **Договор**, Склад, **ВидОперации**, СуммаВключаетНДС, СуммаДокумента, входящий док, **СтавкаНДС в строках**, Единица |
| inventory | 🟡 | КоличествоУчет есть; Комментарий/ДатаЗаполнения — добрать |
| writeoff/transfer | 🟡 | transfer: СкладОтправитель/Получатель/Направление/Себестоимость; writeoff: НДСвСтоимостиТоваров |
| recipe (ТТК-документ) | 🟢 | версия карты и набора, выход, единица выхода, конечные ингредиенты |
| production_release | 🟢 | выпуск блюда и связанные строки фактического расхода ингредиентов |
| return_purchase | 🔴 нет | весь тип |
| gain (оприходование) | 🔴 нет | весь тип |
| НСИ Организация/Контрагент | 🔴 | **ИНН/КПП/ОГРН/ОКПО** (Организация ищется по ИНН!) |
| НСИ Договор | 🔴 нет | весь тип |
| НСИ Склад | 🟡 | Код есть в StockOnHand; ВидСклада — добрать |
| НСИ Номенклатура | 🟢 | КлассSKU/ВидНоменклатуры/КодЦБ — из group/kind, есть |
| ХешПакета | 🔴 | алгоритм канонизации (модуль отсутствует) |

**Вывод:** продажный контур (смена+розница+оплаты+блюда+построчный НДС) — ядро пакета — у Ledger **почти полон**. Пробелы: закупочный контур, реквизиты НСИ (ИНН!), «редкие» типы (production_release/return_purchase/gain/recipe), хеш.

# ЧАСТЬ III. ПЛАН РЕАЛИЗАЦИИ ЭМИТТЕРА

## Фаза 0. Достать модуль хеша (блокер идемпотентности)
- Выгрузить `TL_ЭкспортБП_Идемпотентность` (`ВычислитьХешПакета`, `КанонизоватьJSON`) из ЦБ-базы (расширение установлено там) — через Конфигуратор/`db-dump-xml` (навык `gig-1c`).
- Реализовать канонизацию 1:1 на Python (порядок ключей, формат чисел/дат/булевых).
- **Приёмочный тест:** взять реальный пакет из `C:\TL_BP_Export\`, пересчитать хеш нашим кодом → совпадение с `ХешПакета` в файле.

## Фаза 1. Расширить пул ЦБ (`com_worker` + модель)
Добрать в `op_fetch_cb_shifts`/`_build_shift_package` и НСИ-пул:
1. **purchase-поля:** ВидОперации, ДоговорКонтрагента, Склад(UUID), Организация(UUID), СуммаВключаетНДС, СуммаДокумента, НомерВходящегоДокумента/Дата, **построчная СтавкаНДС** (имя) + Единица.
2. **Новые типы документов** (по образцу `_attach_purchases`, отбор по складу+интервалу смены): `production_release` (ВыпускПродукции), `return_purchase` (ВозвратПоставщику), `gain` (Оприходование), `recipe` (ТТК: БлюдоUUID/Брутто из `РС.ЗначенияТТКНоменклатуры`).
3. **НСИ-реквизиты:** Организация — ИНН/КПП/ОГРН/ОКПО/ЮрФизЛицо; Контрагент — ИНН/КПП/ВидКонтрагента; Договор — весь справочник; Склад — Код/ВидСклада; Номенклатура — уже есть (КодЦБ=Код, ВидНоменклатуры→КлассSKU).
4. Хранение: расширить `meta` пакета смены (плоско по контракту) ИЛИ отдельные таблицы `CbPurchaseDoc`/`CbProductionDoc` и `CbOrg`/`CbContract` для НСИ-реквизитов. Рекомендация: **хранить сырой ЦБ-пакет как есть в L1** (`DataEntry.meta` уже почти он), эмиттер собирает из L1/L2.

## Фаза 2. Эмиттер пакета (`server/app/services/bp_export.py`)
`build_shift_package(shift_key) -> dict` собирает структуру строго по Части I:
1. `Смена` из `meta.Смена` (маппинг ключей, Склад/Организация → UUID).
2. `Документы[]` в **правильном порядке**: recipe → purchase → production_release → retail_sale_sidegoods → return_purchase → inventory → gain → writeoff → transfer. Каждый — из наших данных, с проверкой обязательных полей.
3. `НСИ[]` — собрать все UUID из документов, отдать записи из `CbNomenclature`/`CbRef`/новых НСИ-таблиц. **Валидация инварианта** (НСИ не пуста, все UUID покрыты).
4. **НДС-нормализация** через таблицу 14 имён; неизвестная ставка → ошибка (не эмитить, зеркалить fail-fast приёмника, чтобы ловить рано).
5. `ХешПакета` (Фаза 0).
6. Сериализация: UTF-8 без BOM, отступ таб, порядок ключей = канонизация.
- Эндпоинт: `GET /api/store/bp-package?shift_key=…` (preview JSON) + `POST /api/store/bp-package/emit` (запись в каталог).

## Фаза 3. Выгрузка в каталог + приёмка
- Записать файл с именем `АЗС{код}_{дата}_смена-{номер}_{uuid}.json` в каталог (конфиг `Source.connection_config.export_dir`, дефолт `C:\TL_BP_Export\`).
- Приёмка: тот же `TL_СопуткаСервис.ОбработатьПакетИзСтроки` (файловый ридер `TL_ЗагрузкаИзКаталога` ИЛИ прямой COM-вызов с нашим JSON).
- UI Ledger: в разделе «Магазин» → «Выгрузка в БП» — список смен, статус (эмитировано/принято), кнопка эмита, просмотр пакета.

## Фаза 4. Верификация (параллельный прогон)
- **Байт-сверка:** для одной смены сгенерировать пакет Ledger И пакет `TL_ЭкспортБП` → diff после канонизации. Цель — 0 расхождений (или объяснимые: ИдентификаторПакета/ВремяВыгрузки).
- **Проводочная сверка:** загрузить пакет Ledger в БП-стенд `GIG Base2` → сравнить созданные документы+проводки с эталоном (тем же пакетом от ЦБ). Правило проводок ОРП — `probe_full_audit.py` §3.1 (навык `gig-1c`).
- **Идемпотентность:** повторный эмит той же смены → приёмник пропускает (хеш совпал), дублей нет.

## Порядок и риски
- Фаза 0 — **блокер** (без хеша нет идемпотентности). Фаза 1 (пул) → Фаза 2 (эмиттер) → 3 → 4.
- Сквозной тест общепита обязан включать `recipe` + `production_release` + `retail_sale_sidegoods`: выпуск списывает ингредиенты, продажа готового блюда идёт по НДС22.
- Риск: fail-fast НДС и «Организация по ИНН» — самые частые причины отказа приёмника; закрыть в Фазе 1 (ИНН) и Фазе 2 (нормализация ставок).
- **Ничего в БП-приёмнике не менять** — Ledger подстраивается под существующий контракт.
