# Личность Поддержки в пространстве

Ядро — источник членства, доступа к продукту, роли приложения и версии входа.
Используются существующие app_roles (личное назначение → профиль → roleMap)
и assert_company_product. Сопоставление компаний — eco_app_company_links.

Именной ключ с областью support.identity открывает только проверки своей компании:
POST /api/sso/support-identity {subject, nonce} и /support-directory {nonce}.
Ответ — короткое RS256-доказательство aud=support-identity с nonce запроса,
различением principal/directory и неизменяемыми идентификаторами компании/человека.
Общий ключ, отозванный ключ, ключ станции и чужое членство не принимаются.

Handoff в Support содержит tv, session_expires_at и session_scope. Длительность
подчинённой сессии не превышает срок родительской сессии Ядра. Формат токенов
других приложений не меняется. Поддержка не должна превращать scoped visit
в неограниченный вход: пока отдельный ограниченный маршрут не реализован,
такой handoff отвергается. Обычные назначения по company_roles/app_roles работают.

Ограниченные object_scope/own_organization_id у обычного участника не расширяются
до всей сети: текущий адаптер отказывает до сквозного сопоставления этой области.
Каталог содержит разрешённых и отключённых участников, удалённое членство
исчезает из полного снимка. Это проекция для списков, а не кэш разрешений:
критические запросы приложения проверяют principal непосредственно в Ядре.

Проверка двух настоящих приложений и отдельных PostgreSQL баз находится в
TSupport scripts/test/core-managed-identity-integration.mjs. Запуск с CORE_DIR
(каталог clearledger этой версии) и CORE_PYTHON; создаётся собственный временный
PostgreSQL. Нужны согласованные версии обоих приложений.
