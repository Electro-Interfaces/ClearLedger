# Отметка сверки с бухгалтерией у карточек пространства

Общий механизм на все виды карточек: `app/services/accounting_space.py`,
ручки — `app/routers/accounting_space_router.py`. Второй отметки, которая
считается иначе, заводить нельзя — список, карточка договора, карточка
контрагента и карточка площадки читают один ответ сервера.

Источник сведений не меняется: строки выгрузки (`core.data_entries`, слой `raw`),
сопряжения в их `metadata` (`_accounting*`). Новой схемы ручки не требуют.

## Ручки

| Ручка | Назначение |
|---|---|
| `GET /api/accounting/space/links` | связи одной карточки целиком (блок «Что знает бухгалтерия») |
| `GET /api/accounting/space/link-summary` | отметка одной карточки: `entity_type`, `entity_id` |
| `POST /api/accounting/space/link-summaries` | отметки СПИСКА карточек одним запросом |

`entity_type` ∈ `contract`, `counterparty`, `location`; другой — 400.
Общие параметры: `company_id` (обязателен, в query и у POST), `organization_id`
(разрез по своему юрлицу, необязателен).

Batch — POST, потому что пятьсот UUID в строке запроса упираются в лимит заголовка
nginx; записей он не создаёт. Тело: `{entity_type, entity_ids[], organization_id?}`,
не больше 500 УНИКАЛЬНЫХ id (`SUMMARY_BATCH_MAX`, больше — 400): это согласованный
размер порции интерфейса, в пространстве 901 договор, и при меньшем лимите первая
же порция получала бы отказ. Повторённый id работы не добавляет и порцию не
отбивает. Дубли сворачиваются, порядок первого появления сохраняется, и **ответ
содержит элемент на каждый запрошенный id**: пропуск строка списка прочитала бы
как «ещё грузится».

Неизвестная и недоступная карточка отвечают одинаково: `exists: false`,
`state: "no_source"` в batch и 404 у одиночной ручки. Отличать «нет такой» от
«не ваша» нельзя — сама разница рассказывает о чужих данных.

## Живое сравнение, а не прежний вердикт

Расхождение считается сравнением источника с ТЕКУЩЕЙ карточкой. Исправленный по
выгрузке номер расхождением быть перестаёт (и становится устареванием, потому что
сверенное значение изменилось), испорченный — становится, хотя прежняя сверка
этого не видела. Прежний вердикт остаётся единственным источником только там, где
сравнить нечем: карточка недоступна.

Другой документ (`relation` из `OTHER_DOCUMENT_RELATIONS`: дополнения и
соглашения) своим номером и датой паспорт договора не оспаривает: это реквизиты
ЕГО, иначе «Соглашение № 1» вечно расходилось бы с «41-09/ЭЗС-23». Такие связи
`matched_checked` не дают.

Исключение перечислено именно так, списком ДРУГИХ документов, а не белым списком
«того же»: все остальные отношения, включая конфликтные (`number_conflict`,
`date_conflict`, `joint_party`, `number_missing`, `same_contract_payee_label`,
`multiple_cards`), относятся к ТОМУ ЖЕ договору, и его номер с датой сравнивать
обязательно. Белый список молча превращал каждое новое конфликтное отношение в
«связанный документ» и терял живое сравнение. `multiple_cards` при этом означает
неоднозначную привязку и зелёной отметки не даёт.

## Три оси, одно состояние

Оси раздельные и в галочку не сводятся: `matching` (опознана ли запись),
`verification` (что сверено), `freshness` (менялась ли карточка после сверки).
Поле `state` — производное, для цвета отметки; поля осей остаются в ответе.

| `state` | Смысл |
|---|---|
| `differences` | значение выгрузки не совпало с карточкой |
| `stale` | сверенные значения карточки изменились после сверки |
| `needs_check` | сопряжение есть, сверка реквизитов не подтверждена |
| `matched_checked` | совпадает по сверенным реквизитам — **только `contract`** |
| `contracts_checked` | сверены все договоры — **только `counterparty`/`location`** |
| `no_source` | нет данных для сравнения |

Приоритет при нескольких связях — в этом же порядке, худшее впереди.
`no_source` стоит последним намеренно: это граница периметра выгрузки, а не
дефект карточки. `freshness.stale` выставляется параллельно `state`, в том числе
когда `state = differences`.

## Независимая повторная сверка

Прогон, выполненный отдельно от применения, лежит в `metadata` под единственным
стабильным ключом `_accountingRecheck` (схема согласована 28.10.2026). Ключей с
датой в имени читатель не знает: дата прогона берётся из `checked_at` внутри
конверта, иначе каждый следующий круг требовал бы правки кода.

```
_accountingRecheck = {
  schema_version: 1, run_id, checked_at, source_as_of, source_sha256, source_rows,
  source: {file, sheet, rows},          # per_link наследует, поле может переопределить
  overall,                              # confirmed_fields | partially_confirmed | …
  candidates_in_registry: [...],        # для строк без связей
  per_link: [{
    contract_id, relation,
    compared_fields: [{field, label, source, card, result, basis, source_evidence?}],
    current_hash, unknowns: [{field,label,reason}], open_questions: [{code,label,reason}]
  }]
}
```

`compared_fields` — закрытый перечень из четырёх полей: `number`, `date`,
`counterparty_name`, `type_code`. `result` строго трёхзначный: недостаток сведений
и неоднозначность разбора — это `unknown`, а НЕ `difference`.

**Конверт и история хранятся JSON-СТРОКАМИ**, как `_accountingReconciliations`:
`metadata` приложения по контракту `dict[str, str]`, и нестроковое значение ломает
правку и поиск источника. Читатель принимает обе формы, испорченная строка просто
означает «конверта нет» и ручку не роняет.

У дополнения к договору `source` в конверте — номер и дата ОСНОВНОГО договора
(в ячейке их две пары, прогон разводит их отдельным разбором). Поэтому запрет
сравнения для другого документа относится только к значениям самой строки
(`origin: "row"`); значения конверта сравниваются и для дополнений.

Фактические коды `open_questions` прогона и их калибровка: `link_ambiguous` (66),
`party_ambiguous_identity` (6), `card_date_empty` (5), `party_contradiction`,
`source_ambiguous` (2) — снимают отметку совпадения; `party_name_only` (425) и
`role_card` (152) — оговорка и подсказка, отметку не снимают. Закреплено тестом:
новый код, попавший не в ту группу, уронит его.

`state_note` называет ПРИЧИНУ, а не только состояние: к общему тексту добавляются
расходящиеся реквизиты («Расходятся: Дата.») и блокирующие вопросы прогона с их
`label` и `reason` («Что уточнить: …»). Отдельного места для причины в интерфейсе
нет — он показывает это поле, и менеджер должен видеть, что именно уточнять.

История кругов живёт в `_accountingRecheckHistory` (append) и здесь не
интерпретируется. Прежние `_accountingReconciliations`, их `snapshot_at` и
`_accountingReconciliationStatus` повторная сверка не переписывает: статус
сопряжения по-прежнему берётся только из `_accountingReconciliationStatus`.

Что с конвертом делает сервер:

- `checked_at` → `freshness.rechecked_at` и `verification.recheck.checked_at`. Дату
  прежнего применения (`freshness.checked_at`) она не подменяет: это другое событие;
- `current_hash` становится базой устаревания вместо прежнего хеша — правку,
  которую прогон уже учёл, второй раз устаревшей не объявляем; правка ПОСЛЕ
  прогона делает карточку `stale`;
- **`source_sha256`, не совпавший с редакцией файла в строке, снимает конверт с
  доказательств целиком** (`recheck.applicable: false` с причиной). Его значения
  источника взяты из другой выгрузки, и подтверждать ими сверку нельзя;
- из `compared_fields` берутся ЗНАЧЕНИЯ стороны источника, а не вердикт: сервер
  сравнивает их заново (`origin: "recheck"`, сохранённый вердикт — в `claimed`).
  Иначе достаточно записать `match`, чтобы отметка стала зелёной;
- `unknowns` добавляются в `unchecked_fields`, `open_questions` — в
  `recheck.open_questions` с признаком `blocking`.

Калибровка открытых вопросов: отметку совпадения снимают доказанное противоречие
стороны и неоднозначность связывания (`contradict`, `ambig`, `multiple_cards`,
`party_conflict`…). Совместимость названия стороны и подсказка о виде договора —
нет: у РусГидро аренда площадки и получение электроэнергии часто заведены двумя
карточками с одним номером и датой, и «карточка другой роли» конфликтом не является.

## Что считается доказанной сверкой

Доказательством служат только значения, пришедшие из выгрузки: `source_number`
и `source_date` строки плюс значения из принятого конверта повторной сверки.
Сравнивает их сервер сам.

`verification.compared_fields` — список сравнений: `{field, label, source, space,
equal, result, basis, origin, claimed, claimed_basis, evidence}`. `result` ∈
`match` | `difference` | `unknown` (`equal` — тот же ответ булевым, для интерфейса),
`origin` ∈ `row` | `recheck`, `claimed` — что об этом поле записал прогон.
`verification.checked_fields` — поля с `result = match`.

Правила сравнения: номер — по значимым знакам (`compact`, пустой результат даёт
`unknown`, а не совпадение), дата — точным значением с нормализацией «15.08.2024»
к «2024-08-15», ИНН и КПП — по цифрам. **Название стороны сервер не пересчитывает
и идентичностью не считает**: совместимость значимых слов не юридическая проверка,
ИНН в выгрузке нет, поэтому `counterparty_id` остаётся в `unchecked_fields` до
совпадения реквизитов. Вид договора выгрузка не подтверждает — это подсказка.

`target_values` сверки — снимок НАШЕЙ карточки на момент применения. Он отвечает
за устаревание и сверкой источника не является, поэтому лежит отдельным
`verification.snapshot_fields` с `snapshot_basis`. Если выгрузка не дала ни
номера, ни даты, состояние — `needs_check`, даже когда сама сверка записала себе
`verified`.

`verification.unchecked_fields` перечисляется всегда: ИНН и КПП, оригинал
документа, проведение в 1С, суммы. `entity_verified` — всегда `false`: карточка
целиком не сверялась ни у одного вида.

Устаревание считает сервер: хеш `CHECKED_FIELDS` (`number`, `date`,
`counterparty_id`, `type_code`) пересчитывается из текущей карточки той же
сериализацией, что при применении сверки. Правка поля вне этого состава
проверку не сбрасывает. `freshness.checked_at` — `snapshot_at` применённой
сверки; своего времени проверки сервер не выдумывает, он её не выполнял.

## Контрагент и площадка

Зелёная отметка договора на них не переносится. У них своя область
(`scope = contracts_of_counterparty | contracts_of_location`), `matched_checked`
недостижим, и обязателен `aggregate`:

```
aggregate: { contracts_total, with_source, without_source,
             by_state: {<state>: N},
             contracts: [{id, number, date, type_code, state, state_label, records}] }
```

`contracts_checked` ставится только когда сверены ВСЕ доступные договоры. Один
договор без сведений делает сводку `needs_check`, а не «сверено». Площадка без
договоров существует и отвечает `no_source` с `contracts_total: 0`.
Хеши в `freshness` у сводки пустые: общего хеша у набора договоров нет.

## Доступ

Членство в компании (`assert_company_member`) — тот же уровень, что у реестра
договоров; новых прав ручки не вводят. Сверх него:

- **юрлицо** — `contract_acl()`: `org_filter` (закреплённая за участником
  организация и заголовок `X-Organization-Id`) И параметр ручки. Пока учитывался
  только параметр, участник, закреплённый за одним ООО, видел сопряжения второго
  юрлица того же владельца, просто не передав параметр;
- **объекты** — скоуп участника условием запроса (`scope_location_conds`), а не
  только автоматическим сужением ORM: ACL должен держаться и там, где событие
  сессии не поставлено (например в тестовом процессе без lifespan). Сужаются и
  привязки договоров к объектам, и итог «площадок в пространстве»;
- **строки источника** — фильтрации договоров недостаточно. Связь на договор
  недоступного юрлица убирается, и если у строки не осталось ни одной связи,
  убирается вся строка: её «контрагент в бухгалтерии» и «договор или основание» —
  тоже сведения чужого разреза. Отсутствие карточки ВООБЩЕ при этом остаётся
  видимым (`exists: false`) — это дефект целостности, а не чужие данные.

## Нагрузка

`load_entity_contracts` делает на весь batch ровно два запроса — существование
карточек и их договоры, — поэтому отметки страницы списка не превращаются в
обход по строке. Срез (`load_slice`) читается один раз на запрос; его потолок
описан там же (`ponytail:` в сервисе): 395 строк и 901 договор на 28.10.2026,
при десятках тысяч строк отбор уедет в SQL с теми же правилами.

Регрессии: `tests/test_accounting_space_status.py` (отметки, оси, агрегация, ACL
по юрлицу и объектам, batch и число запросов), `tests/test_accounting_space.py`
(срез, страницы, устаревание). Только отдельная `TEST_DATABASE_URL`.

Что именно удерживают эти тесты (и зачем каждый):

| Проверка | Что сломается без неё |
|---|---|
| `отметка_договора_опирается_на_поля_источника` | зелёная отметка без доказательства из выгрузки |
| `снимок_своих_полей_не_считается_сверкой` | `verified` без значений источника читается как проверено |
| `расхождение_и_устаревание_остаются_разными_осями` | одна галочка вместо трёх осей |
| `состояние_считается_живым_сравнением_а_не_прежним_вердиктом` | исправленное расхождение держится вечно, испорченный реквизит не виден |
| `связанный_документ_не_оспаривает_паспорт_договора` | соглашение вечно «расходится» с договором |
| `повторная_сверка_читается_и_показывается_отдельно` | время прогона подменяет дату прежнего применения, база устаревания берётся старая, совместимость названия читается как сверенная сторона |
| `прогон_по_другой_редакции_файла_не_подтверждает_сверку` | конверт чужой редакции выдаётся за доказательство |
| `конфликтные_отношения_остаются_тем_же_договором` | `number_conflict` и соседи молча становятся «другим документом» и теряют живое сравнение |
| `противоречие_стороны_снимает_отметку` | противоречие стороны и привязка к нескольким карточкам остаются зелёными |
| `конверт_читается_и_строкой_json` | конверт, записанный строкой (а в `metadata` только так и можно), читателем не виден |
| `конверт_дополнения_сравнивает_основной_договор` | доказательство по дополнениям теряется целиком |
| `коды_открытых_вопросов_калиброваны` | новый код прогона молча попадает не в ту группу |
| `контрагент_не_красится_отметкой_своего_договора`, `площадка_показывает_сводку_своих_оснований` | перенос зелёной отметки договора на карточку целиком |
| `batch_отвечает_на_каждый_запрошенный_id` | строка списка без отметки выглядит «ещё грузится» |
| `batch_не_растёт_запросами_от_размера_списка` | возврат к обходу по строке списка |
| `страницы_списка_получают_отметки_одним_запросом` | потери и повторы между пагинацией и отметками |
| `закреплённое_юрлицо_и_скоуп_объектов_не_обходятся`, `строки_чужого_юрлица_не_видны_целиком` | чужое юрлицо и чужие объекты в ответе |
| `суперадмин_видит_оба_юрлица` | ограничение участника принимается за исчезновение данных |
