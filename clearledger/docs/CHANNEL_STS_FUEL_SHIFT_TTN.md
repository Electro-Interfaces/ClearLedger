## 1. Принцип

**Документы 1С строятся из секции `sales`, разложенной по КАНАЛУ ОПЛАТЫ × виду топлива.** Расширение не использует `psm`/`money`. Канал оплаты определяется маппингом по `pay_type.name` (подстрока). Каждый канал → свой документ 1С на свой склад. ТТН (`receipts`) → Перемещение тонн + Комплектация (тонны→литры).

```
STS shift_report.sales[]  ──маппинг оплат──▶  агрегат {Канал × service_code → литры, сумма, скидка}
                                                  │
   retail_cash ─┐                                 ├─▶ ОРП (АЗС) + ПКО (наличные)
   retail_card ─┘ (в ОРП)                         ├─▶ Перемещение 41.02→41.01 на склад канала (cards/online/voucher/ledger)
                                                  └─▶ Списание (writeoff_fuel)

STS receipts[]  ──маппинг топлива──▶ Перемещение(тонны, 41.01) + Комплектация(тонны→литры, 41.02)
```

## 2. Контракт извлечения — СМЕНА (канал `fuel_shift`)

Endpoint: `GET /v1/report/shift_report?system&station&shift`. Берём **только** секцию `sales` (+ `dt_open`/`dt_close` из `/v1/shifts`).

`sales[]` — массив групп по виду оплаты:

| Поле STS | Тип | Назначение |
|---|---|---|
| `pay_type.id` | int | ID вида оплаты (доп. ключ; **не для классификации** — у ГИГ нестабилен) |
| `pay_type.name` | str | **Имя вида оплаты — ключ маппинга канала** |
| `fuel[].service.service_code` | int (1-7) | Код топлива → маппинг номенклатуры |
| `fuel[].service.service_name` | str | Имя топлива (из STS, для отображения) |
| `fuel[].release.volume` | str→Decimal | Объём, литры |
| `fuel[].release.cost` | str→Decimal | Сумма, ₽ |
| `fuel[].release.discount` | num | **Скидка, ₽** (сейчас теряется) |

Реальные `pay_type` ГИГ (проверено вживую): `1 Наличные`, `5 Талоны`, `7 КР`, `16 Купон на сдачу`, `26 СберБанк`, `30 БАЛТОП`, `31 Инфорком`, `33 VIAcard`, `235 МобилПр.`. **`id=2` не существует** — поэтому текущая классификация `id==2→card` всегда даёт 0.

> Отрицательные позиции возможны (`Купон на сдачу` vol=-1.05) — обрабатывать как сторно.

## 3. Контракт извлечения — ТТН (канал `fuel_delivery`)

Endpoint: `GET /v1/report/receipts?system&station&shift`. Ответ вложенный `[{shifts:[{receipt:[…]}]}]` → разворачиваем в плоский список. Поля позиции (проверено вживую):

| Поле STS | Тип | Назначение |
|---|---|---|
| `ttn` | str | Номер ТТН (ключ идемпотентности) |
| `service.service_code` / `service.service_name` | int/str | Вид топлива |
| `doc.volume` | str→Decimal | Объём по документу, **литры** |
| `doc.amount` | str→Decimal | Масса по документу, **кг** |
| `doc.density` | num | Плотность по документу |
| `doc.temp` | num | Температура по документу |
| `fact.volume` / `fact.amount` / `fact.density` / `fact.temp` | | Фактические значения (для отклонений) |
| `base.id` / `base.name` | int/str | Поставщик (нефтебаза). **ИНН STS не отдаёт** |
| `tank` | int | Резервуар приёмки |
| `dt` | str | Дата/время поступления |

Пересчёт: `масса_тонн = doc.amount / 1000`; если массы нет — `масса_кг = doc.volume × плотность`.

> **Баг текущего кода:** парсер пишет `supplier_inn = base.inn` — поля нет, всегда пусто. Брать `base.name` (+ `base.id`).

## 5. Маппинги (3 справочника в приложении, привязка к каналам)

### 5.1 `payment_channels` — каналы оплаты
Поля: `code`, `name`, `warehouse_ref` (склад БП), `requires_transfer` (bool), `counterparty_ref`. Seed ГИГ:

| code | name | Склад | requires_transfer |
|---|---|---|---|
| `retail_cash` | Наличные | — | нет |
| `retail_card` | Банковские карты | — | нет |
| `cards` | Топливные/корп. карты | Карты | да |
| `online` | Онлайн (Яндекс, МобилПр.) | ЯНДЕКС | да |
| `voucher` | Талоны | Талоны | да |
| `ledger` | Ведомости | Ведомости | да |
| `writeoff_fuel` | Прочее (списание) | — | нет |
| `""` | Игнор (купон/прокачка) | — | — |

### 5.2 `payment_mappings` — образец имени STS → канал
Поля: `pattern` (подстрока, lower), `channel_code`, `warehouse_override`. Матчинг: `pattern in pay_type.name.lower()`, первое совпадение. Seed ГИГ (20):

| pattern | channel | склад |
|---|---|---|
| `наличн` | retail_cash | — |
| `сбербанк` | retail_card | — |
| `viacard`,`балтоп`,`baltop`,`корпоратив`,`корп.карты`,`топливн`,`агора`,`инфорком`,`газпромнефть`,`мосресурс` | cards | Карты |
| `яндекс`,`мобил`,`benzuber` | online | ЯНДЕКС |
| `ведомост` | ledger | Ведомости |
| `талон` | voucher | Талоны |
| `прочи` | writeoff_fuel | — |
| `купон`,`прокач` | `""` (игнор) | — |

> Нет совпадения → не блокер: позиция в предупреждение, смена грузится.

### 5.3 `fuel_mappings` — service_code → номенклатура
Поля: `service_code`, `nomenclature_tonnes_ref`, `nomenclature_liters_ref`, `density`, опц. `station_code` (переопределение литровой номенклатуры по станции). Seed — таблица §4.

## 7. Конвейер документов (пакеты для 1С)

### Из смены (`fuel_shift`):

| Документ | Источник (канал) | Склад | Счета | Idem-ключ |
|---|---|---|---|---|
| ОтчётОРозничныхПродажах | retail_cash + retail_card | АЗС | 41.02 / 90.01.1 / 90.02.1 / 90.03; ТЧ «Платёжная карта» = retail_card | `TL|СМЕНА|{sys}|{st}|{sh}` |
| ПриходныйКассовыйОрдер | retail_cash | — | 50.01 / 62.Р (без проводок, основание ОРП) | `…|ПКО` |
| ПеремещениеТоваров | cards/online/voucher/ledger (requires_transfer) | АЗС→склад канала | 41.02→41.01, литры, сумма 0 | `…|{channel}` |
| СписаниеТоваров | writeoff_fuel | АЗС | счёт затрат / 41.02 | `…|СПИСАНИЕ` |

### Из ТТН (`fuel_delivery`):

| Документ | Склад | Счета | Idem-ключ | Время |
|---|---|---|---|---|
| ПеремещениеТоваров (тонны) | ОснСклад→АЗС | 41.01→41.01 | `TL|ТТН|{sys}|{st}|{ttn}|{code}|ПЕРЕМ` | 11:00 |
| КомплектацияНоменклатуры | АЗС | 41.01(т)→41.02(л) | `…|КОМПЛ` | 13:00 |

ПТУ от поставщика — **не создаём** (бухгалтер вручную). Время проведения: Перем.ТТН 11:00 → Комплектация 13:00 → ОРП/Перемещения/ПКО/Списание 23:50.

## 8. Что НЕ берём и почему

- `psm` (итоги, счётчики ТРК), `money` (касса/инкассация), `release` (резервуары) — **не нужны для документов** (расширение их не использует). Решение 28.06: объём = sales+receipts. Эти секции — кандидаты для отдельного слоя «сверка/аналитика» позже (разрез `inkassation`, топливный баланс).

## 9. Текущие баги (фикс при реализации)

1. Классификация оплат по `pay_type.id` (1/2/прочее) → заменить на маппинг по `pay_type.name`. Сейчас `card` всегда 0, безнал свален в `voucher`.
2. `pay_type.name` и `discount` не читаются.
3. `supplier_inn = base.inn` — поля нет, брать `base.name`.
4. `cash`/`card` присваиваются (`=`), не аккумулируются — при нескольких группах перезатирание.
5. Маппинги (`ReconcileMapping`/`mapping.py`) есть, но в fuel-ingest не применяются.

## 10. План реализации

1. **Контракт смены**: парсить `sales` → решётка `pay_type.name × service_code → {volume, cost, discount}`; модель `fuel_shift_sale`.
2. **Контракт ТТН**: фикс `base.name`/`base.id`, поля `doc/fact` (volume/amount/density/temp); сохранять `tank`.
3. **Справочник `payment_channels`** + seed ГИГ + CRUD/UI.
4. **Справочник `payment_mappings`** (матч по подстроке) + seed 20 образцов + UI на канале `fuel_shift`.
5. **Справочник `fuel_mappings`** (т/л/плотность) + seed §4 + UI на канале `fuel_delivery`.
6. **Применить маппинги в ingest** (`fuel_router`): резолв канала/топлива на загрузке, заполнение `fuel_shift_sale`.
7. **Конвейер пакетов**: shift→{ОРП,ПКО,Перемещения,Списание}, ТТН→{Перемещение_т,Комплектация} с натуральными ключами `TL|СМЕНА`/`TL|ТТН`.
8. **UI каналов**: маппинги, разбивка по каналам, предпросмотр документов.
