# Проект ЭЗС: жизненный цикл от участка до эксплуатации

> Разбор запроса на «пункт Проект» и предлагаемая модель.
> Продолжение `SITES_LAND_BANK_BLUEPRINT.md` (Волны 1–3 сделаны).
> Дата: 23.07.2026.

---

## 1. Что нужно

Вести не «строку в реестре площадок», а **проект**: у него свой номер, паспорт,
крупные этапы и статусы внутри них. Двигаться по статусам можно, только выполнив
обязательное на текущем уровне. Всё, что сделано и сказано, остаётся в логе
проекта. К проекту цепляются документы. Часть шагов порождает записи в учёте —
подписали аренду, значит договор должен появиться в бухгалтерии.

Крупные этапы, как их описал заказчик:

1. **Создание проекта и анализ участка** — первичные данные, оценка, решение.
2. **Оформление прав** — договор аренды (или иное основание), сопутствующие документы.
3. **Стройка** — техприсоединение, закупка оборудования, монтаж.
4. **Передача в эксплуатацию** — объект работает.
5. **Архив** — не сложилось; усилия и причина остаются в истории.

## 3. Чего не хватает

1. **Номера проекта.** У площадки есть UUID, но нет человекочитаемого
   идентификатора, который можно назвать в переписке и на совещании.
2. **Крупных этапов.** Есть 10 стадий подряд; заказчик мыслит четырьмя блоками,
   и отчётность нужна по ним.
3. **Развёрнутой стройки.** Сейчас весь третий этап — один статус «В стройке».
   Внутри него минимум пять разных состояний (заявка на ТП → ТУ получены →
   договор ТП → оборудование закуплено → смонтировано → пусконаладка).
4. **Жёстких условий перехода.** Гейты предупреждают, но пропускают. Заказчик
   просит запрет: не закрыл обязательное — статус не меняется.
5. **Документов проекта.** ЕГРН, ТУ, договор, схемы, фото, переписка — сейчас их
   некуда положить рядом с площадкой.
6. **Связи с учётом.** Подписанный договор аренды должен превращаться в запись
   `contracts` + привязку к объекту; закупка — в `ezs_supply_documents`; ввод —
   в `service_locations`. Сейчас все три перехода делаются руками и вне системы.
7. **Отчётов по проектам.** Воронка по этапам, сроки прохождения, просрочки,
   бюджет (план/факт), «что ждёт бухгалтерию».

## 4. Предлагаемая модель

### 4.1 Проект — это площадка, а не новая сущность

Рекомендация: **не заводить отдельную таблицу проектов**, а достроить
`ezs_sites`. Причины:

- отношение 1:1 — на участок ведётся один проект строительства;
- 1 013 записей уже имеют стадии, гейты, историю, ответственных и скоринг —
  дублирование сущности означало бы вечную сверку двух реестров;
- «свой ID» решается человекочитаемым номером на той же записи:
  `ЭЗС-2026-0042` (год + порядковый номер по компании).

Оговорка на будущее: если на одном участке появится вторая очередь, заводится
новый проект со ссылкой на исходную площадку (`parent_site_id`). Это редкий
случай, закладываем поле, но не строим под него интерфейс.

### 4.2 Этапы и статусы

| Этап | Статусы внутри | Что должно быть закрыто, чтобы уйти дальше |
|---|---|---|
| **1. Подбор** | Лид → Скрининг → Переговоры → Проработка → Решение | адрес и координаты; собственник и контакт; свободная мощность; смета подключения; форма контроля; инвестрешение |
| **2. Оформление** | Подготовка документов → На подписи → Договор подписан → Зарегистрирован | подписанный договор (файл), срок и ставка, **запись в учёте** |
| **3. Стройка** | Заявка на ТП → ТУ получены → Договор ТП → Оборудование закуплено → Смонтировано → Пусконаладка | ТУ (файл), договор ТП, документ поставки, акт монтажа |
| **4. Эксплуатация** | Введена | объект заведён в реестре сети, первая сессия прошла |
| **Архив** | Отклонена | причина из словаря |
| **Заморозка** | Пауза | дата пересмотра |

Текущие 10 стадий ложатся сюда без потери данных: `lead…decision` → этап 1,
`contracting` → этап 2, `construction` разворачивается в пять статусов этапа 3,
`live` → этап 4.

### 4.3 Обязательность: запрет с правом обхода

Каждый пункт гейта получает признак **обязательный / желательный**.

- обязательный не закрыт → кнопка перехода заблокирована, рядом сказано, чего
  не хватает;
- у роли «руководитель развития» есть **обход с обоснованием**: переход
  выполняется, обоснование обязательно и уходит в лог как отдельное событие.

Почему не жёсткий запрет без исключений: практика показывает, что процесс
встаёт из-за одной галочки, которую физически некому поставить (нет доступа к
документу, отпуск, подрядчик задерживает акт). Тогда работа уходит в почту и
таблицы — то есть ровно туда, откуда мы её забираем. Обход с обоснованием
оставляет решение внутри системы и оставляет след.

### 4.4 Документы проекта

Новая таблица `ezs_site_docs`: `site_id`, `file_id` (существующий `source_files`),
`kind`, `title`, `stage`, `uploaded_by`, `created_at`.

Типы: выписка ЕГРН, схема участка, фото места, коммерческое предложение,
договор аренды, ТУ, договор ТП, проект, акт монтажа, акт ввода, переписка.

Часть типов — обязательные пункты гейта: например, «Договор подписан» требует
приложенного файла договора, а не только галочки.

### 4.5 Точки касания с учётом

| Событие проекта | Что создаётся в учёте | Существующая опора |
|---|---|---|
| Договор аренды/сервитут подписан | `contracts` (`basis` = договор / сервитут / разрешение) + связь с проектом | модель есть, 883 договора, `basis` заполнен у 109 |
| Оборудование закуплено | `ezs_supply_documents` + строки | контур есть, документов 0 |
| Объект введён | `service_locations` + связь `ezs_sites.location_id` | поле связи уже заведено |
| Аренда начислена | платёжная дисциплина в «Хозяйстве» | `station_contract_settlements` |

⚠ Сейчас `contract_locations` связывает договор со **станцией**, которой у
проекта ещё нет. Нужна связь договор ↔ проект (`ezs_site_id` в связке), иначе
аренда земли под будущую станцию повиснет без объекта.

Принцип: **система предлагает, человек подтверждает.** При переходе «Договор
подписан» открывается форма создания договора с предзаполненными полями
(контрагент, основание, срок, ставка) — но запись создаётся по кнопке, а не
автоматически, потому что бухгалтерский контур не должен наполняться побочным
эффектом смены статуса.

### 4.6 Экраны

Один раздел «Проекты», внутри — вкладки:

1. **Реестр проектов** — номер, объект, этап, статус, ответственный, следующий
   шаг, срок, бюджет; фильтры по этапу, ответственному, просрочке.
2. **Карточка проекта** — Паспорт · Этапы (визуальная лента с гейтами) ·
   Документы · Экономика · Учёт (договор, поставка, объект) · История.
3. **Обзор проектов** — воронка по четырём этапам, средний срок этапа,
   просроченные, «зависшие», плановый и фактический бюджет.
4. **Ждёт учёта** — рабочий список: подписан договор, но нет записи в
   бухгалтерии; закуплено оборудование без документа поставки; введён объект без
   станции в реестре.

Существующие пункты «Обзор пайплайна», «Реестр площадок», «Приоритеты», «Карта»
остаются: они отвечают на вопрос «где строить», а «Проекты» — «как идёт стройка».

## 5. План работ

| Волна | Содержание | Зачем |
|---|---|---|
| **4. Проект как объект** | номер проекта, этапы поверх статусов, развёрнутая стройка (5 статусов), жёсткие гейты с обходом по обоснованию, лента этапов в карточке | появляется сам предмет управления |
| **5. Документы** | `ezs_site_docs`, загрузка и просмотр в карточке, документ как обязательный пункт гейта | доказательная база рядом с проектом |
| **6. Связь с учётом** | договор ↔ проект, создание договора из проекта, документ поставки, ввод объекта в сеть, отчёт «Ждёт учёта» | замыкание цикла на бухгалтерию |
| **7. Отчётность** | обзор по этапам, сроки, бюджет план/факт, выгрузка | управление портфелем проектов |

Волны 4 и 5 имеет смысл делать подряд: без документов жёсткие гейты упрутся в
пункты, которые нечем закрыть.

## 6. Развилки, которые стоит закрыть до начала

1. **Проект = площадка** (рекомендую) или отдельная сущность со своей таблицей?
   От этого зависит вся модель.
2. **Жёсткость гейтов**: блокировать с правом обхода по обоснованию (рекомендую)
   или блокировать полностью?
3. **Кто заводит договор в учёте** — руководитель проекта прямо из карточки или
   бухгалтерия по уведомлению из списка «Ждёт учёта»?
4. **Нумерация проектов**: сквозная по компании (`ЭЗС-2026-0042`) или с кодом
   региона (`ЭЗС-СВЕ-2026-007`)?
