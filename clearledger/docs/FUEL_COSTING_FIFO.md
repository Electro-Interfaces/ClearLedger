# Партионный учёт себестоимости топлива (FIFO) — дизайн

> Статус: ДИЗАЙН (не реализовано). Обсуждение 2026-07-02.
> Цель: менеджер задаёт себестоимость партий (ТТН-сливов), система списывает её
> на продажи по ФИФО и считает маржу по всем разрезам учёта — на входном слое,
> до и независимо от проводок 1С.

## Проблема (пробел)

Сейчас маржа (`analytics_service.pnl`) считает себестоимость (COGS) **только из
проводок 1С Дт 90.02** документов ОРП — постфактум, после проведения в БП. По видам
топлива COGS размазывается грубой пропорцией (сам код: «без раскрытия проводок
невозможно точно отнести»). На входном слое (ТТН) себестоимости нет: поля
`FuelReceipt.doc_cost/fact_cost` — заглушки (всегда 0), в `FuelReceiptOverride`
поля cost нет. FIFO-движка в TradeLedger нет.

## Концепция

- **Партия** = ТТН-слив (АЗС × вид топлива × объём/масса × дата поступления ×
  **себестоимость**). Себестоимость задаёт менеджер.
- **ФИФО-списание**: по каждому сменному отчёту (в хронологии) проданные литры
  списываются из партий той же АЗС и вида топлива по ФИФО — «из какой партии взят
  проданный литр». Каждый литр несёт себестоимость своей партии.
- **Разрезы**: маржа = выручка − ФИФО-себестоимость в любом разрезе
  (вид топлива × вид оплаты × станция × смена × период).
- **На уровне ТТН** менеджер видит ценовые показатели по разрезам: себестоимость,
  списано / остаток партии, средняя цена реализации, маржа партии.

## Выбранные параметры (дефолты, на подтверждение)

- **Единица себестоимости:** обе — ₽/л и ₽/кг, взаимный пересчёт через плотность ТТН
  (закупка обычно в ₽/т по массе, продажи — в литрах).
- **Fallback, если себестоимость не задана:** справочная закупочная цена из 1С
  (`NomenclaturePrice`, вид «Закупочная (документы)») как подсказка/дефолт; менеджер
  может перебить. Партии без себестоимости и без fallback — помечаются «нет себест.»,
  их литры в марже не участвуют (с предупреждением).
- **Маржа:** управленческая (FIFO, входная себестоимость) — **отдельно** от
  бухгалтерской (COGS из 90.02), не замещает её. В `MgmtMargin` — переключатель источника.

## Модель данных (бэкенд)

### Шаг 1
- **`FuelReceiptCost`** — себестоимость на ТТН. Натуральный ключ
  `(company_id, station_id, ttn, fuel_code)` — переживает reingest (паттерн
  `FuelReceiptOverride`). Поля: `unit` (`liter`/`kg`), `unit_cost`, `total_cost`
  (денормализация), `density_used` (для пересчёта л↔кг), `source`
  (`manual`/`onec_price`/`purchase_batch`), `purchase_batch_id?`, `note`,
  `created_at`/`updated_at`.

### Шаг 2
- **`FuelPurchaseBatch`** — крупная закупка: `supplier`, `fuel_code`,
  `total_liters`/`total_mass`, `unit`/`unit_cost`, `purchase_date`,
  `target_station_ids[]`, `status`. Аллокатор раскидывает объём партии на ТТН
  выбранных АЗС по ФИФО (по дате ТТН), создавая `FuelReceiptCost` со ссылкой
  `purchase_batch_id`.

## FIFO-движок (новый сервис `fuel_costing.py`)

Для каждой пары **АЗС × вид топлива** за период:
1. Очередь партий = ТТН с себестоимостью, отсортированные по дате поступления (FIFO).
   Каждая партия несёт `остаток_литров` и `себест_₽/л`.
2. Продажи = литры по видам топлива из смен (`FuelShiftSale`/`FuelPump`), в хронологии смен.
3. Списание: продано X л → берём из головы очереди; не хватило — из следующей партии.
   Каждая порция несёт себестоимость своей партии.
4. Себестоимость смены = Σ (списанные литры из партии i × себест i).
   Внутри смены разносим на **вид оплаты** пропорционально литрам канала (`FuelShiftSale`).

Возвращает: себестоимость и маржу по разрезам (топливо/оплата/станция/смена/период) +
по каждой партии (списано, остаток, выручка от списанного, маржа партии).

Замечания: FIFO **пооперационно по АЗС** (партии станции списываются продажами станции).
Начальный остаток на АЗС (топливо до первой заведённой ТТН) — отдельная «партия-остаток»
с fallback-себестоимостью (иначе первые продажи периода без себестоимости).

## Вписывание в архитектуру Источник → Канал → Разрез (источник-форма)

Себестоимость — не отдельная приблуда, а **данные источника нового типа «форма ручного
ввода»** (`manual_form`), текущие по обычному конвейеру. В системе уже есть ручные
источники `manual_table`/`charge_sessions_excel` (status `available`) с полным путём
Источник→Канал→L1→Нормализация→L2→Разрез; эталон ingest — `services/reestr_normalize.py`.
Пробел: нет типа-источника «интерактивная форма» (есть загрузка файла, не диалог ввода
записей) и привязки формы к потоку канала.

**Канал ТТН (`fuel_delivery`), два потока:**
- `anchor` — STS ТТН-сливы (объём/масса/плотность, автомат, `ingest_fuel_deliveries`).
- `reference` — новый источник `manual_form` «Себестоимость партий»: менеджер вводит
  ₽/л или ₽/кг по партиям в диалоге.

**Поток формы → L2:** сабмит формы → `DataEntry(layer='raw', source='manual', channel_id,
source_label)` (как `ingest_reestr`) → нормализация в доменный L2 `FuelReceiptCost`
(+ `DataEntry(clean, derived_from_entry_id=raw.id)`, lineage). Разрез — FIFO-маржа.

**Как добавить источник-форму (точки расширения, из карты кода):**
- Адаптер `@register_adapter("manual_form")` (`server/app/adapters/`), `status='available'`,
  `test_connection→ok`; автоимпорт в `adapters/__init__.py`. UI каталога источников
  подхватит через `/source-types` + `SourcesPage`.
- Схема полей вводимой записи — переиспользовать `MetadataField`/`DocumentType.metadataFields`
  (`src/config/profiles.ts`) + рендер `ManualEntryForm`/`MetadataFieldsRenderer` (уже есть),
  ЛИБО новое поле `record_schema` на адаптере (по образцу `setup_schema` = поля подключения).
- Привязка к каналу: `ChannelStream(source_id=<manual_form Source>, doc_type_id='ttn_cost',
  role='reference')`; либо `ChannelTemplateDecl` c потоком `StreamDecl("manual_form","ttn_cost",…)`.
- Данные пишутся при сабмите формы; прогон канала (`POST /channels/{id}/ingest`) выполняет
  только стадию нормализации (в `channel_orchestrator.run_channel` — ветка `manual_form`
  или запись сразу при сабмите).

**Переиспользуемый образец:** `manual_table`/`reestr_normalize` — рабочий ручной источник
с идемпотентным L1→L2 и lineage; `manual_form` строится по той же схеме, только вход —
dict из формы, а не строки xlsx.

**Два способа ввода себестоимости (оба → один L2 `FuelReceiptCost`):**
1. Источник-форма в канале — массовый ввод партий (архитектурный путь).
2. Быстрая правка на карточке ТТН (`PATCH /fuel/receipts/{id}/cost`) — одиночная (как корректировка).

## Статус зависимостей (важно для оценки объёма)

- Рантайм источников/каналов/оркестратора, ручной upload-источник (`manual_table`,
  `reestr_normalize`), L1→L2 lineage — **работают**.
- Контракт `SourceAdapter.fetch_delta/parse` в рантайме НЕ используется (загрузка идёт мимо,
  через оркестратор напрямую); `RawBatchRecord` пустая; control-потоки/reconcile в топливных
  шаблонах — `planned`. Значит источник-форму строим по факту-пути (оркестратор +
  доменный ingest), а не через аспирационный `fetch_delta`.
