# Техприсоединение: условия, документы и ответственность

Вкладка проекта «Присоединение» ведёт технические сведения, факты шагов,
ответственных, комплект заявки, замечания и этапы выполнения ТУ. Она не меняет
стадию проекта: это остаётся ответственностью существующей службы процессов.

## Сценарии

- Способ: прямое / опосредованное подключение / оплата арендодателю.
- Основание: новое присоединение / увеличение мощности / перераспределение.
- Снабжение: через арендодателя / прямой договор со сбытом / через сетевую /
  существующий договор из реестра. Шаги снабжения доступны и без заявки на ТП.
- Увеличение требует документов о ранее присоединённой мощности; перераспределение
  дополнительно требует соглашения. Представитель и помещение в МКД добавляют
  соответствующие документы. Дополнительные требования сетевой задаются явно.

Печатная заявка выбирает юрлицо, подставляет основание, мощности, реквизиты и даты
проектирования/ввода. Бланк рассчитан на суммарную мощность до 150 кВт включительно;
для большей мощности сервер отказывает, а не выдаёт неподходящий бланк.

## Работа человека

Сначала сохранить основные параметры ТП, затем условия и ответственность.
Общие назначения исполнителя, контролирующего и поставщика данных действуют по
умолчанию; отдельный шаг может иметь свои назначения и плановую дату.

Файлы проекта загружаются непосредственно у требования. Общие PDF юрлица (ЕГРЮЛ,
доверенность, согласие, карточка организации) загружает администратор один раз;
другие проекты того же заявителя получают ссылку. Чужие организации и компании
не допускаются. Истёкший документ не подтверждает комплект.

Наличие и проверка содержания разделены. Подтверждение относится к составу файлов:
замена/добавление файла снимает готовность до повторной проверки. При сохранении
сверяются версия карточки и отпечаток состава документов. Конфликт возвращает 409
и сохраняет черновик формы. Изменение основных параметров не стирает этот черновик.

У замечания есть область (заявка, приёмка ТУ, сбыт), дата получения, срок, ответ и
дата снятия. Снять замечание без ответа или раньше получения нельзя. Этап ТУ
хранит работы, подрядчика/договор, исполнителя и даты выполнения, уведомления и
приёмки; порядок дат проверяется сервером.

Сроки 3/20/30/5 дней перенесены из исходной рабочей схемы. Три дня относятся к
проверке комплектности, а не к принятию заявки. Это рабочие ориентиры; отдельный
срок шага или ответа задаётся явно. Автоматическое определение правового режима
и полный справочник нормативных сроков в этот механизм не входят.

## Доставка и закрытие

Регламент проверяет комплекты, сроки шагов, этапов и замечаний. После сборки
документов сообщает исполнителю; после закрытия передаёт контролирующим ссылку на
проект с итоговыми документами. Используется штатный личный канал «Уведомления».
Внешних писем этот механизм не отправляет.

Запись сообщения и подтверждение доставки выполняются одной транзакцией.
Повторный тик не дублирует сообщение. Отказ штатной политики (например,
`system_notifications_admin_only`) не считается доставкой и не обходится.
Получатель повторно проверяется по членству, объекту и юрлицу.
Для адресных сообщений ТП предусмотрено отдельное исключение
`company.customization.tp_notifications_to_assignees=true`. По умолчанию оно
выключено: без решения владельца общая политика не расширяется. Исключение не
разрешает остальные системные сообщения.

Закрытие требует итоговых актов, завершения этапов, снятия замечаний, документа
снабжения при выбранной ветке и контролирующего. Состав файлов фиксируется в
архивном снимке. Для изменения закрытого комплекта сначала снимается отметка
завершения. Документы остаются в проекте, связанном с объектом.

## Технические границы и проверка

- `EzsTechConnection.workflow` и `workflow_version`: предметные данные и версия.
- `TpOrganizationDocument`: общие файлы конкретного юрлица.
- `/sites/{id}/tech-connection/workflow`: чтение и сохранение.
- `/sites/{id}/tech-connection/shared-documents`: загрузка PDF и защищённое чтение.
- `ezs_tp_workflow.run_notifications`: часть существующего регламента.
- Старые записи сохраняются без автоматического назначения людей и подтверждения бумаг.

HTTP/SQL: отдельная локальная `tp_test`, тест `test_tp_workflow_integration.py`.
Он отказывается работать с другой базой или удалённым хостом. Фикстура не
подключает общий conftest. Браузер: `e2e/tech-connection/README.md`.

## Исполнение методики через Поддержку

Отметка «Вести работу по методике энергетика» включает два независимых процесса
`tp_connection` и `tp_supply`. По умолчанию она выключена у прежних карточек.
Ядро передаёт факты и участников через фасад `projects_process`; переходы и
назначение текущего исполнителя выполняет штатный движок Поддержки. Интерфейс
показывает его стадию, исполнителя, время сверки и ошибку связи. Регламент
повторяет синхронизацию; повтор не создаёт второй процесс или уведомление.
Изменение ответственного обновляет исполнителя текущей стадии. Запоздавшее
действие прежней стадии не возвращает старое назначение.

Основной маршрут: сбор → проверка → подача → договор и ТУ → работы → проверка
сетевой → итоговые документы → личное ознакомление → завершение. Замечания
сетевой возвращают сборщику задачу дополнения. Сбыт ведётся отдельно и требует
своего комплекта, даты и договора. Даты шагов подтверждает назначенный исполнитель
или контролирующий; административный доступ сохраняется.

Кнопка заполнения из паспорта берёт только пустые поля, показывает источник и
сохраняет ручные значения. Источники: явные поля паспорта объекта, плановая
мощность проекта, контрагент договора электроснабжения и единственное предыдущее
завершённое ТП этого объекта. Номинал оборудования не считается выделенной
мощностью. При неопределённых мощности/напряжении диапазон не угадывается.

Комплект учитывает суммарную новую и существующую мощность, напряжение, схему
подключения, представителя, МКД и явные признаки проектной документации и ПА.
План расположения обязателен, однолинейная схема нужна от 35 кВ; для мощности
свыше 50 МВт запрашивается внешняя схема. Для завершения свыше 670 кВт при
напряжении свыше 1 кВ нужны испытания и нормальная схема. Это предметные проверки
карточки, а не автоматическое юридическое заключение. Для мощности свыше 150 кВт
интерфейс направляет к официальным формам сетевой организации.

При закрытии создаётся отдельный документ «Комплект завершения ТП» в «Треке»:
неизменяемый ZIP с манифестом, файлами ТП и ссылками на первоисточники. В пакет
включаются текущие версии связанных документов «Трека» и общие файлы юрлица;
посторонние материалы проекта не включаются. Каждый контролирующий получает
свой штатный `DocAcquaint` и подтверждает ознакомление только за себя.
Процесс завершается после всех подтверждений. Повторное открытие карточки
отменяет ожидающие подтверждения прежнего пакета; старый документ сохраняется.

Дополнительные API: `POST .../tech-connection/prefill` и
`POST .../tech-connection/acquaint`. Установка двух маршрутов выполняется
скриптом поставки `scripts/tp/install_routes.py` только для явно указанного
UUID компании Поддержки, взятого из реестра связей приложений. Повторная
установка не переписывает граф. Тест движка: `scripts/test/tp-method.mjs`
в TSupport на отдельной локальной `support_test`.
