# Навигация по документам пространства

`GET /api/references/space-documents?company_id=…` остаётся проекцией существующих
`Contract`, `DocCard` и `EzsSiteDoc`. Чтение не создаёт карточек или файлов.
Проверка членства находится в references router, чтение `DocCard` использует
штатный `_readable_doc_clause`. Права на изменение и скачивание проверяются
соответствующими API владельца документа.

Минимальное дополнение существующего TypeScript-контракта:

```ts
interface SpaceDocumentOwners {
  docId?: string               // DocCard: всегда, независимо от файла/договора
  contractId?: string | null   // Contract или основной владелец DocCard
  contractIds?: string[]       // все доступные договорные связи DocCard
  siteId?: string              // EzsSiteDoc: проверенная площадка
  projectId?: string | null    // явный EzsSiteDoc.project_id, проверенный по company/site
  siteDocId?: string           // ID самого EzsSiteDoc
}
```

Прежние `id`, `docType`, `title`, `catalog`, `date`, `fileId`, `fileName`, `size`,
`status` сохраняются. Отсутствующее поле и `null` не дают основания угадывать
владельца по названию, пути каталога или ID другой сущности.

У `DocCard` один лист с прежним `id = doc-<UUID>`. `contractIds` включает
существующий договор своей компании из `subject_ref` и все договорные
`DocRelation` той же компании, без повторов. Корректный `subject_ref` идёт
первым; остальные UUID отсортированы. Если предмет ошибочный или чужой,
выбирается первый доступный договор из отсортированных связей. `contractId`
и каталог соответствуют первому владельцу; остальные владельцы доступны через
`contractIds`. Карточка без договоров сохраняет `docId` и попадает в «Трек».

Основной файл `DocCard` выбирается из текущих неудалённых версий своей компании:
`signed_scan` → `body` → `appendix` → `attachment` → неизвестные роли.
Внутри приоритета: `revision DESC`, `uploaded_at DESC`, `id ASC`.
Текущая редакция существует отдельно для каждой роли, поэтому порядок строк
запроса и более позднее приложение не определяют основной файл.

Для `EzsSiteDoc` площадка должна принадлежать компании документа. Явный проект
публикуется только при совпадении его компании и площадки. При ошибочной
проектной связи документ остаётся у своей площадки с `projectId = null`.
Документы с чужой площадкой исключаются; чужой файл площадки не публикуется.
Проект не подбирается по имени или наличию единственного проекта на площадке.
Для явно привязанных проектов в каталоге добавлен уровень с названием и полным
UUID проекта: два проекта одной площадки с одинаковыми названиями разделены.
Для документов без проекта прежний путь каталога сохранён.

Действующий экран владельца площадки:
`/projects?mode=projects&sub=pr_project&project=<siteId>&ptab=docs`.
Несмотря на имя параметра `project`, текущий `getSite` обращается к
`/api/sites/{id}` и ожидает `EzsSite.id`. Настоящий `projectId` нельзя
подставлять вместо `siteId`. Выбор конкретного `EzsProject` и отдельного файла
внутри этого экрана пока не поддержан; новые маршруты проекция не создаёт.

Регрессии: `server/tests/test_space_documents.py` и существующий
`test_contract_scope.py::test_space_documents_tree`. Интеграционные тесты
запускаются только с отдельной `TEST_DATABASE_URL` и штатной SQL-схемой.
