# Коннекторы АСУиМ ЭЗС — загрузка из аналитической витрины РусГидро

Концепция подключения Учёта к ежедневной выгрузке АСУиМ ЭЗС (админпанель, через
которую идут продажа и реализация зарядных сессий).

Первоисточник постановки: `D:\Downloads\АСУиМ ЭЗС. Ежедневная выгрузка данных. Описание-1.docx`
(АО «ЭЗС РусГидро» / ООО «РусГидро ИТ сервис»).
Каркас, в который всё встраивается: `server/app/adapters/catalog.py` (типы источников),
`server/app/channel_catalog.py` (каналы), `server/app/services/channel_orchestrator.py` (прогон).

---

## 1. Что изменилось

Сейчас данные ЭЗС попадают в Учёт файлами из админпанели: `charge_sessions_excel`
(«Сессии (NN).xlsx»), `stations_excel` («Станции (NN).xlsx»), `manual_table` (реестры договоров
и тарифов э/э). Человек выгружает, кладёт файл в канал, жмёт «обработать».

РусГидро ИТ сервис построил постоянную витрину: данные АСУиМ ежедневно в 01:00 МСК
переносятся Airflow-задачей в аналитическую базу **ClickHouse** и лежат там **13 именованных
представлений** с русскими названиями колонок. Доступ — только чтение, TLS.

| Параметр | Значение |
|---|---|
| Сервер | `ch.rushydro.ru`, порт `8443` |
| База | `ecs` |
| Учётная запись | `ecs_reader` (только чтение, пароль передаётся отдельно) |
| Обновление | ежедневно 01:00 МСК |
| Глубина | сессии и платежи — с 01.09.2025, инкрементно; справочники — полная перезагрузка |
| Служебное поле | `_дата_выгрузки` (`_load_date`) — момент загрузки записи |

Меняется не только регулярность. Витрина — **стабильный контракт данных**: фиксированный
состав полей, человекочитаемые имена, техническое имя рядом для сопоставления, обещание
расширять состав без изменения способа подключения. Выгрузки админпанели такого не давали.

## 2. Два пути доставки, одна обработка

Способ подключения — вопрос доступа заказчика, а не архитектуры. Готовим оба, начинаем с того,
который доступен без согласований.

### Путь А (основной сейчас): Excel → файл → канал Учёта

Сотрудник с рабочим местом внутри контура подключается к витрине из Excel по ODBC (ровно так,
как описано в документе заказчика), выгружает нужное представление и сохраняет файл. Файл
грузится в канал Учёта — тем же способом, каким сегодня грузятся «Сессии» и «Станции».

Почему это работает не хуже: **Excel отдаёт те же колонки с теми же русскими именами**, что и
прямой запрос к базе. То есть маппер «колонка представления → поле Учёта» пишется один раз и
работает для обоих путей. Разница только в том, кто и как принёс строки.

Регламент выгрузки — §5.

### Путь Б (когда дадут доступ): прямое чтение витрины

`ch.rushydro.ru` **не резолвится в публичном DNS** (проверено 27.07.2026 с рабочей машины:
`Non-existent domain`) — это внутренний хост контура РусГидро. Чтобы Учёт читал витрину сам,
нужен маршрут, в порядке предпочтения:

1. Публикация витрины для белого IP ВМ пилота `elsy-eco-01` — TLS и права read-only уже есть,
   не хватает только сетевого доступа.
2. VPN-пир в контур РусГидро для `elsy-eco-01` (задача того же класса, что доступ к
   TradeLink-хабу в overlay).
3. Агент-выгрузчик внутри контура заказчика: служба читает ClickHouse и отправляет батчи в API
   Учёта (push вместо pull).

Плюс подтвердить, что HTTP-интерфейс ClickHouse на 8443 открыт: официальный ODBC-драйвер,
описанный в документе, ходит именно поверх HTTP(S), поэтому с большой вероятностью да — но
проверяем фактом.

### Промежуточный путь: файл без человека

Если ручная выгрузка станет рутиной, средний вариант дешевле полного доступа: сотрудник или
задача заказчика кладёт файлы в согласованную папку (Nextcloud `cloud.dataworker.ru` или
почтовый ящик), Учёт забирает их сам. Транспорт файловый, ручной работы нет, доступа в контур
не требуется. Делать это стоит тогда, когда надоест грузить руками, — не раньше.

## 3. Один тип источника со способом получения

**`asuim` — «АСУиМ ЭЗС (витрина РусГидро)»**, категория «Электромобильность (ЭЗС)».
Одна запись в справочнике источников, внутри — 13 `doc_type` по числу представлений и поле
**«Способ получения»**: `file` (выгрузка из Excel) либо `clickhouse` (прямое подключение).

Паттерн уже принят в каталоге — так устроен `acquiring_sber` (`mode`: API банка / реестр
файлом / реестр почтой). Заводить два типа источника под один и тот же набор данных незачем.

Для `mode=file` настройка источника пустая: файл приходит в канал, лист определяется по
заголовкам. Для `mode=clickhouse` — хост, порт (8443), база (`ecs`), пользователь, пароль
(secret, шифруется Fernet), TLS, размер батча.

Транспорт прямого пути — **`httpx` (уже в зависимостях) и HTTP-интерфейс ClickHouse**, без ODBC
и клиентской библиотеки:

```
POST https://ch.rushydro.ru:8443/?database=ecs
Authorization: Basic ecs_reader:***
body: SELECT * FROM charge_sessions_ru
      WHERE "дата_начала" >= {since} AND "дата_начала" < {until}
      ORDER BY "дата_начала" LIMIT {n} OFFSET {k} FORMAT JSONEachRow
```

`test_connection`: для `file` — «загрузите выгрузку в канал»; для `clickhouse` —
`SELECT count() FROM stations_ru`, одним запросом проверяет сеть, права и наличие представлений.

## 4. Разбор файла по именам колонок, а не по номерам

Существующие парсеры (`parse_sessions_xlsx`, `parse_stations_xlsx`) читают колонки **по
индексам** — это оправдано для выгрузок админпанели, где заголовки были нестабильны, но для
витрины неверно: заказчик обещает расширять состав полей, и любая вставленная колонка сдвинет
весь разбор.

Для витринных файлов разбираем **по заголовку**: `id_сессии`, `дата_начала`, `энергия_квтч` —
имена документированы в приложении 1 и совпадают с именами полей в базе. Отсюда:

- перестановка и добавление колонок ничего не ломают;
- один и тот же маппер обслуживает и файл, и прямой запрос;
- новое поле в витрине — одна строка в таблице соответствий, а не пересчёт индексов.

**Автоопределение формата** при загрузке: если в заголовке есть `id_сессии` / `id_станции` —
витринный маппер; иначе — существующий индексный разбор старых выгрузок. Уже загруженные
данные и старые файлы продолжают работать.

Канал принимает **несколько файлов сразу** — механика есть в `reestr_contracts_payments`
(`config.uploadFiles`, формат определяется автоматически). Выгрузил четыре представления —
положил четыре файла в один канал, каждый опознаётся сам.

## 5. Регламент выгрузки для сотрудника РусГидро

Что попросить у заказчика делать руками (пока нет прямого доступа).

**Периодичность.** Сессии и платежи — раз в неделю за прошедшую неделю (или раз в месяц за
месяц). Справочники — раз в месяц целиком, плюс внеочередно после массовых изменений.

**Ограничение Excel.** Лист вмещает 1 048 576 строк, и объём сессий это со временем превысит
(раздел 5.1 документа). Поэтому выгрузка **всегда окном по датам**, а не «всё целиком»:

```sql
SELECT * FROM charge_sessions_ru
WHERE "дата_начала" >= '2026-07-01' AND "дата_начала" < '2026-08-01'

SELECT * FROM payments_ru
WHERE "дата" >= '2026-07-01' AND "дата" < '2026-08-01'

SELECT * FROM stations_ru          -- справочники целиком, окно не нужно
SELECT * FROM tariffs_ru
SELECT * FROM organizations_ru
```

Запрос указывается в дополнительных параметрах ODBC-подключения (раздел 5.2 документа).
Кириллические имена полей — в двойных кавычках.

**Формат сохранения.** Лист Excel (`.xlsx`) с шапкой в первой строке — как есть, без
переименования колонок, без объединённых ячеек и итоговых строк. CSV UTF-8 тоже принимаем.
Вариант «Только создать подключение → модель данных» для нас не подходит: данных на листе нет,
файл нечего грузить.

**Именование файлов** — чтобы канал и человек не путались:
`asuim_<представление>_<период>.xlsx`, например `asuim_charge_sessions_ru_2026-07.xlsx`,
`asuim_stations_ru_2026-07-28.xlsx`.

**Повторные и пересекающиеся окна безопасны.** Дедуп по `id_сессии` стоит в базе Учёта
(`UNIQUE(company_id, session_ext_id)`), режим `append` не размножит записи — пересечение дат
на стыке недель ничего не испортит. Лучше перекрыть, чем потерять.

## 6. Каналы: четыре конвейера

Каналы группируются не по представлениям, а по разрезам Учёта — как уже сделано для топлива
и сопутки. Для `mode=file` расписание ручное (загрузка), для `clickhouse` — по cron.

| Канал | Потоки (представления) | Режим | Расписание при прямом доступе |
|---|---|---|---|
| **ЭЗС: сессии и платежи** | `charge_sessions_ru` (anchor), `payments_ru` (control) | инкремент по `дата_начала` / `дата` | ежедневно 03:00 МСК |
| **ЭЗС: станции и коннекторы** | `stations_ru` (anchor), `connectors_ru`, `chargepoint_groups_ru`, `brands_ru` (reference) | полная перезагрузка, upsert | ежедневно 03:30 МСК |
| **ЭЗС: тарифы** | `tariffs_ru` (anchor) | полная перезагрузка | ежедневно 03:30 МСК |
| **ЭЗС: клиенты и организации** | `organizations_ru` (anchor), `users_ru`, `rfid_cards_ru` (reference) | полная перезагрузка | ежедневно 03:30 МСК |

Расписание — с запасом после 01:00: витрина обновляется ночью, к 03:00 загрузка заказчика
гарантированно завершена. Планировщик каналов (`services/channel_scheduler.py`) уже умеет
`cron` и `pause_on_error`. Инкремент при прямом доступе держим на существующих
`PullCheckpoint` / `SourceSync`.

## 7. Куда что ложится

| Представление | Приёмник в Учёте | Что делаем |
|---|---|---|
| `charge_sessions_ru` (41 поле) | `charge_sessions` | **переиспользуем `ingest_charge_sessions`**, нужен только маппер колонок; модель расширяем (см. §8) |
| `stations_ru` (71 поле) | `service_locations` (`type='ev_charging'`) | **переиспользуем `ingest_stations`** в режиме `replace`; маппер + разложить новые поля паспорта |
| `payments_ru` (15 полей) | новая таблица `charge_payments` | новая сущность — платежей в Учёте сейчас нет |
| `tariffs_ru` (27 полей) | новая таблица `ezs_tariffs` | сейчас тариф выводится из факта сессий, справочника нет |
| `organizations_ru` (7 полей) | `corporate_clients` | обновление реестра ЮЛ, даты договора, число пользователей |
| `users_ru` (15 полей) | связка «пользователь → организация» | нужен только `id → organization_id` (+ телефон); ФИО/e-mail не храним, см. §9 |
| `connectors_ru` (16 полей) | паспорт станции (`extra_metadata`) | отдельную сущность **не заводим** — разрез по типу разъёма уже есть в сессиях |
| `brands_ru`, `chargepoint_groups_ru` | справочные поля станции | расшифровка `id_бренда` / `id_группы` при загрузке станций |
| `rfid_cards_ru` (8 полей) | справочник карт | нужен для разбора «карта → пользователь»; можно вторым шагом |
| `cars_ru`, `promo_codes_ru` | — | потребителя в Учёте пока нет, откладываем |
| `admins_ru` | — | **не забираем**: только ПДн, ценности для учёта нет |

Главный выигрыш по трудозатратам: `parse_*` приводят строку к внутренним ключам
(`session_ext_id`, `station_code`, `energy_kwh`, …), а вся нормализация и запись живут дальше —
в `ingest_*`. Для витрины нужен **второй парсер поверх тех же ключей**, а не второй конвейер.

## 8. Что витрина даёт нового (главное в этой работе)

Не «то же самое, но регулярнее» — в представлениях есть поля, которых в выгрузках админпанели
не было, и они закрывают дыры в учёте. Это верно независимо от способа доставки.

1. **Доли владельца и компании по каждой сессии** — `доля_владельца_руб` (`owner_amount`),
   `доля_компании_руб` (`company_amount`). Агентская модель в явном виде. Сейчас расчёт с
   владельцами станций живёт только на уровне договоров (`station_contract_settlements`, роли
   `energy`/`rent`/`service`), посессионного факта нет. Появляется сверка «начислено владельцу
   по факту сессий ↔ обязательства по договору» — новое правило `ezs_owner_share` в
   `reconcile_catalog`.

2. **Платёжные транзакции** — `payments_ru` несёт `id_транзакции_банка` (Сбербанк),
   `сумма_холда`, `сумма_возврата`, `статус` и `url_фискального_чека`. Закрывает контур
   «сессия → списание → фискальный чек» без отдельных коннекторов к эквайрингу и ОФД (оба
   сейчас `planned`). Правило сверки `ezs_payments`: сессия ↔ платёж ↔ чек, с подсветкой
   зависших холдов и возвратов.

3. **Точная связка ЮЛ.** Сейчас корпоративный клиент цепляется к сессии по телефону
   (`corporate_clients.phone = charge_sessions.user_id`) — эвристика. В витрине сессия несёт
   `id_пользователя`, а `users_ru` даёт `organization_id`. Джойн становится по ключу; телефон
   остаётся для совместимости и для ФЛ.

4. **Флаг «с админ-панели»** — `is_charge_from_admin_panel`. Сейчас служебные сессии
   отделяются по `charge_type == 'ADMIN'` (эвристика в `_cut_key`). Появляется признак от
   системы — корзина `ezs_admin` строится на факте. Рядом `подозрительная` (`is_suspicious`) —
   отдельный сигнал контроля утечек.

5. **Справочник тарифов** с временны́ми зонами (день/ночь/пик/полупик), периодами действия,
   привязкой к группам станций, группам пользователей и организациям. Сегодня номинал известен
   только из самой сессии, поэтому «факт против номинала» в `tariff_service` сравнивает факт с
   фактом. Со справочником сравнение становится настоящим.

6. **Паспорт станции глубже**: кадастровый номер, счётчик, дата установки и ввода в работу,
   `последняя_активность`, `время_работы_в_процентах`, `процент_успеха`, доступность
   коннекторов, `в_процессе_передачи`. Часть — в свободные поля `service_locations`, остальное
   в `extra_metadata`.

**Расширение модели `charge_sessions`** (новые колонки, миграция одним шагом):
`owner_amount`, `company_amount`, `tariff_ext_id`, `tariff_name`, `is_admin_panel`,
`is_suspicious`, `user_ext_id`, `organization_ext_id`, `connector_ext_id`.
Старые сессии из файлов админпанели остаются с NULL — ничего не переписываем.

## 9. Персональные данные

`users_ru` и `admins_ru` содержат ФИО, телефон, e-mail (раздел 5.4 документа: выгрузки не
передаются третьим лицам и не размещаются в общедоступных ресурсах).

**Решение МАГа 08.08.2026.** Пока не получено отдельное разрешение на обработку персональных
данных, из справочника физических лиц берём **только номер телефона** — он и так является
ключом связи в модели (`charge_sessions.user_id` = телефон). ФИО, отчество, e-mail, логин и
аватар не переносим и не храним: в `ezs_customers` таких колонок нет вовсе, а не «есть, но
пустые». В пробной выгрузке это 1 177 фамилий, 1 258 имён, 1 028 отчеств и 9 587 адресов
почты, которые остались за периметром.

Для **юридических лиц** ограничения нет: телефон корпоративного аккаунта — идентификатор
организации, а не человека, и он используется как ключ связи ЮЛ с сессиями.

`admins_ru` не забираем вовсе. К выдаче пользовательских полей в интерфейсе применяем
`services/pii_masker.py`.

Отдельно для файлового пути: выгруженные файлы содержат ПДн, поэтому канал загрузки — обычный
режим хранения `source_files` внутри контейнера заказчика, наружу файлы не уходят.

## 9б. Битые показания счётчика (28.08.2026)

Витрина отдаёт зарядки, которых физически не было: счётчик станции изредка врёт
разностью показаний, и в выгрузку уезжают тысячи кВт·ч за секунды. Живой пример —
ЭЗС 584 «Овчинникова» (Владивосток) 03.07.2026: **10 341 кВт·ч за 11 секунд на
226 468 ₽**, тогда как фактическое списание по этой же сессии — 1007,40 ₽, чек ОФД
на месте. Одна строка завысила день в 2,3 раза (396 450 ₽ вместо ≈171 тыс).

По базе пилота таких десять, они завышают отпуск на 42 тыс кВт·ч и выручку на
805 тыс ₽. Колонкой `подозрительная` источник их не метит — для витрины это
обычные завершённые сессии.

**Правило** (`is_meter_error` в `services/charge_sessions_normalize.py`): отпуск
больше 150 кВт·ч при подразумеваемой мощности выше 350 кВт (самая быстрая станция
сети) — брак. Строка идёт в журнал разбора с `reason='meter_error'`, в учёт не
попадает. Судим по отпуску, а не по деньгам: сумма считается из той же энергии по
тарифу и отдельного сигнала не несёт.

**Два порога, а не один** — граница проходит между двумя живыми группами:

| Что за строки | Энергия | Мощность | Платёж | Решение |
|---|---|---|---|---|
| Брак счётчика | 1 011–12 789 кВт·ч | тысячи кВт | в 100–1000 раз меньше суммы | в журнал |
| Врёт длительность | до 46 кВт·ч | до 1000 кВт | равен сумме до рубля | в учёт |
| Грузовой транспорт | до 200 кВт·ч | до 262 кВт | равен сумме до рубля | в учёт |

Порога по одной мощности не хватает: он забрал бы 327 нормальных сессий, где врёт
не счётчик, а отметка времени.

**Платёж такой зарядки остаётся в учёте** — в отличие от `suspicious`. Деньги
получены, чек выбит; врут показания, а не касса. Поэтому `ingest_payments` уводит
в журнал только платежи сессий с `reason='suspicious'`.

## 10а. Регламент повторной загрузки (09.08.2026)

Первая выгрузка была разовой операцией. Дальше витрину нужно **обновлять**, и правила у
представлений разные — они следуют из природы данных, а не из удобства кода.

| Представление | Режим | Ключ | Что происходит с тем, чего нет в файле |
|---|---|---|---|
| `payments_ru` | инкремент, окна по датам | id платежа | остаётся (историю не трогаем) |
| `charge_sessions_ru` | инкремент, окна по датам | id сессии | остаётся |
| `stations_ru` | дозаполнение (`partial`) | id станции → код → серийник → номер | остаётся |
| `connectors_ru` | замена паспорта разъёмов у станций из файла | станция + номер разъёма | остаётся у станций вне файла |
| `users_ru` · `rfid_cards_ru` | дозаполнение по ключу | id клиента / id карты | остаётся |
| `organizations_ru` | дозаполнение по ключу | id организации, фолбэк по имени | остаётся |
| `tariffs_ru` · `brands_ru` · `chargepoint_groups_ru` · `cars_ru` | **полная перезагрузка** | — | **удаляется**: справочник приходит целиком |
| `admins_ru` | не грузится | — | — |

**Порядок загрузки важен** — он задан связями, а не алфавитом:

1. `stations_ru` — карточки объектов; всё остальное резолвится через них.
2. `connectors_ru` — паспорт разъёмов (станции, которых нет, теряются молча — смотреть счётчик «станций не найдено» в отчёте прогона).
3. `organizations_ru` → `users_ru` — телефон организации витрина не отдаёт, он проставляется из клиента этой организации, поэтому клиенты идут после организаций.
4. `rfid_cards_ru`, `tariffs_ru`, справочники — в любом порядке.
5. `charge_sessions_ru`, затем `payments_ru` — платёж ссылается на сессию; обратный порядок не ломает загрузку (связь без FK), но до прихода сессий платежи будут числиться сиротами.

**Ритм.** Еженедельно — инкремент по сессиям и платежам (окна с перекрытием в сутки:
повторные строки дедуплицируются по id). Раз в месяц — полный прогон всех десяти
представлений: он ловит правки задним числом, которые инкремент по датам не видит
(отменённый платёж, переименованная станция, закрытый тариф).

**Почему полный прогон безопасен** (проверено тестами `tests/test_asuim_vitrina.py`):
пустая колонка выгрузки больше не стирает уже загруженное — ни у клиента, ни у карты,
ни у платежа, ни в паспорте станции. До 09.08.2026 это было не так: повторная загрузка
обнуляла телефон и баланс клиента, сбрасывала рабочий статус станции в «нет данных» и
снимала метку тестовой.

**Что проверять после каждого прогона** — по отчёту прогона и экрану «Данные» → «База
пространства»:

- строк принято против строк в файле (расхождение = потерянные станции или битые строки);
- «станций не найдено» у коннекторов — это разъёмы, не доехавшие ни до какой карточки;
- предупреждение «было N, стало M» у справочников и прайса — частичная выгрузка вместо полной;
- платежи без сессии за свежий период (норма — 0,1–0,5 % в месяц, больше означает отставание выгрузки сессий);
- новые карточки станций: заведённая заново станция вместо обновлённой означает, что у неё сменился `id_станции` в витрине.

**Чего в процедуре ещё нет.** Канал принимает **один файл за прогон**
(`config.uploadFileId`), поэтому десять представлений — это десять заходов руками.
Пакетная загрузка (архив или мультивыбор с автоопределением каждого файла по шапке)
не сделана; при ежемесячном ритме это первое, что стоит автоматизировать. Служебное
поле `_дата_выгрузки` не сохраняется ни в одной строке — по данным нельзя сказать, из
какой выгрузки они пришли; в `payments_ru` оно содержит 240 разных значений, то есть
инкремент на стороне заказчика уже работает, и это поле может стать отметкой свежести.
