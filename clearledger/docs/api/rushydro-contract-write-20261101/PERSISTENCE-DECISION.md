# Root: хранение и полномочия договорного цикла V2

Решение для следующей реализации P1. Проверено по Source
`b8b1c66cb5262a908cd9e1f0cc222e822e6c6ce9`: `models_partner.py`,
`models_partner_contracts.py`, `partner_identity.py`,
`partner_contract_authority.py`, `partner_contract_profiles.py`,
`models.py`, `doc_access.py` и revision0004.
Это утверждённые границы будущей реализации; миграция, модели и доступы
ниже ещё не реализованы и не включены.

## Существующая основа

Пять `PartnerResourceScope` и типизированные колонки `PartnerResourceItem`
не поддерживают Site. Canonical verifier пересчитывает эти пять наборов
при каждом запросе. Ни ресурс договора, ни receipt не являются
пользовательским назначением на площадку. Старый CREATE-profile имеет
свои закрытые списки ссылок и операцию `createContract`; его расширение
произвольными новыми полями нарушило бы действующий контракт.

Поэтому таблицы, DDL, hash-v1, DTO и namespace revision0004 сохраняются.
V2 использует тот же canonical issuer и общие владельцы карточек,
условий и документов. Новые сущности ниже хранят полномочия и историю
команд, а не вторые карточки договоров или документов.

## Site: три независимые границы

1. Добавить `site_authority_contexts`: точные `company_id`, `site_id`,
   `organization_id`, `approved=false`, `revoked=true`, положительная
   `policy_generation`. Уникальность `(company_id, site_id)` и отдельные
   tenant-safe FK на настоящую площадку и организацию. Нет автоматического
   определения организации из контракта, пользователя или land pointer.
2. Добавить `site_user_permissions`: контекст, текущий пользователь,
   точное действие и одобрение по умолчанию false. Уникальность
   `(company_id, site_id, user_id, action)`. Это явное native-назначение;
   роль admin/superadmin, автор документа и наличие связи не подменяют его.
   Запись относится к текущему членству пользователя в этой компании.
3. Расширить действующий типизированный ресурсный набор отдельным
   `kind=sites` и `site_id UUID`. Для Site допустимы только SET/EMPTY,
   по умолчанию EMPTY; ALL запрещён. Сохраняются one-id/typed-id checks.
   Проверяется пересечение installation Site SET и native-назначения.

Площадка остаётся `EzsSite`, а станция — `ServiceLocation` с точным String40.
Если площадка связана со станцией, дополнительно применяется текущий
ObjectId ceiling. Пустой ceiling не становится ALL. Собственная организация
участника и организации контекста/документа должны согласоваться.
Отсутствие любого обязательного одобрения означает отказ.

Следующий код должен задать закрытый словарь Site-действий по фактическим
потребителям: чтение; изменение связей; создание договора/документа в
контексте; чтение/правка/скачивание документа. Неизвестное действие — отказ,
а не эквивалент read. Словарь сверяется с native ACL перед фиксацией DDL.

Выбранные 19 записей TARGET не содержат создание Site. Birth policy не
должна разрешать создание площадок или выдавать права на существующие Site.

## Полномочия V2 и создание ресурса

Новые таблицы: `partner_contract_cycle_profiles`,
`partner_contract_cycle_principals`, `partner_contract_cycle_refs`,
`partner_contract_cycle_birth_policies`.

Профиль привязан к одной существующей installation/client/company;
`user_enabled=false`, `revoked=true`, generation > 0. Машинные principals
в текущем договорном цикле не принимаются. Principal — явно одобренный
пользователь с текущим членством, не произвольный actorId из запроса.
Refs — закрытый типизированный набор organization/counterparty/location/site
с одной колонкой идентификатора и проверкой компании. Наборы contracts и
documents продолжают принадлежать canonical resource grants.

Birth policy привязана к профилю, principal, организации, точному Site либо
location-контексту, операции и конечному перечню действий. Допустимые цели:
новая карточка договора и новый черновик DocCard. По умолчанию disabled;
не бывает wildcard-контекста, ALL-ресурса или разрешения на любой target kind.
Для V2 birth принимается только явный SET/EMPTY соответствующего ресурсного
вида; действующие v1 ALL-профили не переписываются и не расширяются.

После свежей авторизации и под общими блокировками первая успешная команда
атомарно создаёт ресурс, добавляет только его точный ID в разрешённый SET,
фиксирует предусмотренные policy действия и аудит, затем success receipt.
Переход EMPTY → SET разрешён только этим одобренным первым созданием.
Ни receipt, ни ссылка с площадкой/договором не заменяют независимые native
права на документ и файл.

Повтор команды сначала заново проверяет текущие полномочия и сохранённые
исходные refs. Он не выполняет birth заново, не восстанавливает отозванный ID
или действия, не добавляет существующие ресурсы и не расширяет SET.

## Квитанции команд

Новые `partner_contract_cycle_receipts` и
`partner_contract_cycle_receipt_refs` независимы от старых intents.
Namespace: `(company_id, app_id, installation_id, operation, command_key)`.
В receipt сохраняются исходные client, user, grant, cycle-profile,
operation/hash versions, request SHA-256, точная цель, ограниченный результат,
created_at и реальный root transaction id.

Операция выбирается из закрытого списка команд V2, не из произвольной строки
клиента. Birth разрешён только двум указанным операциям. Для команды с
precondition хеш включает original expectedVersion и семантику If-Match.
Денежные значения — фиксированные десятичные строки; ObjectId не
нормализуется. Set-поля сортируются только по явной схеме соответствующей
команды. commandKey не включается в payload hash; изменение остальных
значимых полей при том же namespace даёт конфликт после авторизации.

Результат — ограниченный JSON выбранной команды, до 128 KiB в UTF-8;
токенов, credentials, storage paths и подписанных download URLs в нём нет.
Лимит учитывает согласованный DocState до 200 версий: прежние 32 KiB
не гарантировали размещение такого допустимого результата. Файловые байты
в receipt не хранятся. Не хранить произвольный HTTP response или полный ORM snapshot.
Сохранённый результат неизменен; replayed вычисляется для ответа.

Refs имеют явный kind и ровно один типизированный идентификатор. Исходный
идентификатор и контекст неизменны; текущие nullable FK, если нужны для
удалённого ресурса, не переписывают историю и не дают полномочий.
Success и все refs вставляются в одной исходной транзакции; позднее
добавление/перестановка детей запрещено. UPDATE содержимого запрещён.
Прямой DELETE с возможностью повторного использования ключа запрещён;
удаление всего tenant требует отдельной согласованной политики хранения.
Срок годности не освобождает namespace. Неуспех не записывается как success.

При авторизованном совпадающем replay возвращается исходный результат до
проверки свежего semantic editVersion; текущее состояние не меняется.
Другой пользователь или grant не наследует чужую команду. Потерянный ACK
выясняется новым запросом с тем же ключом и текущей авторизацией.

## Изменения общих сущностей

- `Contract.validity_kind`: nullable unknown/openEnded/until. Старое NULL
  читается как unknown; миграция не угадывает бессрочность. Новое until
  требует календарную дату valid_until, не раньше даты договора.
- `OpsContractTerm.site_id`: отдельный UUID/FK. site требует site_id и
  запрещает location_id; не-site запрещает site_id. Исторические неизвестные
  scope без site_id сохраняются, readers их блокируют. Отдельная уникальная
  ось Site и окно не смешиваются с coalesce(location_id,''). Прежняя ось
  company/location сохраняет прежнюю уникальность для legacy-строк.
- `DocCard.site_id`: отдельный UUID/FK; при Site object_id отсутствует,
  tenant/context/organization согласованы. Native list/read/edit и общий
  file owner применяют один строгий Site predicate до limit/count/return.
  Для строк без site_id прежнее поведение сохраняется.

Нельзя включить Site-документы только в новую product query: общий
`doc_access` содержит отдельные admin/superadmin/list/file/edit пути.
Все они должны соблюдать Site predicate, включая ранние возвраты.
DocGrant, confidentiality, retention, approval и file/version ACL остаются
дополнительными независимыми условиями. `allow_null_object` не решает эту задачу.

## Порядок реализации и проверки

Сначала подготовить совместимые readers и общий term/close barrier, затем
заморозить revision с catalog contract/verifier и зарегистрированными моделями.
Новый ORM с дополнительными колонками нельзя запускать на старой схеме:
аддитивная миграция применяется до запуска такого бинарника, при выключенных
Site writers и отсутствии новых Site-строк. До разрешения записи должны быть
проверены все совместимые readers, native ACL и полный новый prefix.
Неизменность пакетов 0001–0004 проверяется по байтам и артефактным хешам.
Новые versioned-таблицы исключаются из legacy create_all; startup проверяет
полный применённый prefix. Ни create_all, ни reader не чинят схему.

Приёмка отдельно доказывает fresh/upgrade/repeat, отказ от drift/частичной
схемы, default-deny, tenant-safe FK, typed checks, immutable receipts/children,
atomic rollback/birth, current revoke/replay, native Site/file/list/edit ACL,
параллельные native/product команды и сохранение старого v1.
Модели/каталог/registry count сверяются с фактическим новым составом;
старые числа 341/347 не переносятся на новую схему автоматически.

Рабочие Site writes включаются только после проверки всех используемых
binaries и процедуры выпуска. Откат оставляет совместимые readers и данные,
отключает writers; небезопасного возврата старого fallback или удаления
истории нет. Выпуск и рабочие одобрения этим документом не поручены.
