## B: один полный proposed порядок, discovery и root capability

Порядок B: **typed admission keys → существующие location advisories при mutation → counterparty creation advisory → contract creation advisory → canonical authority rows → typed refs → exact intent/Contract/links/receipt → INSERT/flush/audit/DTO → commit**. Ни одна ветка B не может начать с row lock, а потом добавить более ранний key. Only read discovery перед keys не даёт authority.

Discovery выполняется под no_autoflush в clean root: JWT/current verifier preliminary → scalar IDs token/family/grant/client/app/company/install/actor/profile/current role. Body задаёт только валидированные command refs; не company/actor/grant. Preliminary identity session закрывается до independent quota. Domain root перечитывает discovery; **полный** набор typed keys строится до первого их acquisition. Если pointer/role/profile/owner-company изменился к lock point, transaction rollback и fresh same-intent retry с новым plan; не добирать недостающий ранний key, не использовать authority из старого verifier/Facts.

Proposed typed two-int xact advisory keys: отдельный ROOT-assigned namespace для каждого rank/type; key = signed32 SHA256 canonical payload prefix. Сортируется **реальный `(namespace,signed_key)`**, не только logical UUID/string, затем duplicates merged с заранее самым сильным режимом. Коллизия создаёт только ложное ожидание, никогда доступ; row predicates всё равно сравнивают exact tuple. Namespace значения пока не резервируются, ROOT сверяет весь manifest. Existing bigint location/reference/nonce namespaces не меняются. Никаких session-level locks, SHARED→EXCLUSIVE upgrade, savepoint acquire/release, ordering by случайный hash iteration. All lock states bound к тому же sync root/connection, как реальный LockedLocationSet; capability не bearer и не переносится в другую session.

FOR KEY SHARE не блокирует is_active/scopes/approved/non-key UPDATE и недостаточен.

После всех waits и row locks вызывается **SAME existing real verifier** на той же root session/connection; никаких копий JWT/live_grant правил. Snapshot IDs/actor discriminator сравниваются с полученными; current CREATE profile policy проверяет userEnabled/serviceEnabled, typed allowset, org/type/CP/location sets и current ceilings. User object ceiling включает более строгий product access intersection (membership.object_scope is not None); current live_grant truthy branch не превращает [] в ALL в новой domain policy. Service не читает/создаёт User membership. Expiry проверяется после waits и до mutation/commit boundary.

Linearization: окончательная fresh policy decision под удерживаемыми participating parent guards/authority row SHARE; durable effect на commit. Revoker, который успел commit до acquisition/revalidation, закрывает CREATE. Revoker, блокированный SHARE/parent guard, честно commit после CREATE. Старая identity session, снимок Facts и cached settings не становятся durable authority. Known failure rollback всей root; unknown commit acknowledgement разрешается fresh same-intent retry. Новый commit capability после промежуточного commit не наследуется автоматически.

## B: отрицательные interleavings и оставшиеся gaps

1. CA/install: current approve holds CA UPDATE135 → installation UPDATE on flush144; naive CREATE install SHARE→CA SHARE deadlocks. B Install writer EXCLUSIVE versus reader SHARED плюс canonical CA→install закрывает это пересечение, если approve участвует до CA INSERT/lock. Без участия FAIL, не solved.
2. Family/token: current refresh family UPDATE506 → old token UPDATE530; naive reader token SHARE→family SHARE deadlocks. B family→token в reader и parent keys до protocol locks; writer не получает earlier key после family. Revoke family-only не требует exclusive company.
3. CP/contract barrier: imported root CP→contract177–178 → CP writes; new reader refs SHARE→contract barrier reverse. B CP→contract до refs; mixed root не может прийти к barrier с prior CP/location write без K90 entrance. `_sync_contracts` helper сам не доказывает clean root.
4. User/member inversion: actual remove_user member DELETE+flush761–762 → User delete772. N User SHARE→member SHARE; D member DELETE→User DELETE могут ждать друг друга. Fix конкретного remove_user: User EXCLUSIVE key/parent lock до member flush. Account delete в другом user не сериализует N.
5. Role/member inversion: actual delete_role member assignments → delete role133. N Role SHARE→member SHARE, D UOW member UPDATE→role DELETE. Role EXCLUSIVE parent guard до чтения holder set и parent-first row lock нужен writer; одни SHARE readers не лечат inversion.
6. Absent profile/principal: row SELECT не нашёл child; admin INSERT child возможен. Install/Profile guard должен использоваться и read, и create/replace/delete child writer. Missing authority всё равно отказ, а не grant, но mixed snapshot receipt approvals без guard недопустим.
7. Whole-set installation replacement: approve DELETE scopes/items+INSERT; locking старых items не блокирует отсутствующий новый. Install EXCLUSIVE до replacement; CREATE Install SHARED до fresh scalar sets; profile guard аналогично.
8. Membership move RoleA→RoleB: discoverA, writer movesB, reader locksA и читает memberB. Reader revalidate pointer, rollback/replan; не использовать модулиA, не приобрести lower RoleB после member row. Writer должен объявить old+new role keys до Member EXCLUSIVE.
9. Cross-company global account revoke: User token_version update действует на одного user в обоих tenants. K30 User EXCLUSIVE конфликтует с их SHARED; disjoint user/tenant продолжаются. Никакой tenant-local lock без общего User row/parent guard этого не доказывает.
10. Cross-company App/client revoke: target App/client disable закрывает installations того же App/client в разных companies. Common per-App/per-client keys/rows обязательны, но независимому App/client не нужен общий F.
11. Raw store sequential duplicate: serialization без exact business duplicate check допускает второй legal-identity INSERT уже после N commit. Shared duplicate owner/legacy barrier required; advisory alone не бизнес-уникальность.
12. Receipt read count/list drift: два READ COMMITTED SQL без общего contract writer fence могут дать разные наборы. B использует count+page **в одном SQL statement snapshot**, не выдаёт их за transaction-stable snapshot и не берёт миллион row SHARE.
13. RR trap: если открыть REPEATABLE READ и первый SELECT advisory ждёт revoke, snapshot мог возникнуть **до** commit revoke. Нельзя объявить RR-after-locks solved: B admission revalidation READ COMMITTED; count+page single statement после revalidation. Никаких stale RR verifier claims.
14. Multi-company producer keys: A key(company1)→B key(company2) против обратного batch. Full sorted actual lockkeys plan до row writes либо reviewed per-company separate roots; второй company key после writes запрещён. Нет invented разрешения менять business transaction boundaries.
15. Service credential rotation: selected valid credential/family locked, current real verifier повторён; actual client+original grant actor stable. Credential set guard withdrawal после SHARE ждёт; новый credential из того же grant не расширяет profile/receipt.
16. Existing nonce/code/request locks: source OAuth request FOR UPDATE precedes nonce advisory. New parent guards должны быть раньше обоих; reader CREATE не берёт code/nonce lock, поэтому не нужно включать его во все эти protocol namespaces. Новая обратная acquire path должна получить отдельный test.

Эти schedules — prospective NOT RUN. Отсутствие полной классификации mixed roots, post-await mutation, implicit FK cascades и внешних writers означает **gate OPEN**. Не заменять gap общими фразами «row lock всё решает».

## Измеряемая граница выбора A/B

ROOT sole application/test/SQL/Node executor. Сейчас measured samples0, latency/throughput/RSS/lock-wait/query-plan UNKNOWN. До выбора ROOT фиксирует implementation-only exact source scope, author/test manifests и independent benchmark oracle; никакого invented deadline, пользовательского quota/cap/ретеншна. Прогоны только isolated synthetic Postgres с real OAuth issuance/verifier и actual row locks.

Сравнение: одинаковые distinct companies/users/clients и отдельные shared-user/shared-client cases; create vs revoke/approve, native/raw imports vs external CREATE, same-company business duplicate, multi-company batches. Измерить successful/denied outcomes, p50/p95/p99 admission/lock/commit wait, throughput/CPU/RSS/SQL count, blocked-by identity, retry/deadlock outcomes, transaction duration вокруг real existing import awaits. A должен показать cross-tenant blocking, B — отсутствие несвязанного admission wait при disjoint keys; существующие pool/budget/DB bottlenecks отделяются от locks. Нет утверждения «B всегда быстрее», пока measurements нет.

Нынешний `database.get_db` (5564–5572) делает commit после yield и rollback только `except Exception`. Новый write adapter обязан отдельно обрабатывать `BaseException`/`CancelledError` и закрывать/reap session; это не обещание переписать общий dependency. `expire_on_commit=False` и default autoflush означают, что простое повторное `get` недостаточно. Физический момент checkout/pool wait, SQLAlchemy UOW ordering и PostgreSQL query plans исходник не измеряет.
