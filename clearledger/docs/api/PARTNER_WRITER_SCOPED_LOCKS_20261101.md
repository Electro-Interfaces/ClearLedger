## Контракт плана, строк и seam

Clean MVCC/no_autoflush discovery фиксирует original parents/pointers, полные credential IDs, location/profile/item sets, selected resources и прежние отсутствия до единственного `LockPlan/acquire_scoped_locks`. Дрейф состава после parent wait требует whole-root rollback/409. Отсутствующая CA получает UUID/InstallationKey заранее; отличный actual ON CONFLICT winner откатывает весь root до lock другого CA/install.

**Обязательное условие: READ COMMITTED на каждом участвующем actual DB root.** `populate_existing` освежает identity map, но не snapshot PostgreSQL и не доказывает current-after-wait в REPEATABLE READ. Реальный get_db/PG target mode здесь **UNCONFIRMED**: ROOT должен подтвердить/обеспечить READ COMMITTED как отдельное environment/admission условие до исполнения. Runtime query/изменение engine/config не выполнялись.

Canonical rows: **Company → App → Client → Users → Role → Member → CA → Installation → Grant → Credential(s) → Family → Token**, затем Request/Code и заранее известные company-scoped reference rows. Mutations берут UPDATE, authorities SHARE, не KEY SHARE; predicates tenant/original pointer стоят в SQL до lock, populate_existing убирает stale identity map. Поля/строки, изменяемые этой операцией, не перезатираются checkpoint; остальная authority перечитывается. Указатели/absent parents проверяются до downstream rows; новые protocol identities не становятся поздним источником ключей.

`verify_locked_partner_access(db: Session, token: str, *, capability: ScopedLockCapability, expected: VerifiedPartnerToken) -> VerifiedPartnerToken` — **один thin seam**. Caller уже держит canonical rows на том же actual Session/Connection/root; cap доказывает issuance/lifetime/точное typed покрытие, **не row locks/ACL**. Seam вызывает только прежний `verify_access`, сравнивает original token/client/app/install/company/grant/user/kind/subject tuple, возвращает свежие scopes/resources. DTO не является portable write authority. После следующих waits caller повторяет seam с исходной cap, не строит второй plan.

Native after-wait: transient actual bearer → public `decode_token` → `native_user_from_claims`/`native_visit_from_claims` → `native_claims_context`/`require_core_user` → только прежний admin gate. Нет copy JWT/live policy, повторного get_current_user/presence commit или nested prepare_native/auth_write.
