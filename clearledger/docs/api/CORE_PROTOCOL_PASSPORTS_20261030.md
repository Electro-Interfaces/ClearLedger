## Admission: что именно прочитано в коде

Во всех обозначениях с пользовательским JWT `get_current_user` (`server/app/auth.py:214`) декодирует JWT, читает User, проверяет `session_valid` и отдельно ветку visit/scp. Это базовый HTTP admission, не доказательство предметных полномочий. `assert_company_member` (`auth.py:294`) разрешает UUID/slug, проверяет visit-company, членство или superadmin и выставляет object/organization scope; сам по себе он не доказывает, что последующий builder использует каждый scope. `assert_company_product` (`auth.py:441`) добавляет проверку продукта по роли. В `scope_company_id` (`deps.py:43`) заголовок выбранной компании проверяется через membership; fallback `user.company_id` возвращается непосредственно. Поэтому код SC ниже нельзя читать как независимую проверку всех станций.

## W: WebSocket чата и жизненный цикл авторизации

**Регистрация:** `main.py:641` подключает chat router под `/api`; `/chat/ws` → actual `WEBSOCKET /api/chat/ws`, `app.routers.chat_router.chat_ws`, order `[1471]`. Указанный в runtime `capture_company_header` не доказывает WS tenant admission: HTTP `Request` dependency и WS scope не проверялись запросом.

**Вход:** `chat_router.py:3245` `_ws_user` получает JWT из обязательного query `token`, проверяет decode (включая JWT exp), UUID sub, существование User, `session_valid` (`auth.py:110`: token_version и максимальная давность at). `get_current_user` здесь не вызывается; его visit/scp ветка не переносится автоматически на WS. До `manager.connect` отклонение закрывается кодом 1008. ASGI handshake refusal до accept нельзя выдавать за гарантированный close frame 1008 браузеру: прочитанная реализация Uvicorn 0.34.0 превращает этот close в HTTP 403; фактический stack/browser требует отдельной синтетической проверки.

**Accept и auto-subscribe:** `services/chat_ws.py:214` вызывает `ws.accept()`, сохраняет только user_id/company_id в meta, подписывает `user:{uid}` и, если есть, `company:{user.company_id}`; это default company пользователя на момент входа. Затем `chat_ws` шлёт `{type:connected,userId}` и presence. Нет source-подтверждённого выбора другой компании из WS query.

**Сообщения:** сервер читает JSON-кадры, обрабатывает ping/pong, subscribe/unsubscribe и typing. `_ws_can_subscribe` (`chat_router.py:3273`) разрешает собственный user-канал, компании из свежих `_member_ids` **или** сохранённого `user.company_id`, chat-каналы через `_assert_participant` (:186); superadmin пропускает не-chat каналы. `_assert_participant` проверяет active room, company (кроме direct), ticket/task policy, участника и scope продукта; superadmin bypass ограничен самим helper. Typing повторяет subscribe gate перед broadcast; обычный ping авторизацию не перепроверяет. Неизвестный тип не получает явной protocol error; общий exception завершает цикл без документированного error event.

**Доставка:** `_broadcast_local` (`services/chat_ws.py:313`) перед каждым send вызывает `ticket_communications.delivery_allowed` (:119). Для task-room `recipient_allowed` (:96) заново читает User, проверяет task access и участника; для ticket-room читает User, staff gate и историю reply/pinned/message. Для обычной комнаты `recipient_allowed` возвращает True; для не-chat событий `delivery_allowed` может вернуть True ещё раньше. Это важное ограничение: свежий предметный gate существует, но не служит универсальной проверкой JWT/token_version всех соединений. События между workers проходят PostgreSQL notification → `_deliver_notification` → тот же `_broadcast_local`; SQL здесь не исполнялся.

**Renew/revoke:** `POST /api/auth/refresh` (`auth_router.py:538`) выдаёт новый JWT с прежним at, для visit сохраняет прежние scp/cid/pvs/exp. WS не имеет сообщения auth-renew и не хранит JWT/exp в manager meta; refresh HTTP не заменяет токен открытого сокета. Смена пароля/logout-all повышает `User.token_version` в auth router, и следующий handshake старого JWT отвергается; в while-loop и обычной доставке повторной проверки token_version/exp нет. Свежие ticket/task gates частично ограничивают доставку, но не закрывают это различие контрактов. Здесь не утверждается, что отзыв закрывает уже accepted WS.

**Клиент:** `src/hooks/useChatWs.ts:14` строит query URL из актуального getToken при каждом connect; hook не обновляет credential в уже открытом WS. Он отправляет ping каждые 25 секунд, закрывает сокет после 70 секунд без кадров, ограничивает retries (до 5 с exponential backoff, stop на увиденном 1008), при reconnect вызывает callback для повторного чтения. Сервер не предоставляет replay cursor/sequence/ack; ws notification нельзя объявлять гарантированной доставкой. `/auditor/ws/terminal` встречается в frontend `AuditorTerminal.tsx:222`, но отсутствует в этом backend runtime registry: это **не второй зарегистрированный WS Ядра** и его gateway/upstream вне каталога.

**Query privacy, source-only:** `main.py:135–137` устанавливает `api_access_logging.install_oauth_access_filters`; `api_access_logging.py:8` распознаёт query `token=` независимо от OAuth path, `safe_target` убирает query из стандартных **HTTP** Uvicorn five-args/Gunicorn Mapping access records. Это не доказательство redaction именно WS accepted/rejected logger: локальная source-копия Uvicorn 0.34.0 использует `uvicorn.error` и другой tuple format; полная цепочка и границы приведены в P-02. Template другого репозитория `/srv/projects/ecosystem-deploy/stacks/_template/nginx.conf:61,102–104` задаёт `stack_noquery` для exact `/api/chat/ws`, `$uri` без args; его применение в конкретном ingress/образе не проверено. HEAD/хеш template в companion. Реальные журналы не читались, факт экспозиции токена в продуктиве не утверждается.

**Решение W:** сохранить WS как отдельный явно версионируемый event-протокол с JSON envelope, описанными типами/close/error semantics; admission вынести в общую проверку session + company + channel. Следующий конкретный пакет: определить срок accepted WS, revocation version и поведение при потере membership; хранить необходимый auth context, повторно проверять его перед subscribe/обычной доставкой либо закрывать по revocation signal. Для browser bootstrap выбрать короткий одноразовый WS ticket вместо долгого access JWT в URL, с company/channel binding и redaction всей цепочки. Этот ticket — предложение, в текущем коде его нет. До внедрения общего gate сохранить свежие task/ticket guards и перепроверку history; нельзя заменить их одним membership gate.

## C: консоль станции, catchall и upstream

**Владелец:** `station_console_router` — adapter рабочего места Магазина к TradeLink Hub, а не клиентский REST API всех данных станции. Session endpoint POST открывает 60-минутную console-cookie со sub/company/station/name/iat/exp/typ. Cookie `HttpOnly; Secure; SameSite=Lax`, path строго `/api/store/station/{station_id}/console`, max-age 3600. На каждом proxy request проверяется свежий UserCompany.business_grants и станционный grant; отзыв grant запрещает следующий запрос. Console-cookie не несёт token_version и не вызывает `session_valid`: logout-all/пароль пользователя и отзыв станционного grant — разные механизмы. User/account blocking semantics для cookie не заявлены.

**Dispatch:** пять зарегистрированных методов GET/POST/PUT/DELETE/HEAD обслуживают один `{path:path}`; PATCH/OPTIONS как endpoint здесь отсутствуют. До отправки path трижды unquote и проверяется на сегмент `..`, backslash, `//`, начальный slash, NUL. Настроенный HUB_URL фиксирует upstream base; station_id/path формируют `/api/v1/integration/stations/{station_id}/console/{path}`. Секрет X-Integration-Key берётся сервером, пользовательские Authorization/Cookie в upstream не копируются; outgoing передаёт server integration key, user ID, percent-encoded name и только station grants плюс входящие Content-Type/Accept. Все query multi_items сохраняют повторяющиеся ключи; body целиком в памяти.

**Status и error:** HTTPX request использует timeout 130 секунд, `follow_redirects=False`, не вызывает raise_for_status. Поэтому upstream 3xx/4xx/5xx остаётся тем же status, а не нормализуется в 200 или Problem Details. Transport HTTPError превращается в local 504 c текстом исключения; отсутствие HUB_KEY → 503, path → 400, cookie → 401, grant → 403. Для отсутствующей cookie Accept с `text/html` получает HTML 401 с восстановлением session через Bearer HTTP POST; остальные получают JSON detail. Upstream body любого error status проходит тот же HTML/bytes dispatch.

**Headers/redirect/HTML:** исключаются ровно content-encoding/content-length/transfer-encoding/connection, остальное строится из `headers.items()`. Это не полная hop-by-hop/Connection-nominated фильтрация, а multivalue headers вроде Set-Cookie не гарантированы такой структурой. У root-relative Location снимается внутренний hub prefix и добавляется Ledger prefix; абсолютный и network-path Location не становятся автоматически safe redirect (network-path `//...` сейчас попадает в startswith('/') ветку). HTML переписывает только перечисленные двойные атрибуты href/action/src/data-открыть, `fetch("/` и JS location assignment; это не универсальный HTML/JS rewriter. External/relative/custom JS/CSS/ws URLs остаются отдельной совместимостью upstream.

После HTTPX чтения `.text` HTML перекодируется Response, однако upstream Content-Type сохранён; согласованность charset/ETag/Content-MD5 после изменения тела не обеспечивается явно. Non-HTML берётся из `.content`; range/conditional request headers не передаются, streaming не передаётся, upstream compression уже декодирована. На любом успешном достижении ответа, включая upstream 4xx/5xx, cookie продлевается ещё на час после grant check. Это idle renewal, не абсолютный lifetime и не JWT refresh пользователя.

**SSE/WS:** если upstream динамически ответит `text/event-stream`, строка Content-Type может сохраниться, но ответ будет буферизован до завершения/timeout. Это не рабочий streaming bridge. Upgrade WebSocket для console catchall не зарегистрирован; HTTPX request не даёт WS tunnel. Глобальная гарантия отсутствия динамического SSE отсюда не следует.

**Соседний JSON endpoint** `GET /api/store/station/{station_id}/state` (`station_console_router.station_state:357`) — отдельный integration client: `get_current_user` + scope_company_id, без такого же station-admin gate; проверяет hub 200 и возвращает online/reason/url либо online:false. Это не проксирование upstream статуса/тела. Не расширять его смысл до разрешения открыть console.

**Решение C:** сохранить console под отдельным adapter contract; не выдавать его catchall за универсальную product REST surface. Следующий пакет должен либо явно запретить streaming/upgrades и документировать буферные ограничения, либо реализовать отдельный streaming adapter с cancellation/backpressure, безопасным перечнем response headers и route policy для upstream. Зафиксировать allowed redirects, charset/валидаторы после HTML rewriting, request/body limits и absolute cookie lifetime/revocation связь; сохранить повторяющиеся query и станционные grants. При будущем переносе нельзя «исправить» upstream статусы в 200/JSON.

**Membership ≠ resource policy.** `/api/files/{file_id}` действительно исполняет несколько независимых guards, но helper каждого домена возвращает «не относится ко мне» при отсутствии связей. Внутри одного домена может быть разрешение через любую допустимую связь; между доменами общий endpoint не объединяет все gates в один OR. Прямые domain file endpoints обходят `/files` и потому имеют собственные chains из таблицы. Product content намеренно отвергает cross-domain SourceFile, обнаруженный через ChatMessage/ConfSession/StoreDocFile/TaskAttachment, до выдачи байтов (`product_api/files.py:55–65`); не убирать этот fail-closed запрет до извлечения общей политики.

**Product file chain:** Query.detail устанавливает доступ к документу, DocVersion требует doc_id/company/tombstone/archive_purged, SourceFile требует company; затем download policy. `_open_beneath` (:16) открывает от upload root через dir_fd с O_NOFOLLOW, проверяет regular file; генератор читает по 65536, finally/background закрывают handle. Это конечный файл, не SSE; серверная JSON/schema media metadata не заменяет реального MIME. У legacy `/files` Path.exists + FileResponse иной механизм, его равенство confined open не заявляется.

**Снимки и хранение:** doc-share ограничивает версии snapshot и archive_purged, сверяет документ с link.doc_id, читает текущий SourceFile. Наличие разрешённой ссылки не доказывает равенство bytes на диске immutable snapshot и не покрывает все retention/tombstone правила product download; это конкретный долг выравнивания политик. Calendar feed не имеет read-time exp в функции; при стандартизации нужно явно решить rotation/expiry. Публичная capability-ссылка передаётся как секрет, без печати её реального значения в документации.

ZIP архива имеет ограничения 2000 rows / 1.5GB declared size и маркеры отсутствующих файлов, но compressed archive целиком BytesIO. `Content-Disposition` общий helper даёт ASCII fallback и UTF-8 filename*; другие места отличаются и требуют отдельной совместимости.
