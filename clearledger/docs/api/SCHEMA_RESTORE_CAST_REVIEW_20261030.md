# Независимая source-only проверка cast diff, 30.10.2026

Все 50 наблюдаемых пар согласуются с одним узким правилом: приведение
непустого одномерного массива varchar-литералов к text[] распределяется по
его элементам. Дополнительного изменения операторов, литералов, идентификаторов,
коллаций или внешних условий в этих парах не найдено. Это условный семантический
вывод по закреплённым представлениям каталога, не full restore acceptance и не
проверка реализации canonicalizer.

Для всех изменённых SQL отдельно выделены токены строк, слов, `::`, операторов
и пунктуации с исходными позициями. Закрытая грамматика принимает только:

```text
L := обычный single-quoted строковый литерал
S := ARRAY[L::character varying, ...]::text[]
T := ARRAY[L::character varying::text, ...]
SI := (ARRAY[L::character varying, ...])::text[]
TI := ARRAY[(L::character varying)::text, ...]
```

Каждый S/T либо SI/TI заменён в памяти одним структурным маркером с точной
последовательностью исходных L. После замены весь оставшийся SQL совпал
**побайтно во всех 50 парах**, включая пробелы, скобки, порядок условий и
создание индексов. Это проверка наблюдаемых форм, не общий SQL parser;
ожидаемые пары имён или SQL не использовались как lookup для принятия.

Контексты CHECK: 38 простых условий; 1 AND двух сравнений; 2 формы

Эти typmods колонок не удаляются и не переносятся в literal casts.

## Почему правило применимо и где кончается доказательство

PG16 [§4.2.12](https://www.postgresql.org/docs/16/sql-expressions.html#SQL-SYNTAX-ARRAY-CONSTRUCTORS)
описывает приведение конструктора массива как приведение каждого выражения
к типу элемента. Здесь все элементы уже явно varchar, результирующий тип
обеих форм — text[], размерность и порядок одинаковы; спорной унификации
смешанных типов нет. [§10.3](https://www.postgresql.org/docs/16/typeconv-func.html)
указывает binary compatibility varchar/text. Это основание считать перенос
именно этого cast изменением представления при подтверждённых built-in типах.

Из равенства типизированного массива и неизменности внешних операторов следует
одинаковый результат всех 49 `= ANY` и 4 `<> ALL`, затем неизменных AND/OR/NULL
guards. Это покрывает весь наблюдаемый контекст, включая ограничения и
membership частичных уникальных индексов. Нельзя заменять UNKNOWN на FALSE:
[§9.24](https://www.postgresql.org/docs/16/functions-comparisons.html)
сохраняет трёхзначную логику; CHECK допускает TRUE и UNKNOWN
([§5.4.1](https://www.postgresql.org/docs/16/ddl-constraints.html#DDL-CONSTRAINTS-CHECK-CONSTRAINTS)),
а [частичный индекс](https://www.postgresql.org/docs/16/indexes-partial.html)
выбирает строки, удовлетворяющие предикату. Эквивалентность результатов
предиката здесь логический вывод, не измерение на сервере.

Каталоги не содержат pg_type/pg_cast/pg_operator и определений collations;
одинаковое имя `default` не доказывает равенство свойств разных БД.
[pg_cast](https://www.postgresql.org/docs/16/catalog-pg-cast.html)
различает binary (`b`), function и I/O casts, а также typmod coercion.
До последующего разрешённого root-run нужно подтвердить разрешение имён в
pg_catalog, действительные OID и binary varchar→text cast, функции/контексты,
строгость и разрешение text-операторов, effective collation и настройки
литералов. Source-only вывод не заменяет эти доказательства.

## Допустимая граница будущего test-level canonicalizer

Нужен token/AST разбор с полным потреблением распознанного span, без regex
замены по всему SQL, удаления всех скобок или упрощения Boolean-выражений.
Разрешены только S↔T и SI↔TI выше, в проверенном deparser-контексте, с точными
L и типами; вне span всё сохраняется. Флаги metadata сравниваются отдельно.
Скобки удаляются только вокруг точно распознанного операнда cast.
Неизвестный тип, qualifier, typmod, collation, иной cast, комментарий,
выражение вместо L, незавершённый токен, другая размерность требуют
unchanged/refused, без попытки угадать смысл. Неподдержанный SQL не должен
получать общий маркер, способный уравнять разные входы.

Полученное текстовое предложение координатора использует четыре формы выше,
но расширяет L до plain literal либо **точного NULL**, и хранит результат как
типизированные части: raw outer SQL плюс tagged tuple с ordered raw L.
Такая граница обоснована: tagged tuple нельзя спутать с текстом SQL. Наш
локальный строковый маркер служил лишь измерению известных spans, не образцом
реализации. NULL расширение математически совместимо с этим cast, если
сохраняются NULL-элемент и его позиция; принятие/удаление NULL как общего
«пустого значения» недопустимо. В наблюдаемом входе NULL-элементов нет,
поэтому это расширение требует отдельных controls и пока не проверено.
То же относится к doubled-quote literals. Quoted identifiers должны оставаться
непрозрачными токенами; comments, E/U&/dollar forms и adjacent string
concatenation требуют отказа. Для backslash нужен подтверждённый
`standard_conforming_strings=on` либо отказ; lowercasing всего SQL недопустим.
Текстовое предложение не является immutable source snapshot реализации.

Негативные контроли для будущей реализации: во всех строках ниже различие
должно остаться либо вход должен быть отвергнут. Это спецификация pure
testcases и семантические контрпримеры; готовая реализация на них не запускалась.

| Изменение синтетического примера | Что запрещено терять |
|---|---|
| `'Ab C'` → `'ab c'` или `'a  b'` → `'a b'` | case и пробелы внутри L |
| `'a,b]'` → `'a,b'`; `'it''s'` → `'its'`; `E'a\\nb'` → `'a\\nb'` | границы/escaping строки; неподдержанные формы отказаться |
| `ARRAY['a'::character varying,'b'::character varying]` → обратный порядок | порядок/число элементов, даже если конкретный ANY даёт тот же ответ |
| `'ab'::character varying(1)` → `'ab'::character varying(2)`; `character(2)` → `character varying` | typmod: `a` против `ab`; семантика trailing spaces |
| `::text[]` → `::app.text[]`; `::character varying` → `::app.varchar` | type qualifiers, domains и разрешение типов |
| добавление `COLLATE "C"` или замена на другую collation | правила сравнения |
| `NULL::character varying` → `'NULL'::character varying`; удаление NULL-элемента | NULL и трёхзначная логика |
| `ARRAY[]::text[]` → `NULL::text[]`; одномерный → вложенный массив | empty/NULL, размерность и границы |
| `= ANY` → `<> ALL`; `AND` → `OR`; удаление `IS NULL` | оператор и Boolean-логика |
| `(p OR q) AND r` → `p OR (q AND r)`; `"Status"` → `status` | внешние скобки и quoted identifiers |
| `f()::character varying` вместо L; изменение UNIQUE, ключей или флагов | функция/побочные эффекты и весь внешний DDL/metadata |

## Что должен доказать последующий root-run

1. Закрепить candidate commit и hashes: lexer не меняет L, quoted identifiers,
   whitespace внутри строк и неизвестные spans; каждый ожидаемый отказ
   сохраняет неравенство. Проверить все 50 полных пар и неизменность остальных
   категорий, без allowlist по именам объектов. Frozen Foundation verifier
   остаётся неизменным.
2. В разрешённой отдельной PG16 среде подтвердить фактические pg_cast/type/
   operator/collation условия выше: ожидаемые built-in OID 1043→25,
   castmethod `b`, castcontext `i`, castfunc 0 должны быть получены из той
   среды, а не приняты на веру. Отдельная строка cast для массивов может
   отсутствовать из-за generic rules; отсутствие не доказывает отказа cast.
   Сравнить тип, размеры, границы и элементы
   обеих форм, затем результаты предикатов через NULL-aware equality.
3. Проверить x из множества {совпадающее значение, несовпадающее, NULL}, обе

   проверить typed NULL element, NULL array, empty array как negative boundary
   controls: при отсутствии совпадения NULL-элемент даёт UNKNOWN; empty ANY

   эти формы отвергает, она не должна сводить их к обычному массиву.
4. Отдельно подтвердить принятие/отказ CHECK и membership/уникальность
   частичных индексов, затем выполнить полную restore acceptance по принятому
