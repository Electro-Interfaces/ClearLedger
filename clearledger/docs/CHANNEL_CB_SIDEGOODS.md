# Канал ЦБ → сопутка/общепит → L2 (детальная проработка)

> Версия: 13.06.2026. Термины — `GLOSSARY.md`; источники — `docs/SOURCES_GIG.md`.
> Заземление: `.epf TL_ЭкспортБП_Сервер.bsl` (контракт v2), `clearledger/server/app`.

Конкретная реализация для ГИГ: **источник ЦБ → канал сопутки/общепита → разрез → размещение в L2 CLEAN**.

---

## 1. Источник — `onec_operational` [конфигурация ЭЛСИ.АЗК]

- **Подключение (pull):** `OneCComClient` → 32-бит `com_worker.py` (V83.COMConnector), на COM-Agent (1c-dev-01). connection_string: `Srvr="SQL1";Ref="azs_centre";Usr="Elsy";Pwd=…`. Read-only.
- **Опорный документ смены:** `Документ.ОтчётОРозничныхПродажах` (ОРП) — подтверждено probe (ОтчетСмены пуст, реальные продажи в ОРП). Один пакет = **одна смена одной АЗС**.
- **doc_types (прицепляются к смене по `Склад`=ОРП.Склад + дата ∈ [Открытие..Закрытие]):**
  `retail_sale_sidegoods` (сам ОРП) · `purchase` (ПТУ) · `production_release` (ВыпускПродукции) · `recipe` (ТТК, справочный) · `return_purchase` · (+ `transfer`/`writeoff`/`inventory` при необходимости).
- **Извлечение:** переиспускаем проверенную логику `.epf` (`ВыбратьСмены(период,Склад)` → `СформироватьПакет(смена)`), портируя запросы в Python-COM `com_worker`. **TODO:** порт extraction (env: живой ЦБ через COM-Agent).

## 2. Канал — `sidegoods` / `food`

- **Гранулярность:** пакет = смена. **Идемпотентность:** натуральный ключ `ОСЭ_Номер` (или `НомерСмены`).
- **Стадии:**
  - `fetch` — pull смен за период (пакет: смена + прицепленные kind) → L1 RAW (RawBatch + `DataEntry layer='raw'` сырой пакет).
  - `normalize` — пакет → канонические записи L2 (см. §3). Для общепита — разворот блюд по `recipe`(ТТК) на ингредиенты (модель B).
  - `reconcile` — разрез (контроль, опц., §4).
  - `save` — L2 CLEAN.

## 3. Нормализация → L2 = `DataEntry` (документная грана)

Решение 13.06: сопутка/общепит в L2 = `DataEntry` (без миграции, переиспускает intake/сверку). Реализовано: **`app/services/cb_normalize.py` · `normalize_shift_package(пакет)`** (чистый Python, само-тест ✓).

На каждый документ пакета (кроме `recipe`) — черновик `DataEntry`:

| Поле DataEntry | Значение |
|---|---|
| `category_id` | `retail` (ОРП) · `purchase` (ПТУ/возврат) · `food` (выпуск) |
| `subcategory_id`/`doc_type_id` | kind |
| `source` / `source_label` | `oneC` / «ЦБ ЭЛСИ.АЗК» |
| `source_id` | `{ОСЭ_Номер}:{kind}:{ИсточникUUID}` — натуральный ключ (идемпотентность) |
| `layer` / `status` | `clean` / `verified` |
| `meta` (JSONB) | `{Смена{…}, kind, СодержитБлюда, Документ{Товары[],Оплаты[],…}}` |

**Разворот блюд (модель B):** строки `retail_sale_sidegoods` с `ЭтоБлюдо`/`КлассSKU=Общепит` → в `meta.Документ.Товары[].Ингредиенты` дописываются ингредиенты `брутто-на-порцию × количество` из `recipe`(ТТК). `recipe` своего DataEntry не порождает (справочный поток).

**НДС-модель розницы (из контракта):** `Сумма` строки — **с НДС** (как пробил кассир); приёмник БП строит `Кт 90.01.1=Сумма / Кт 68.02=НДС 22/122 / Σ Дт 62.Р=СуммаДок` (`project_orp_retail_vat_model`). Нормализация суммы НЕ трогает.

## 4. Разрез (контроль L2, опционально)

Для ЦБ-канала опорный = сам ЦБ, поэтому основная работа — **нормализация**, а разрезы — контрольные:
- `marking_sidegoods` — маркируемые ↔ Честный Знак (`gtin/datamatrix`).
- `receipts_ofd` — Σ ОРП ↔ фискальные чеки ОФД.
Исполняет `ReconcileEngine` (`/reconcile/run`); статус planned до подключения источников ЧЗ/ОФД.
