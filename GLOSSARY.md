## 0. Корневой термин

### TradeLedger
**Продукт.** Слой подготовки данных к учёту (pre-accounting / reconciliation layer) между разнородной операционной реальностью компании и её 1С. **НЕ** замена 1С, **НЕ** ERP, **НЕ** вторая бухгалтерия. Делает стадии, которых в 1С структурно нет: сбор гетерогенного входа, сверку и поиск расхождений до попадания факта в учёт, управленческо-налоговую песочницу периода. Граница: **мы отвечаем за чистоту ФАКТОВ до 1С; 1С отвечает за ПРОВОДКИ** (§1, §8.4).

Когда заходим к новой компании — **разворачиваем TradeLedger под её профиль**. Это не «трёхуровневая система вообще», а именно настроенный экземпляр TradeLedger. Бухгалтер видит **TradeLedger** и понимает, что/откуда/как берётся.

```
TradeLedger
  └─ конфигурация под компанию (= Профиль/Модуль отрасли)
       ├─ Источники      — что подключаем
       ├─ Каналы         — как собираем первичку → L1
       └─ Разрезы сверки — как сводим L1 → L2 (через Движок сверки)
   данные текут по слоям: L1 RAW → L2 CLEAN → L3 EXPORT → L4 1C_REF (эталон)
```

> ⚠ **Кубики ≠ слои — не путать:**
> - **Кубики конструктора** (что собираем, ТРИ): Источник · Канал · Разрез сверки.
> - **Слои данных** (куда течёт, ЧЕТЫРЕ): L1 RAW · L2 CLEAN · L3 EXPORT · L4 1C_REF.
> Это РАЗНЫЕ оси. Кубики производят данные; слои — состояния данных.

> 📛 **Имя продукта = TradeLedger** (решение 13.06.2026). `ClearLedger` — **устаревшее имя кодовой базы** (React+FastAPI, рабочее место менеджера), подлежит переименованию `clearledger/ → tradeledger/` (отдельная миграция, затрагивает деплой `ledger.dataworker.ru/ClearLedger/`). До миграции `ClearLedger` в путях/коде = синоним TradeLedger, не отдельный продукт.

### Профиль / Модуль отрасли — `ModuleManifest`
🟡 Конфигурация-«коробка» под вид бизнеса (ГСМ, трейд, общепит, e-commerce). Декларирует **данными** (не кодом): типы источников, шаблоны каналов, разрезы сверки, нормализацию, отраслевые нормы (НДС/счета), шаблоны ключей идемпотентности (§3.4). Тест платформы: «новый бизнес = новый манифест, ноль правок ядра» — сегодня **не пройден** (§3.5, §13 риск 1). На сегодня реально один профиль — ГСМ (ГИГ).

## 1. Входной слой (Стадия 1 — СБОР → L1)

### Тип источника — `source_type` / `SourceAdapter`
✅ *Класс* внешней системы и его код-драйвер: `sts`, `ofd_*`, `acquiring_sber`, `onec_odata`, `onec_com`. Реализуется классом `SourceAdapter` (`server/app/adapters/base.py`), регистрируется `@register_adapter("sts")`. Декларирует `setup_schema` (поля формы подключения) + `available_doc_types`. Реестр адаптеров отдаётся `source_types_router`. Сейчас зарегистрирован один — `STSAdapter` (`fetch_delta` работает, `parse()` возвращает `[]`).

### Источник — `Source`
🟡 = **ПОДКЛЮЧЕНИЕ.** Настроенный экземпляр конкретной системы («STS ГИГ (65)», «1С Бухгалтерия ГИГ»). Хранит `connection_config` (не-секреты: URL, login, system_ids). Отвечает на вопрос **«куда и чем подключаемся»**. Модель `Source` (`models.py:1224`) есть, CRUD-роутера нет.

### Учётные данные источника — `SourceCredentials`
🟡 Секреты (пароли/токены) отдельной таблицей, шифрование Fernet (`models.py:1270`). Вынесены из `Source`, чтобы дамп-эндпоинты не вернули секреты и можно было ротировать ключ.

### Способ обмена (паттерн интеграции)
*КАК* технически общаемся с источником. Их несколько — **не одно слово**:

| Паттерн | Что происходит | Порождает L1? | Пример |
|---|---|---|---|
| **Выгрузка** (pull / `fetch_delta`) | периодически тянем датасет за окно | ✅ | STS сменные отчёты, ОФД чеки |
| **Проверка** (verify / lookup) | точечный запрос «подтверди факт», данные не грузим | ❌ (на лету при сверке) | Сбер-эквайринг через API |
| **Приём** (push / webhook) | источник сам шлёт событие | ✅ | банк-вебхук, входящая почта/чат |
| **Ручная загрузка** (upload) | человек кладёт документ/чат → OCR/AI | ✅ | загрузка накладной на обработку |

### Тип документа источника — `SourceDocType`
✅ Что источник умеет отдавать: `shift_report`, `receipt`, `transactions`, `ttn` (`base.py:43`).

### Поток — `ChannelStream`
🟡 = **ЧТО ТЯНЕМ.** Труба «источник × тип документа × **роль**» + фильтры (`models.py:1354`). Отвечает на вопрос **«что именно из подключения забираем и зачем»**.

### Роль потока
В каком качестве данные участвуют (§6.2 `streams: [anchor, external, control]`):

| Роль | Смысл | Пример |
|---|---|---|
| **Опорный** (anchor) | становится первичным документом в 1С | STS смена → ОРП |
| **Контрольный** (control) | для сверки против опорного | ОФД (Σ чеков), эквайринг |
| **Внешний** (external) | независимый поток для триангуляции | MSTO, корп-карты |
| **Эталон** | срез закрытого периода из 1С клиента | `ReferenceSnapshot` |

### Канал — `Channel`
🟡 = **КАК ОБРАБАТЫВАЕМ.** Конвейер-обработчик: берёт 1+ потоков из 1+ источников → прогоняет через стадии → кладёт результат в слои. Единица оркестрации. Несёт расписание (`schedule`: manual/interval/cron), политику дублей (`duplicate_policy`: skip/warn/overwrite), период (`period_days`), статус. Модель `Channel` (`models.py:1299`) есть, CRUD-роутера и рантайм-оркестратора (`ChannelSyncEngine`) — нет.

> **Канал ≠ зонтик для всего.** Канал появляется там, где есть **обработка/сведение нескольких потоков**, а не на каждое подключение. Не путать с 1С-«обработкой» (DataProcessor).

### Стадия канала — `ChannelStage`
🟡 Этап конвейера: `fetch` → `normalize` → `reconcile` → `validate` → `transform` → `save` (`models.py:1381`, `order_index`).

### Сырой батч — `RawBatch` / `RawBatchRecord`
🟡 То, что вернул `fetch_delta` (immutable, для дебага/переигрывания) → слой **L1 RAW**. DTO `RawBatch` (`base.py:67`) + таблица `RawBatchRecord` (`models.py:1521`).

### Нормализованная запись — `NormalizedRecord`
🟡 Результат `parse()` — унифицированная запись под целевую сущность (`fuel_shift`…) → слой **L2** (`base.py:86`). `parse()` пока пуст у всех адаптеров.

## 2. Сверка и нормализация (Стадия 2 — L1 → L2)

Отдельный процесс между «сырьём» и «нормой». Сырьё в L1 может быть с ошибками → требует проверки. После сверки (авто/полуавто) и разрешения человеком запись считается **сверенной** и попадает в L2.

```
L1 RAW → ① СВЕРКА → ② КЛАССИФИКАЦИЯ РАСХОЖДЕНИЙ → ③ РАЗРЕШЕНИЕ (человек) → ④ НОРМАЛИЗАЦИЯ → L2
```

### Движок сверки — `ReconcileEngine`
🟡 = **МЕХАНИЗМ.** Один, не подключается. Знает только КАК: загрузить потоки → разбить на корзины → сопоставить (fuzzy/точно) → сравнить поля с допусками → классифицировать тяжесть → записать lineage. Не знает доменных литералов. **Сегодня единого движка НЕТ** — три разных движка с разными топологиями gate: сверка с 1С doc↔entry по ИНН (`reconciliation_router` ✅ работает), топливная corp (station+fuel+time), MSTO (§6.4). Сведение в один — это **переписывание**, не расширение; часть замороженного обобщения ядра (§12.4).

### Разрез сверки — `ReconRule` / ось сверки
🟡 = **ПОДКЛЮЧАЕМЫЙ КОМПОНЕНТ** («кубик конструктора сверки»). Один разрез = одна сверка («корп-карты по станции+топливу с допуском 0.01 л против смены»). Декларативный, не код. Набор разрезов на компанию = **матрица сверки** (для топлива — 7 строк, §6.3). В манифесте — секция `reconcileAxes`.

> ⚠ Текущая модель `ReconcileRule` (`models.py:1413`) **плоская** (`match_field` + `compare_fields` + один `tolerance`) и **не выражает** предикат/severity/топологию — подлежит замене схемой (§6.4). Привязана к `channel_id`; цель — к профилю.

**6 настраиваемых кубиков разреза** (§6.2):

| Кубик | Задаёт | Пример (корп-топливо) |
|---|---|---|
| Потоки + роли | какие данные и кто опорный | `[смена=control, корп=external, TF=anchor]` |
| Предикат канала (`filter`) | «мой ли поток» (вместо хардкода `'кр'`) | `pay_channel in [corp]` |
| Ключ разбиения (`key`) | по каким полям бить на корзины | `[station, fuel]` |
| Стратегия сопоставления (`match`) | точно по ключу / fuzzy по времени+весам | `time_tol 90с; веса card·50/amount·30/vol·20` |
| Сравнение (`compare`) | поля + допуски | `volume ±0.01 л` |
| Классификатор (`severity`) | пороги + критичные поля + повышение в закрытом периоде | `none·0.005/rounding·0.05/minor·1/material·100; critical:[inn]` |

### Расхождение — `Discrepancy`
✅ Несоответствие, найденное сверкой. Тяжесть (`discrepancy_status`, `models.py:416`): `none` / `rounding` / `minor` / `material` / `critical` / `unmatched`. Статус сматчивания (`match_status`, `AccountingDoc`): `matched` / `unmatched` / `pending` / `discrepancy`.

### Разрешение — `Resolution` (человек-в-петле)
✅ Принять / отклонить / сматчить вручную (`reconciliation_router /match`), события в `audit_events`. **ИИ никогда не переводит факт в `verified`** (§7.4).

### Закрепление маппинга — `ReconcileMapping`
✅ Закреплённое соответствие (код источника → НСИ / станция → склад). После закрепления становится детерминированным правилом (`models.py:654`).

### Запрос на уточнение — `ClarificationRequest`
❌ **НЕ реализовано (новая сущность).** Тред «уточни/исправь этот факт», навешенный на расхождение; участники — люди/компании (аутсорсер ↔ клиент). FSM: `открыт → отвечен → принято/отклонено → закрыт`. Ближайшее в коде — ИИ-агент A4 «Разрешатель аномалий» (объясняет причину, §7.2) + человек-в-петле, но коммуникационного треда между сторонами нет.

## 3. Периоды и эталон

### Период — `Period`
✅ `status` = `open` (рабочая зона, правки можно) | `closed` (эталон, read-only, `is_locked` каскадом). Закрытие происходит **вне TradeLedger** (в БП: УстановкаДатЗапрета); TradeLedger детектит при репликации (`closure_source='from_bp'`, `bp_closure_ref`). Модель `models.py:1042`.

### Эталон — `ReferenceSnapshot` (= слой **L4 1C_REF**)
✅ Снимок закрытого периода из 1С клиента (checksum + список Ref_Key документов) — **якорь доверия**: клиент верит не нам, а своей же 1С (`models.py:1088`, §5.3). Это **слой L4** (что реально лежит в БП). Риск-якорь: хранит summary+refs, не строки — обогащать построчно при закрытии (§5.3).

### Двойная роль 1С (важно!)
**Одна и та же 1С играет две роли в зависимости от системы И состояния периода:**

| Система · период | Роль | Что делаем |
|---|---|---|
| **1С Бухгалтерия (БП), ЗАКРЫТЫЙ** | **Эталон** + **приёмник** | читаем `ReferenceSnapshot` для сверки; пишем L3→1С через .cfe |
| **1С УТ / операционная, ОТКРЫТЫЙ** | **Источник первички** | обычный `Source`, кормит L1 для текущей работы |

⟹ **роль источника = система + состояние периода.** Репликация из 1С: `sync_catalogs` (НСИ), `sync_documents` (закрытые периоды), `sync_policy` (`OneCPolicy`), `period_closure` (детект) — эндпоинты `onec_router` ✅.

### Межпериодная корректировка — `AdvisoryCorrection` / `AdvisoryEntry`
❌ **НЕ реализовано** (§5.1, §8.3). Правка закрытого периода запрещена → уточнение уходит в advisory-реестр в открытый период (reason + НПА + персональный approve). FSM: `proposed → approved → (ExportPacket kind='correction') → applied`.

## 4. Слои данных и выход (Стадия 4 — L2 → L3 → 1С → L4)

### Слои (4 слоя — канон по `docs/sverka-spec.md`)
Сверки идут **попарно между слоями** (L1↔L2 нормализация, L2↔L4 против эталона, L3↔L4 приёмка в 1С).

- **L1 RAW** 🟡 — сырьё из источника как пришло, append-only (`RawBatchRecord`; `DataEntry.layer='raw'`, `status=new|recognized`). Не редактируется.
- **L2 CLEAN** 🟡 — нормализовано и сверено, готово к выгрузке (`DataEntry.layer='clean'`, `status=verified`; `FuelShift` агрегаты + `raw_entry_id`→L1). *Синонимы: Normalized / ХАБ.* Главный артефакт; аналитика (Стадия 3) — поверх него.
- **L3 EXPORT** ✅ — что **отправляем** в 1С (`ExportPacket`). *Синоним: Prepared.* L3 ≠ L2: то, что реально ушло в пакете.
- **L4 1C_REF** ✅ — **эталон**: что **реально лежит** в БП после проведения (срез закрытого периода, `ReferenceSnapshot`). Якорь доверия. Сверка L3↔L4 ловит, приняла ли 1С наш пакет корректно.

### Конверт выгрузки — `ExportPacket`
✅ L3-пакет под одну единицу выгрузки. Несёт `idem_key` (= **натуральный ключ** нативного пути .cfe `TL|СМЕНА|{system}|{station}|{shift}`), `natural_key`, `target_doc_type`, `operation_type`, `body`. **Без блока Дт/Кт** — 1С проводит сама (§4/§9). Частичный UNIQUE-индекс `(company_id, idem_key) WHERE status<>'rejected'` — DB-страховка от задвоения (`models.py:451`, `database.py` v1.8).

### Точка чтения — `PullCheckpoint`
✅ «Что уже забрало расширение БП» для идемпотентности pull (`extension_id`, `acknowledged_uuids`, `models.py:1163`).

### Приёмник — `.cfe` (TradeLedger.cfe в БП ГИГ)
✅ «Глупый исполнитель ярлыка»: диспетчер по `packet_kind`, заполняет `ВидОперации` из ярлыка пакета, проводит штатно. Нативный ключ `TL|СМЕНА|...` (`NefteUchet Module.bsl:1297`), идемпотентность через `РС.TL_СтатусыЗагрузки` (`ПолучитьСтатус`).

### Маршрутизатор учёта — `RouteEngine` / `RoutingRule`
❌ **НЕ реализовано** (§8). Решает `doc_type` + `ВидОперации` + период + расщепление + идемпотентный ключ. Дт/Кт НЕ решает. Сейчас `ВидОперации` захардкожен в .cfe — техдолг (§8.5).

## 5. Что НЕ путать (перегруженные термины)

| Термин | Проблема | Правильно |
|---|---|---|
| **`Connector`** 🗑 (`connectors`, живой роутер) | старое «подключение», дублирует `Source` | мигрировать → `Source` + `source_type` |
| **`OneCConnection`** 🗑 (`onec_connections`, живой) | частный случай `Source` для 1С отдельной таблицей | целевое: `source_type='onec_odata'\|'onec_com'` |
| **`DataEntry.source`** (строка `upload/email/oneC/...`) | третье значение слова «источник» — канал *происхождения* записи | смыслово это `origin`, не `Source` |
| фронт `connectors/` + `channels/` + `sources/` | три UI на один смысл | `channels/`+`sources/` целевые; `connectors/` на вывод |
| **«обработка»** | в 1С = DataProcessor | конвейер у нас = **Канал** |
| **«три уровня»** | путается со слоями | 3 кубика (Источник/Канал/Разрез) ≠ 4 слоя (L1/L2/L3/L4) |
| **ClearLedger** 🗑 | старое имя продукта/кодбазы | продукт = **TradeLedger**; `clearledger/` → `tradeledger/` (отдельная миграция) |
| **слой Normalized/CLEAN/Prepared/EXPORT** | синонимы из разных доков | канон: L2 = **CLEAN**, L3 = **EXPORT** |

## 6. Мнемоника и связь со стадиями

```
SourceType (чем) → Source (куда) → Stream (что+роль) → Channel (как) →
   RawBatch (сырьё, L1 RAW) → [Сверка: ReconcileEngine × Разрезы] →
   NormalizedRecord (L2 CLEAN) → ExportPacket (L3 EXPORT) → .cfe → 1С → эталон (L4 1C_REF)
```

| Стадия конвейера (§2) | Кубики/механизмы | Слой |
|---|---|---|
| 1 СБОР | Источник · Канал (fetch) | → L1 RAW |
| 2 СВЕРКА + НОРМАЛИЗАЦИЯ | Движок сверки · Разрезы · Разрешение | L1↔L2 → L2 CLEAN |
| 3 РАБОТА С ДАННЫМИ | аналитика (7 endpoints ✅) | поверх L2 |
| 4 ПОДГОТОВКА К УЧЁТУ | RouteEngine ❌ · ExportPacket ✅ · .cfe ✅ | → L3 EXPORT → 1С → L4 1C_REF (сверка приёмки L3↔L4) |
