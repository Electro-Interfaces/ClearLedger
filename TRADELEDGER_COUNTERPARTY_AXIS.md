# TradeLedger: контрагенты и договоры как ОСЬ учёта

> Единый план. 18.06.2026. Сводит: универсальные справочники контрагентов/договоров,
> их связь с торговыми точками и **другими разрезами учёта**, операции без договора,
> двунаправленную навигацию, интеграцию в сверку/аналитику. Детальная схема 1С —
> `docs/SCHEMA_REFS_GIG.md`. Термины — `GLOSSARY.md`. Слои L1–L4 — `LAYER2_ARCHITECTURE.md`.

---

## 0. Видение

**Контрагент и договор — центральная ось учёта** (аналог субконто 1С), вокруг которой
строятся почти все разрезы. Практически каждая учётная операция «с кем и по какому
договору». Разрезы (торговая точка, номенклатура, канал, статья ДДС, период…) —
**ограничивают и уточняют** ось, но не заменяют её.

**Редкие исключения — операции БЕЗ внешнего договора**, их надо заложить сразу:
- Розничные продажи (фискальные чеки, банковские карты) — безличный покупатель.
- Внутренние движения (перемещение нефтепродуктов/товаров между своими точками).
- Управленческий/внутренний учёт без внешних контрагентов.

Принцип: **ось контрагента заполнена ВСЕГДА** (внешний / служебный розничный /
внутренняя организация); **договор опционален** (`nullable`, признак «без договора»).

## 1. Принципы

1. **Универсальность.** Справочники не привязаны к ГИГ. Берём ВСЕ поля 1С
   (динамич. fetch по `describe_entity`). Хранение **raw + promo**: полный снимок →
   `raw` JSONB (L1), промо-колонки для сверки/фильтра/связей. См. SCHEMA_REFS_GIG §0.
2. **Ось пронизывает слои.** Контрагент/договор присутствуют типизированно на каждом
   уровне: НСИ → L2-запись → проводка(субконто) → сверка(ключ) → аналитика(группировка)
   → маршрутизация(Дт/Кт). Сейчас — разорвано (см. §2).
3. **Разрез = ограничение оси.** Договор несёт НАБОР ограничений по разрезам, каждое
   со своим охватом (`all` / набор). Точки — первая грань, номенклатура/канал/… — та же
   схема (§5).
4. **Связи — наш слой.** В 1С связи договор↔точка/разрез нет; договор приходит «голым»
   (Владелец+Организация). Охват задаём в TradeLedger.
5. **Один источник истины.** Точки/разрезы контрагента = производное от его договоров.
   Прямой связи контрагент↔разрез (помимо договоров) нет.

## 2. Что есть сейчас (база для встройки)

- **Разрезы — ad-hoc**, единого «Dimension» нет: отдельные сущности (`Counterparty`,
  `Contract`, `ServiceLocation`, `NomenclatureItem`, `Organization`, `Warehouse`,
  `BankAccount`, `Period`, `Source`, `Channel`) + маппинги (`ReconcileMapping.kind`:
  station/fuel/paytype/nomenclature/**counterparty**; договоров НЕТ) + разрезы сверки
  (`reconcile_catalog.ReconRuleDecl.key`).
- **Контрагент уже ось** частично: сверка по ИНН (`reconciliation_service`), разрез
  «Ведомости» (`key=["station","contractor"]`), дебиторка/кредиторка
  (`analytics_service.PayablesReceivables`).
- **Договор почти не задействован**: модель есть, `external_ref` всегда NULL,
  не синхронизируется, нет CRUD-фильтров, не в сверке/аналитике.
- **Розница — без контрагента** (`key=["station","shift"]`); служебного «Розничного
  покупателя» в коде НЕТ.
- **Субконто в проводках** (`AccountingDoc.lines.postings`) — нетипизированный текст
  (`"СубконтоДт1":"Контрагент:XXX"`), не парсится; аналитика берёт `counterparty_name` из шапки.
- **RouteEngine (Дт/Кт)** — не реализован (заполняет `.cfe` в 1С). GLOSSARY §RouteEngine.

## 2б. Эталон 1С (как ось реализована в БП ГИГ)

Снято probe `probe_accounting_model.py` со стенда GIG Base2 (БП 3.0.194.18). Ось =
**субконто плана счетов** (хозрасчётный):

| Счёт | Субконто | Ось |
|---|---|---|
| 60/60.01/02, 62/62.01/02, 76.05/06 | **Контрагенты · Договоры · ДокументыРасчётов** | контрагентская (**тройка**) |
| **62.Р** «Расчёты с розничными покупателями» | **Склады** | **точка, БЕЗ контрагента** |
| 76.АВ/ВА, 19.03 | Контрагенты · Счета-фактуры | контрагент+НДС |
| 41/41.01/41.02 | Номенклатура · Партии · Склады | товарная (без контрагента), кол-во |
| 10.03 | Номенклатура | |
| 90.01/02/03 | НоменклатурныеГруппы · СтавкиНДС (·Номенклатура) [обороты] | результат (без контрагента) |
| 50 · 51 | СтатьиДДС · БанковскиеСчета+СтатьиДДС | денежная |
| 44.01 · 68.02 | СтатьиЗатрат · ВидыПлатежейВБюджет | |

Договор пронизывает НДС/спецрегистры: `ДоговорКонтрагента` — измерение в КнигеПокупок/
Продаж, НДСПредъявленный/Начисленный/сАвансов, `ПрочиеРасчеты` (Контрагент+РасчётныйДокумент+
Договор), `РеализованныеТоварыКомитентов`.

**Три следствия для модели:**
1. **Ось расчётов — ТРОЙКА** Контрагент+Договор+**ДокументРасчётов** (3-е субконто 60/62 —
   FIFO взаиморасчётов «по документам»). Заложить как уровень детализации `settlement_doc_ref?`.
2. **Розница = СКЛАД, не контрагент** (62.Р→Склады; служебного «Розничного покупателя» в
   БП ГИГ НЕТ). Операции без договора имеют естественный разрез — точку. Служебный
   контрагент опционален (только для единого представления оси).
3. **Торговая точка = Склад 1С** (`ServiceLocation` ↔ `Catalog_Склады`, 31 склад: АГЗС
   Витебский/Верево/Межевая/Непокоренных/Огоньки/Симагино, АЗС Брусничное 205…). Товарный
   (41) и розничный (62.Р) учёт нативно по складу → точки синхронизируемы из 1С.

## 3. Модель НСИ (контрагенты, договоры)

Полностью в `docs/SCHEMA_REFS_GIG.md` §1–2. Кратко:
- `Counterparty`: `+raw JSONB`, промо `full_name/type(ЮЛ/ФЛ/ИП)/okpo/head_ref`; апсёрт
  по `external_ref` (Ref_Key). + признак `kind`: `external` | `retail` | `internal` (§6).
- `Contract`: `+raw JSONB`, промо `kind(ВидДоговора)/currency/valid_until/is_closed`;
  `counterparty_id`=GUID владельца; заполнять `external_ref`; `+scope` по разрезам (§5).
- Универсальный pull всех реквизитов; новый `_sync_contracts()` + резолв Владелец→контрагент.

## 4. Ось через слои (целевое сквозное проникновение)

| Слой | Сейчас | Цель |
|---|---|---|
| НСИ | Counterparty ✅, Contract голый | оба universal raw+promo, договоры синхронизируются |
| L2-запись | контрагент в JSONB-мете, договора нет | типизированные `counterparty_ref` (всегда) + `contract_ref?` |
| Проводка/субконто | текст `"Контрагент:XXX"` | типизир. **тройка** `subconto_counterparty_ref` + `subconto_contract_ref` + `subconto_settlement_doc_ref?` (§2б), резолв по external_ref |
| Сверка | по ИНН, разрез «Ведомости» | договор как официальный ключ: `key=[...,"counterparty","contract"]` |
| Аналитика | дебиторка по контрагенту | `group_by=counterparty|contract`, фильтр по договору |
| Маршрутизация | `.cfe` хардкод | RouteEngine: Дт/Кт по (doc_type, operation_type, counterparty, contract, period, point) — future |

## 5. Обобщённая модель: ограничения договора по РАЗРЕЗАМ

Договор имеет **набор граней-ограничений**, по одной на тип разреза; каждая грань —
охват `all` (весь разрез, включая будущие элементы) либо набор (`set`). Контрагент →
разрезы = производное (объединение граней его договоров).

| Грань (dimension) | Сущность | Охват | Пример |
|---|---|---|---|
| `location` (точка) | `ServiceLocation` | all_company / set / unassigned | аренда 3 точек; поставка на все точки |
| `nomenclature` | `NomenclatureItem`/группа | all / set | договор поставки только ДТ |
| `channel`/`source` | `Channel`/`Source` | all / set | договор только по каналу «корп.карты» |
| `organization` | `Organization` | (обычно 1) | юрлицо договора |
| `dds_article`/счёт | счёт/статья | all / set | целевой счёт расчётов |

**Реализация — раздельные M2M по граням** (целостность через FK), единый паттерн охвата:
- Грань 1 (MVP) — точки: `Contract.scope_type` (`company`/`locations`/`unassigned`,
  дефолт после pull) + `contract_locations` (M2M: contract_id, location_id, company_id,
  note?). См. SCHEMA_REFS_GIG §2a.
- Грани 2+ (по той же схеме, по мере надобности): `contract_nomenclature`,
  `contract_channels`, … каждая со своим `*_scope`. Реестр типов разрезов — в каталоге
  (`reconcile_catalog`/новый dimensions-каталог), чтобы UI был единообразным.

Полиморфную единую таблицу `dimension_link(subject, dim_type, dim_ref)` рассмотреть
позже как сахар над гранями (минус — слабее FK-целостность). Старт — типизированные M2M.

## 6. Операции без договора (розница, внутренние)

Эталон 1С (§2б): розница не привязана к контрагенту — счёт 62.Р аналитируется по
**Складам** (= торговым точкам). Значит для безличных операций **главный разрез — точка**,
не контрагент.

- **Розница** (чеки/карты): `contract_ref` = NULL, **главный разрез — точка** (как 62.Р→
  Склады). `counterparty_ref` опционален — служебный «Розничный покупатель» только если
  нужно единое представление оси контрагента в UI/аналитике (в БП ГИГ его нет).
- **Внутренние движения** (перемещения между своими точками): без договора, разрез —
  пара точек (откуда/куда), контрагент — наша организация (`internal`) либо пусто.
- Признак записи `no_contract`; ось остаётся осмысленной за счёт точки.
- Сверка розницы — по своим ключам (`station,shift`/`station,date`), без договора.
- Служебные контрагенты `Counterparty.kind` (`retail`/`internal`) — **опциональны**,
  вводим только при необходимости сводного представления.

## 7. Двунаправленная навигация (цель UX)

- **Контрагент → разрезы**: блок «Где работаем» — бейдж «Вся компания» либо точки
  (по договорам), грани номенклатуры/каналов; список договоров по видам; счётчик
  `unassigned`. API: `GET /counterparties/{id}/locations`, `…/contracts`.
- **Точка → договоры/контрагенты**: блок «Договоры» — адресные (точка ∈ contract_locations)
  + общекомпанейские (`scope=company`), помечены; контрагенты = DISTINCT владельцы.
  API: `GET /locations/{id}/contracts`, `GET /contracts?location_id=`.
- **Договор**: форма с переключателем охвата «Вся компания / Выбранные точки» +
  мультиселект (далее — грани номенклатуры/каналов тем же компонентом).
- **Очередь «нераспределённые договоры»** после импорта из 1С — массовое проставление охвата.

## 8. План реализации (фазы)

- **Фаза 0 — готово.** Схема 1С снята (probe), дизайн оси/связей зафиксирован (этот док + SCHEMA_REFS_GIG).
- **Фаза 1 — НСИ (backend).** Модели raw+promo (`Counterparty`/`Contract` + `kind`,
  служебные контрагенты); универсальный pull; `_sync_contracts()` + `external_ref`;
  миграция; тесты.
- **Фаза 2 — ось договор↔точки.** `scope_type` + `contract_locations`; эндпоинты
  двунаправленные; UI карточек контрагента/точки + форма охвата + очередь нераспределённых.
- **Фаза 3 — обобщение на разрезы.** Грани `contract_nomenclature`/`contract_channels`
  по той же схеме; служебные контрагенты для розницы/внутренних; реестр типов разрезов.
- **Фаза 4 — сверка/аналитика.** Договор в ключах разрезов; `group_by=contract`;
  типизированное субконто в проводках (резолв по external_ref).
- **Фаза 5 — RouteEngine (future).** Маршрутизация Дт/Кт по оси+разрезам.
