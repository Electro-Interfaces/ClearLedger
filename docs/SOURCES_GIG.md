## 0. Базовая модель ГИГ

ГИГ — первый (и пока единственный) профиль TradeLedger. Три направления = три подсистемы (`TL_Нефтепродукты` / `TL_Сопутка` / `TL_Общепит`), но **единый конвейер**: Источник → Канал → L1 → сверка (Движок × Разрезы) → L2 → L3 → БП ГИГ.

**Принцип сверки (решено 13.06):** в каждом направлении есть один **опорный** документ; остальные источники — **внешние/контрольные**, сверяют его срезы. Опорный становится документом 1С; контрольные не порождают первичку, а подтверждают её.

**Решения 13.06.2026:**
- Сопутка и общепит идут **через TradeLedger** (не прямой ЦБ→БП), с последующей загрузкой в бухгалтерию.
- ЦБ как Source — **pull**: TradeLedger тянет из ЦБ (COM / OData / HTTP-сервис; переиспользует onec-стек). Не push.
- Сменный отчёт STS — **опорный** документ по топливу, уже содержащий все каналы оплат; TradeCorp/MSTO/эквайринг/ОФД — внешние/контрольные источники для сверки его срезов.
- **1С — семейство источников.** Любая операционная конфигурация (УТ / КА / Розница / Моё дело / ЭЛСИ.АЗК) = один тип `onec_operational` (механизм pull общий, конфигурация — параметр). **1С:Бухгалтерия компании — ОСОБЫЙ отдельный источник** `onec_accounting` (эталон L4 + приёмник; механизм частично реализован в `onec_router`, не как обычный Source-адаптер).

## 2. Нефтепродукты

**Опорный = сменный отчёт STS** (содержит все pay_type). Каналы оплат → их контрольные/внешние источники:

```
STS shift_report (ОПОРНЫЙ)
  ├─ cards (корп/топл. карты)  ↔ TradeCorp        [внешний: сверка реализации]
  ├─ online (Яндекс/онлайн)    ↔ MSTO             [внешний: сверка заказов]
  ├─ retail_card (банк-карты)  ↔ Эквайринг (Сбер) [контрольный: сверка оплат]
  ├─ retail_cash (наличные)    ↔ ОФД (Σ чеков)    [контрольный: фискализация]
  ├─ voucher/ledger (талоны/ведомости) ↔ договоры/внутр. учёт
  └─ приём/резервуары          ↔ ТТН + уровнемеры [приход = Δостаток]
```

| Источник | Тип | Способ обмена | Роль | Тип документа | Статус |
|---|---|---|---|---|---|
| **STS облако** (Autooplata, `pos.autooplata.ru/tms`) | `sts` | выгрузка | **опорный** | `shift_report`, `receipt`(ТТН) | ✅ адаптер (sys 65/15) |
| **TradeCorp** (наш процессинг корп-карт) | `tradecorp` | выгрузка | внешний (реализация корп-карт) | транзакции карт | 🟡 proxy-клиент → нужен backend-Source |
| **MSTO** (Я.Заправки/Benzuber/FuelUp) | `msto` | выгрузка | внешний (онлайн-заказы) | заказы/продажи | 🟡 proxy-клиент → нужен backend-Source |
| **Эквайринг (Сбер)** | `acquiring_sber` | проверка / выгрузка реестра | контрольный | оплаты по банк-картам | ❌ |
| **ОФД** (вендор TBD) | `ofd_*` | выгрузка | контрольный | фискальные чеки (Σ) | ❌ |
| Резервуары/уровнемеры | — (внутри `shift_report`) | — | контрольный | приход=Δостаток | 🟡 данные есть, движка нет |

## 4. Общепит — через TradeLedger

**Опорный = ЦБ ЭЛСИ.АЗК** (ОРП-блюда + выпуск + списание ингредиентов); рецептуры — справочный поток из той же ЦБ:

| Источник | Тип | Способ обмена | Роль | Тип документа | Статус |
|---|---|---|---|---|---|
| **ЦБ ЭЛСИ.АЗК** | `onec_operational` (onec-pull) | выгрузка (pull) | **опорный** | ОРП-блюда, выпуск продукции, списание ингредиентов | 🟡 |
| **ЦБ — ТТК** (`Документ.ТТК`) | (тот же Source) | выгрузка (pull) | **справочный** (рецептуры) | `kind=recipe` (брутто на порцию) | 🟡 эмитится продюсером |
| **ОФД** (TBD) / **Эквайринг** | как выше | выгрузка / проверка | контрольный | чеки/оплаты общепита | ❌ |

Рабочий — `sts` (`available`); остальные 8 — записи справочника (`status=planned`: метаданные/форма есть, поведение реализуется при постройке адаптера, см. `adapters/catalog.py`). Из записи справочника создаётся экземпляр `Source` (company_id + connection_config + `SourceCredentials`) — CRUD «добавить/привязать/настроить» = следующий слой.

## 7. Каналы обработки — справочник

Второй справочник (параллель источникам): **канал** = конвейер, связывающий 1+ источников и несущий стадии предобработки → преобразования → сверки → сохранения. Реализован в `server/app/channel_catalog.py`; `GET /channel-templates` отдаёт шаблоны. Из шаблона создаётся экземпляр `Channel` (+`ChannelStream` на источник, +`ChannelStage` на стадию).

| Шаблон | Направление | Потоки (источники) | Стадии | Сверки | Статус |
|---|---|---|---|---|---|
| `fuel_shift` | топливо | sts(опорный) + tradecorp/msto/acquiring_sber/ofd | fetch→normalize→transform→reconcile→validate→save | 4 (корп/онлайн/банк/фиск) | partial |
| `fuel_delivery` | топливо | sts.receipt | fetch→normalize→save | — | partial |
| `sidegoods` | сопутка | onec_operational(5 док) + chestny_znak/ofd/acquiring_sber | full | 3 | planned |
| `food` | общепит | onec_operational(блюда/выпуск/ТТК) + ofd/acquiring_sber | full (+разворот по ТТК) | 1 | planned |
| `reference_1c` | эталон | onec_accounting (НСИ/закр.период/политика) | fetch(sync)→snapshot | — | partial |

> ⚠ Фронтовый `channelTemplateService.ts` (`CHANNEL_TEMPLATES`) использует СТАРЫЙ словарь source_type (`rest`/`1c`/`cloud`/`email`) — подлежит выравниванию под backend-реестр (sts/onec_operational/…). Канон — backend `channel_catalog.py`.

Следующий слой: `channels_router` — CRUD экземпляров `Channel` (создать из шаблона + привязать источники + настроить стадии + запуск).
