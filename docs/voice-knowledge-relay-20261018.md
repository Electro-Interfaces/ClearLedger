# Статьи Поддержки для окна телефонии

Узел читает `POST /api/eco/support/knowledge` именным ключом `voice.identify`.
Компания определяется ключом, «Телефония» должна быть включена. В теле разрешены
только код темы `topic` и `limit` от 1 до 3. Компания из тела не принимается.

Ядро использует существующую каноническую карту `eco_app_company_links` приложения
`support`, проверяет его включение и подписывает короткий RS256-токен:
`aud=support`, `svc=voice.knowledge`, `cid=<Support company UUID>`, `jti`, TTL 120 с.
Запрос в Support — `/api/v1/eco/voice/knowledge`, с теми же кодом и лимитом.
Текста разговора, телефона, аудио и расшифровки в этом API нет.

Ответ ограничен опубликованными статьями видимости `cc` или `public`:
`ref`, `title`, `content` до 16000 символов, `visibility`, положительный `version`.
Ядро проверяет форму каждого DTO, число статей, общий размер ответа и удаляет
остальные поля. Вызов имеет таймаут 650 мс, перенаправления запрещены.
Ответ не сохраняется в БД Ядра и помечен `Cache-Control: no-store`.

Невключённая Поддержка, отсутствие карты/ключа подписи, отказ или повреждённый
ответ дают `availability=unavailable`, а не ложный пустой результат. Неизвестная
тема сохраняет только предусмотренный код `topic_unconfigured`.

Локальная проверка 18.10.2026 на собственном временном PostgreSQL:
исходный код воспроизводимо возвращал 404; после реализации 18/18 тестов
knowledge/context/core/token проходят. Проверены карта и JWT, собственный scope,
отказ чужому scope, выключение приложений, запрет подмены компании, лимит и DTO.
Приёмка настоящей цепочки Support → Core → nodewindow выполняется отдельно
после подключения парного endpoint и окна; один этот relay её не доказывает.
