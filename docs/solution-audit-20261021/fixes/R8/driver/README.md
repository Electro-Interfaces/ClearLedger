# Драйвер кластера R8 — парная проверка «Ядро выдаёт — Поддержка принимает»

Контур изолированный, ресурсы только свои: контейнеры `fix-r8-*`, порты 37000–37999.

| Что | Где |
|---|---|
| Поддержка (ветка `fix/audit-r2-core-channel-20261021`, **только чтение**) | `http://127.0.0.1:37010` |
| Издатель JWKS Ядра (реальный `sso.public_jwks()`) | `http://127.0.0.1:37020/jwks` |
| База Поддержки (`pgvector/pgvector:pg16`) | контейнер `fix-r8-pgv`, 127.0.0.1:37433 |
| База проверок Ядра (`postgres:16`) | контейнер `fix-r8-pg`, 127.0.0.1:37432 |
| Образ прогона (Python 3.13 — такой же, как в `server/Dockerfile`) | `fix-r8-py:1` |

Рантайм (`FIX_RT`) держит `server.env`, `start-server.sh` и ключ подписи `sso.key`.
В репозиторий он не попадает: ключ и пароль базы — секреты, пусть синтетические.

```sh
# 1. База Поддержки: db/init/*.sql ветки R2 + фикстура двух заказчиков
# 2. Экземпляр Поддержки:
FIX_RT=<рантайм> "$FIX_RT/start-server.sh" &
# 3. Прогон (ярлык — имя файла доказательства):
FIX_LABEL=red-before python docs/solution-audit-20261021/fixes/R8/driver/run.py
```

Ключ подписи живёт в рантайме, а не генерируется на прогон: Поддержка кеширует JWKS
пять минут, и новая пара на каждый прогон требовала бы перезапуска её экземпляра
между красным и зелёным — тогда условий менялось бы два вместо одного.

Подпись не подделывается: экземпляр Поддержки настроен доверять именно этому
издателю. Проверяется, что умеет обладатель **законного** служебного токена Ядра, а
не можно ли обойти проверку подписи.

Токен выпускается реальными путями выдачи Ядра (`space_projection._target`,
`space_desk._support`), поэтому красный и зелёный прогоны отличаются только
продуктовым кодом. В доказательства уходит разбор клеймов без подписи и без `jti`;
сам токен — никогда.

Фикстура: два заказчика Поддержки (`fix-r8-a`, `fix-r8-b`), у каждого опубликованный
процесс с ребром **без слоёв полномочий** — по нему машина доставляет исход внешней
работы (положительный контроль P-01), и участник-диспетчер у заказчика А (контроль
обычного handoff человека, P-02).

## Сброс между прогонами

Положительный контроль P-01 двигает процесс заказчика А на шаг «выполнена», а handoff
связывает участника с устойчивым `sub`. Перед повторным прогоном фикстура возвращается
в исходное состояние (`reset.sql` рантайма): стадии обоих процессов на `new`, история
переходов очищена, `users.eco_user_id` снят.

## Красный и зелёный одним драйвером

Корень кода Ядра задаётся переменной `FIX_CORE`:

```sh
FIX_LABEL=red-before  FIX_CORE=<дерево на e1cc3e6b>/clearledger/server  python …/run.py
FIX_LABEL=green-after                                                    python …/run.py
```

Между прогонами отличается **только продуктовый код Ядра**: экземпляр Поддержки, её
база, фикстура, ключ подписи и сам драйвер — одни и те же.

## Ресурсы контура убраны

После снятия доказательств контур остановлен и удалён: контейнеры `fix-r8-pg`,
`fix-r8-pgv`, сеть `fix-r8-net`, образ `fix-r8-py:1`, экземпляр Поддержки на 37010 и
издатель на 37020. Порты 37000–37999 свободны. Чужие процессы и контейнеры (`ch-*`,
`audit-*`, `support-kb-test-*`, `kka-*`, `orca-web-ru`) не трогались.

Рантайм с ключом подписи и паролями базы жил только в каталоге сессии и в репозиторий
не попадал. Два временных рабочих дерева (`before` на `e1cc3e6b`, `after` на
`fe94f3f5`) из `git worktree` сняты; сами каталоги остались в каталоге сессии, потому
что контейнерный прогон оставил в них файлы кеша от своего пользователя — они уйдут
вместе с каталогом сессии.

Чтобы снять контур заново, нужны: `postgres:16` (своя база проверок Ядра),
`pgvector/pgvector:pg16` (база Поддержки — без расширения `vector` её схема не
применяется), образ по `server/requirements*.txt` на `python:3.13-slim`, `db/init/*.sql`
ветки R2 и фикстура выше. Поднимать базу Ядра с `max_locks_per_transaction` не меньше
512, если рядом идут другие прогоны: уборка `conftest` делает `DROP SCHEMA public
CASCADE` по схеме в сотни таблиц и на значении по умолчанию 64 падает по таблице
блокировок.
