## Что было

`sign_service_token` в `clearledger/server/app/services/sso.py` выпускала токен с
клеймами `iss`, `aud`, `sub`, `svc`, `jti`, `iat`, `nbf`, `exp` — и всё. Арендатора
удостоверение не называло, поэтому область действия служебного вызова задавал
параметр `companyId` **запроса**. Один служебный токен Ядра работал в контуре любого
заказчика приложения: достаточно было подменить параметр.

Необязательный аргумент `company_id` у функции был и клал клейм `cid`, но:

* им пользовались **три пути выдачи из десяти** — `managed_connectors`,
  `ticket_communications`, `voice_support_context`; остальные семь компанию в
  удостоверение не кладут, хотя она в точке подписи уже прочитана;
* контракт версии 2 служебного канала `cid` арендатором **не считает**: там он лишь
  выбирает компанию по умолчанию внутри списка `companies`, и прямые формы — это
  `company` либо `company_id`.

Нигде не добавлялось: она уже была прочитана в каждой точке выдачи, просто попадала

## Что сделано

### Корень: один обязательный аргумент на стыке

`sign_service_token(*, aud, scope, app_company_id, ttl_seconds=120, actor_id=None)` —
`app_company_id` без значения по умолчанию, пустая строка отвергается `ValueError`.

Защита стоит там, где сходятся все вызовы, а не в маршрутах: подпись одна, и забыть
компанию можно только здесь. Новый путь выдачи теперь обязан её назвать — иначе вызов
не соберётся. Повторять проверку в каждом из десяти маршрутов значило бы развести
десять копий, которые разойдутся молча.

### Форма клеймов: прямая, двумя именами с одним значением

```
"cid":        <компания в терминах получателя>
"company_id": <то же, если это UUID>      либо      "company": <то же, если это код>
```

**Почему прямая форма, а не список `companies`.** В точке выдачи Ядру известна ровно
одна компания — та, чью пару прочитала карта. Список пришлось бы собирать специально,
и он назвал бы компании, которых этот вызов не касается: область действия токена
обязана быть минимальной (требование задания). Прямая форма физически не может назвать
больше одной. Слаг-форма (`companies[].slug` ↔ `companies.code` Поддержки) потребовала
бы второй карты «кто чей код»: Ядро хранит `external_company_id`, а `external_code` —
нужный слаг — поле необязательное и заведено «для сверки глазами», опираться на него
значило бы молча терять арендатора там, где его не заполнили.

**Почему `company_id` и `company` оба.** `external_company_id` — строка, и комментарий
модели говорит прямо: «у разных приложений разный тип». Приёмник (`tokenTenantRefs` в
`scripts/lib/sso-verify.js`) читает `company_id` **только как UUID**, а неUUID — как
слаг в `company`. Положить код в `company_id` значило бы потерять арендатора без
единого сообщения об ошибке.

**Почему `cid` остался.** По нему арендатора читают уже работающие приёмники, и терять
их нельзя — см. таблицу совместимости ниже.

`kid` в заголовке был и остался (`settings.sso_kid`, по умолчанию `elsyplus/1`):
контракт версии 2 закрепляет ключ по `kid`, и набор без него проверялся бы «первым
попавшимся». Срок жизни (120 с), `sub`, `svc` и скоупы не менялись: задача не в том,
чтобы сделать удобнее.

### Совместимость: кто ещё принимает служебный токен Ядра

Проверены все приёмники, не только процессный фасад.

| Приёмник | Что читает из токена | После правки |
|---|---|---|
| TSupport `routes/v1/process.js` (`requireCoreService`, ветка R2) | `companies`/`company`/`company_id`; `cid` — выбор по умолчанию в списке | **закрывается**: арендатор следует из токена |
| TSupport `routes/v1/eco.js` (`coreService(scope)`: `projection`, `events`, `desk`) | только `svc`; компания из тела и запроса | не ломается — лишние клеймы игнорируются; появилось чем закрыть тот же корень (см. «что осталось») |
| TSupport `routes/v1/connector-management.js` | `claims.cid === req.query.companyId`, `claims.actor` | не ломается: `cid` сохранён, `actor` сохранён |
| TSupport `routes/v1/voice-knowledge.js` | `aud`, `svc`, `claims.cid` как наша компания | не ломается |
| TSupport `routes/v1/voice-context.js`, `ticket-communications.js` | `claims.cid` | не ломается |
| TSupport `lib/support-context-auth.js` | отдельная подпись `support_context.service_token` (своя аудитория, `cid` + `coreCid`) — не `sign_service_token` | не затронут, арендатора называл и раньше |
| Узел «Телефонии» (ContactHub) | `cid` из своей настройки | не ломается |
| Кромка Ядра `routers/edge_router.py` | `X-Cloud-API-Key`, не JWT | не затронута |
| `routers/space_bridge_router.py` Ядра | пропуска партнёра (`sign_visit_token`), не служебные токены | не затронут |

Ни один приёмник не проверяет состав клеймов «по белому списку», поэтому добавленные
клеймы ничего не ломают, а `cid` сохранён ровно для тех, кто читает арендатора по нему.

## Что осталось незакрытым

1. **Эко-мост Поддержки `scripts/routes/v1/eco.js` по-прежнему берёт компанию из
   запроса.** `coreService(scope)` проверяет только `svc`, а `companyId` читает из тела
   и параметров — тот же корень, что у B-11, на маршрутах `projection`, `events` и
   `desk`. Правка Ядра даёт этому мосту всё необходимое: токен теперь называет
   арендатора на **всех** скоупах, не только на процессном фасаде, — но сам мост
   остаётся в репозитории Поддержки и в границу ни R2, ни R8 не входил. Это следующий
   шаг пары, и он заводится отдельно (R2 отметил его тем же пунктом).
2. **Соответствие `external_code` не проверяется.** Если при онбординге в карту внесли
   чужой `external_company_id`, токен честно назовёт названную там компанию. Карту
   ведёт человек в Центре управления, и это сознательная граница: Поддержка проверяет
   соответствие у себя (`SERVICE_TENANT_UNKNOWN`), а второй справочник «кто чей код» в
   Ядре заводить незачем.
3. **Миграции не потребовались:** источник компании уже в схеме
   (`eco_app_company_links`), новых колонок и номеров нет. Задвоенные номера TSupport
   эта работа не касается.
4. **Выкатка парная и в этом порядке:** сначала эта правка Ядра (токен с арендатором
   старая Поддержка принимает как прежде — лишние клеймы она игнорирует), затем
   TSupport#6 (новая Поддержка без такого токена процессный фасад не обслуживает).
