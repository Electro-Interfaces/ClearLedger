# HubEx → управленческая отчётность TradeLedger

> Проработка от 19.06.2026. Что можно построить на API HubEx FSM в рамках TradeLedger
> для управления сетью ЭЗС РусГидро. Основано на read-only разведке живого API.

## 1. Что реально доступно (факты разведки)

База: `https://api.hubex.ru/fsm`, авторизация по сервисному токену (`HUBEX_SERVICE_TOKEN`,
в `deploy/.env`, наружу не уходит). Подтверждённые рабочие эндпоинты (HTTP 200/206):

| Эндпоинт | Объём | Назначение |
|----------|-------|-----------|
| `GET /WORK/Tasks` | **10 012 заявок** | Заявки/инциденты/ТО — ядро отчётности |
| `GET /ES/Assets` | **463 объекта** | ЭЗС как объекты обслуживания |
| `GET /ES/Companies` | 143 | Подрядчики / заказчики |
| `GET /ES/Locations` | 9667 | Адреса + координаты (`coordinate`) |
| `GET /WORK/TaskStatuses` | 140 | Справочник статусов |
| `GET /WORK/TaskTypes` | 11 | Типы заявок (инцидент/авария/ТО/…) |
| `GET /WORK/WorkTypes` | 46 | Виды работ, есть `erpID` → мост к ERP/1С |
| `GET /SLA/Criticalities` | — | Уровни критичности |

Пагинация через заголовок `Range: items=FROM-TILL`, общий объём — в `Content-Range: .../TOTAL`.

### Структура заявки (`WORK/Tasks`) — что несёт каждая запись
- **Идентификация:** `number`, `taskType`, `workType` (узел/компонент ЭЗС), `notes`
- **Статус:** `taskStatus` (+цвет), `taskStage` (стадия), `actualCriticality` (+цвет)
- **Объект:** `asset` (ЭЗС: id, name, company), `location` (адрес + **координаты**)
- **Люди:** `assignedTo` / `listAssignedTo` (исполнитель, признак `isTechnician`),
  `requestedBy` (заявитель), `company` (подрядчик)
- **Жизненный цикл (`timesheet`):** `created` · `requested` · `assigned` · `deadline`
  · `completed` · `closed` — полная временная шкала ⇒ можно считать ВСЕ SLA-метрики
- **Прочее:** `isRated`, `childCount`, `lastModified` (для инкрементального синка)

### Реальные распределения (по выборке свежих заявок)
- **Виды работ** детализированы по узлам ЭЗС: отказы CHAdeMO / CCS / Type2 / GBT,
  RFID-карты, ПО зарядной станции, ремонт коннекторов, восстановление работ.
  ⇒ прямой сигнал для плана закупки ЗИП и анализа надёжности оборудования.
- **Критичность:** критичные / высокие / средние / информационные.
- **Исполнители:** заявки распределены по нескольким подрядчикам ⇒ сравнение качества.

## 2. Каталог управленческих отчётов

### A. Состояние сети (оперативный дашборд)
KPI-плитки: открытых всего · из них критичных · **просроченных** (`deadline < now` и не закрыта)
· новых без исполнителя. Плюс:
- Воронка по стадиям (`taskStage`): новые → назначены → в работе → на контроле → закрыты
- Срезы по типу (инцидент/авария/ТО) и по критичности
- **Карта заявок** (`location.coordinate`) — где сейчас аварии на сети

### B. SLA и сроки (из `timesheet`)
- **Время реакции** = `assigned − requested`
- **Время в работе** = `completed − assigned`
- **Полный цикл** = `closed − created`
- **% соблюдения SLA** = доля `completed ≤ deadline`
- **Просрочка** = открытые с истёкшим `deadline`
- Срезы по типу / критичности / подрядчику; средние + перцентили p50/p90

### C. Надёжность оборудования (Asset Reliability)
- Топ-N проблемных ЭЗС по числу заявок и по числу аварий
- Распределение `workType` (46 видов) → какие узлы отказывают чаще ⇒ **план ЗИП**
- Повторные отказы по объекту (recurrence), оценка MTBF
- Доля аварийных vs плановых работ по объекту

### D. Эффективность подрядчиков (Contractor Performance)
- Объём заявок по исполнителю / подрядной компании
- Среднее время выполнения и % SLA в разрезе подрядчика
- Текущая нагрузка (открытые заявки на исполнителя)
- Рейтинг (`isRated`)

### E. Динамика и тренды
- Поток заявок по неделям/месяцам (`created`) — сезонность отказов
- Backlog / burndown незакрытых заявок
- Тренд доли аварий в общем потоке

### F. Финансовый мост (главная управленческая ценность) ⭐
- Стоимость обслуживания на объект (нормо-часы/затраты по заявкам) → **cost-per-asset**
- Сопоставление OPEX обслуживания ЭЗС с её выручкой из аналитики TradeLedger
  → **рентабельность точки с учётом сервиса**
- `workType.erpID` — ключ для проводок затрат на ТО в 1С/ERP

## 3. Архитектура встраивания в TradeLedger

Вписывается в существующую модель «Источник → поток → L1 → аналитика»:

1. **HubEx = новый Источник** (`source_type = hubex_fsm`), рядом со STS / ЦБ / 1С.
2. **Синхронизация в Postgres** (не дёргать 10k заявок на каждый запрос):
   - постраничный pull (`Range`) с инкрементом по `lastModified`
   - таблица `hubex_tasks`: raw JSONB (L1) + промо-колонки (`number`, `status`,
     `task_type`, `work_type`, `criticality`, `asset_id`, `assignee`, `company`,
     `created/requested/assigned/deadline/completed/closed`)
   - справочники: `hubex_assets`, `hubex_companies`, статусы/типы/критичность
3. **Backend** `/api/hubex/analytics/*` (по образцу существующих `/api/analytics/*`):
   `network-health`, `sla`, `asset-reliability`, `contractors`, `trends` — SQL-агрегаты
   по локальной таблице (быстро, офлайн-устойчиво).
4. **Frontend** — раздел «Сервис сети» (или режим рабочего стола для EV-направления):
   дашборд с KPI, воронкой, топом проблемных ЭЗС, SLA-сводкой, картой.
5. **Фаза 2** — вебхуки `MSG` для near-real-time обновления статусов.

## 4. Рекомендуемый MVP (этап 1)

1. `hubex_service`: методы `list_tasks(filters, paging)`, `get_assets`, справочники.
2. Синк заявок + assets в Postgres (промо-колонки) с инкрементом по `lastModified`.
3. Эндпоинты `/api/hubex/analytics/network-health` + `/sla`.
4. Страница-дашборд: KPI-плитки + воронка статусов + топ-10 проблемных ЭЗС + SLA-сводка.

Даёт немедленно видимую ценность для управления сетью РусГидро; дальше наращиваются
надёжность оборудования, подрядчики, тренды и финансовый мост.

## 5. Технические заметки
- Объём 10 012 заявок ⇒ обязателен синк в БД + инкремент по `lastModified`, не live-fetch.
- Часть путей вернула 404 (`PA/Employees`, `SLA/Rules`, `WH/Items`) — либо иные пути,
  либо нет в скоупе токена; исполнители доступны внутри самой заявки (`assignedTo`).
- 140 статусов — для воронки группировать по `taskStage`, не по сырому статусу.
- Координаты есть у локаций ⇒ карта реализуема без геокодинга.
