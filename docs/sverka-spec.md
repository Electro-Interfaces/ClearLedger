# Спецификация сверки TradeLedger ↔ БП ГИГ

> Версия: 2.0 · Дата: 2026-05-24 · Терминология: `D:\Users\magsp\Ledger\GLOSSARY.md`
> 📛 Продукт = **TradeLedger**. «ClearLedger» ниже = синоним (имя кодовой базы, переименование — отдельная миграция). Эта спека уже **4-слойная** (L1 RAW → L2 CLEAN → L3 EXPORT → L4 1C_REF) — это канон.

Этот документ — рабочая спецификация: какие поля тянуть из 1С, какие
ключи связи использовать, какие формулы применять для двух
маркетинговых сценариев сверки:

1. **Сменные отчёты** (АЗС → STS API → ClearLedger) ↔ **ОРП** в БП ГИГ
2. **ТТН** (поставщик → файл/email → ClearLedger) ↔ **ПТУ** в БП ГИГ

Текущая sync_documents тянет только шапки (Number, Date, СуммаДокумента,
Контрагент, Организация, Склад). **Для реальной сверки этого недостаточно** —
нужны табличные части и реквизиты ТТН.

## 0. 4-слойная архитектура данных (требование МАГ)

Сверка между ClearLedger и 1С — это НЕ 1↔1 между двумя массивами.
В системе **четыре слоя данных**, и сверки идут попарно между ними.

### 0.1 Слои

```
┌──────────────────┐      ┌──────────────────┐      ┌──────────────────┐      ┌──────────────────┐
│  L1 RAW          │      │  L2 CLEAN        │      │  L3 EXPORT       │      │  L4 1C_REF       │
│  Из внешних      │      │  Нормализовано   │      │  Подготовлено    │      │  Эталон из БП    │
│  систем как есть │ ───▶ │  + проверено     │ ───▶ │  для загрузки    │ ◀──▶ │  ГИГ для сверки  │
│                  │      │  + наши правки   │      │  в 1С            │      │                  │
└──────────────────┘      └──────────────────┘      └──────────────────┘      └──────────────────┘
       │                          │                          │                          │
   STS API,                   Бухгалтер ↓               ↑ Загрузчик               sync_documents
   ТТН-файл,                  правит и                 на стороне 1С              + fetch_doc_lines
   email                      утверждает               (TradeLedger.cfe           + fetch_postings
                                                       тянет L3)
```

**L1 — RAW**. Сырьё из внешних источников «как пришло», immutable:
- STS API: JSON смены (shift_id, station_id, fuel_sales[], payments[], totals).
- ТТН-файл: PDF/Excel/XML, сохранён в `IndexedDB sources` + распознан в
  `extracts` (текст + поля).
- Email: оригинальное .eml + вложения.
- 1С-XML (если поставщик прислал в формате 1С) — то же.

В моделях ClearLedger сейчас представлен через:
- `Source` / `SourceFile` / `SourceCredentials` — описание подключения.
- `IntakeItem` / `ExtractRecord` — пайплайн извлечения.
- Сам сырьевой `DataEntry` со `source='upload'|'api'|'email'|'oneC'|...`
  и `status='new'|'recognized'` — **это и есть L1**.

L1 **не редактируется** — только чтение и переобработка.

**L2 — CLEAN**. Нормализованная версия того же документа: бухгалтер/AI
подтвердили распознавание, поправили опечатки, расставили правильные
коды номенклатуры, выбрали контрагента из справочника. Это **наша
рабочая версия документа** — на её основе строятся отчёты, сверки и
выгрузка в 1С.

В моделях:
- `DataEntry` со `status='verified'` — **это L2**.
- `meta` JSONB содержит нормализованные значения (правильный ИНН,
  правильные суммы, правильная номенклатура).
- Связь L1↔L2 через `source_id` + `match_status`/`linkService`.

**L2 ≠ L1 по содержанию** — это важно. Бухгалтер мог исправить опечатку
поставщика, перевести количество из мешков в кг по коэффициенту,
поменять контрагента (одинаковое имя у двух разных ИНН).

**L3 — EXPORT**. То что мы **отправляем** в 1С через её расширение
(TradeLedger.cfe тянет пакеты через HTTP API ClearLedger). **L3 ≠ L2** —
часть данных может агрегироваться, исключаться или объединяться:
- Несколько смен за день → один ОРП (если в БП так настроен учёт).
- Кассовые операции вынесены в отдельные ПКО.
- Услуги (доставка) из ТТН могут идти отдельным документом.
- Часть статей не выгружается вообще (вспомогательные, переходные).

Сейчас в моделях ClearLedger **L3 явно не выделен**. Это пробел —
нужна модель `ExportPacket(id, kind, source_entries[], status,
exported_at, ack_at)` или похожее. Иначе нельзя сказать «вот это мы
точно отправили в 1С» vs «это просто прошло проверку».

**L4 — 1C_REF**. Эталон того что **реально лежит в БП ГИГ** после
загрузки. Источник — sync_documents (шапки) + fetch_doc_lines (ТЧ)
+ fetch_postings (проводки). В моделях это **`AccountingDoc`**.

### 0.2 Сверки между слоями

Сверка — попарная между слоями. Каждая отвечает на свой вопрос:

| Сверка | Вопрос | Что бьёт расхождение |
|---|---|---|
| **L1 ↔ L2** | «Правильно ли мы распознали и нормализовали сырьё?» | Бухгалтер пропустил ошибку OCR, неправильно подобрал контрагента из справочника, поменял сумму без основания |
| **L2 ↔ L3** | «Что из нашей нормализованной базы реально пошло в выгрузку?» | Документ забыли пометить «к выгрузке», агрегация смён сломалась, исключения по статьям применились не там |
| **L3 ↔ L4** | «Загрузило ли 1С наш пакет корректно?» | Расширение упало, проводки 1С отличаются от ожиданий, ВидОперации поставило не то, период оказался закрытым |
| **L1 ↔ L4** | «End-to-end: соответствует ли то что в 1С исходному источнику?» | Накопленные ошибки L1→L2 и L2→L3 и L3→L4 в сумме |
| **L4 эталон ↔ L4 пред.период** | «Не изменилось ли в БП то что мы уже сверили?» | Бухгалтер задним числом изменил документ; перепроведение поменяло проводки |

Текущая реализация `reconciliation_service` делает **только L1↔L4**
напрямую (DataEntry.meta ↔ AccountingDoc). L2 не выделен, L3 отсутствует.
Для полного цикла нужно:

1. Развести в `DataEntry` flag `is_normalized` (или статус `verified`) —
   это будет L2.
2. Добавить модель `ExportPacket` — L3.
3. Сверочный сервис делает 4 прохода (L1↔L2, L2↔L3, L3↔L4, L1↔L4),
   результат пишет в `ReconcileMatch` с указанием `between` (например
   `'l2_l3'` или `'l3_l4'`).
4. UI показывает **матрицу 4×4** для каждого документа: где совпадает,
   где есть delta, на каком переходе появилась.

### 0.3 Что меняется в моделях

```python
# AccountingDoc уже есть = L4.
# DataEntry уже есть = L1 (с status='new'|'recognized') ИЛИ L2 (status='verified').
# Для явного разделения: добавить поле layer = Literal['raw', 'clean'].

class ExportPacket(Base):                                # L3 (новая)
    __tablename__ = "export_packets"
    id, company_id
    kind                # 'shift_orp' | 'purchase_ttn' | 'cash_pko' | ...
    target_doc_type     # на какой тип AccountingDoc мы рассчитываем
    status              # 'draft'|'queued'|'sent'|'acked'|'rejected'
    sent_at, acked_at
    payload             # JSONB — что выгрузили
    source_entry_ids    # array UUID — какие L2 DataEntry агрегированы
    target_doc_id       # UUID AccountingDoc когда 1С квитировала

class ReconcileMatch(Base):                              # расширить
    ...
    layer_from   # 'l1' | 'l2' | 'l3' | 'l4'
    layer_to     # ' ... '
    severity, summary, details
```

### 0.4 UI ожидание

Когда бухгалтер открывает документ — он должен видеть **полную цепочку**:
1. **L1** — оригинальный файл/JSON (превью).
2. **L2** — наша нормализованная версия с подсветкой того что
   исправлено.
3. **L3** — что выгрузили (или статус «не выгружено»).
4. **L4** — шапка / ТЧ / проводки из БП ГИГ.

И **3 индикатора сверки**: L1↔L2 (распознавание), L2↔L3 (выгрузка),
L3↔L4 (приёмка 1С). Если все три зелёные — документ полностью
закрыт; если хоть один красный — видно где разрыв.

### 0.5 Приоритет реализации

Сейчас (Шаги 1-4 спеки) реализован только **L4** и **частично L1**.
L2 неявно есть в `DataEntry.status='verified'` без выделения,
**L3 отсутствует**. Минимальный путь к закрытию цикла:

1. **Phase A**: реализовать L4 в UI полностью — шапка + ТЧ + проводки
   (это текущая задача, сейчас работаем тут).
2. **Phase B**: ввести `DataEntry.layer` + UI «L1 ↔ L2» (diff
   сырьё vs нормализованное).
3. **Phase C**: модель `ExportPacket` + UI выгрузки + сверка L3↔L4.
4. **Phase D**: матрица сверки 4×4 в UI и комбинированные правила
   (закрытый период + расхождение на каком слое = разный severity).

## 1. Сменный отчёт АЗС ↔ ОРП

### 1.1 Что есть в ClearLedger (источник истины — STS API)

Через `pos.autooplata.ru/tms` за каждую смену приходит JSON:

| Поле смены | Тип | Что |
|---|---|---|
| `shift_id` | int | Номер смены в STS |
| `station_id` | int | Код АЗС в STS (208, 209, 210, 5, 8) |
| `opened_at` | datetime | Открытие смены |
| `closed_at` | datetime | Закрытие смены |
| `operator` | string | ФИО оператора |
| `fuel_sales` | list | Продажи по топливу |
| `sideline_sales` | list | Продажи сопутки |
| `payments` | list | Разбивка по видам оплат |
| `cash_in_out` | object | Наличный остаток на начало/конец |
| `totals` | object | Σ выручка с НДС, Σ НДС, Σ скидки |

**Каждая смена** = ровно **один ОРП** в БП ГИГ. Связка по `(дата + склад)` или
через TL_СоответствиеИсточников расширения TradeLedger.cfe.

### 1.2 Что нужно из ОРП БП ГИГ

#### 1.2.1 Шапка `Document_ОтчетОРозничныхПродажах`

```python
ORP_SELECT_HEADER = [
    "Ref_Key",
    "DeletionMark",
    "Posted",
    "Number",                              # Номер документа в БП
    "Date",                                # Дата+время (закрытия смены)
    "Организация_Key",                     # → UUID Catalog_Организации
    "Склад_Key",                           # → UUID Catalog_Склады (АЗС)
    "ВидОперации",                         # Enum: ОтчетККМОПродажах / НТТО / ...
    "СуммаДокумента",                      # Σ с НДС
    "Комментарий",                         # Может содержать "Загружено из ..."
    # Доп. реквизиты — для аудита загрузчика TradeLedger:
    "ОтражениеВРеглУчете",                 # Дата отражения
]
```

Критично: `ВидОперации` определяет проводки. Для розничной кассы ожидаем
**`ОтчетККМОПродажах`** (см. memory `project_srez2_implemented` —
50.01/62.Р/90.01.1/90.03/68.02), а не `НТТО` (90.01/62.Р без 50.01).
Если ВидОперации иной — сверка по формуле даст ложное расхождение.

#### 1.2.2 ТЧ «Товары» — `Document_ОтчетОРозничныхПродажах_Товары`

OData отдаёт ТЧ как навигационное свойство. URL:
```
/Document_ОтчетОРозничныхПродажах_Товары?$filter=Ref_Key eq guid'<ref>'
```

или через `$expand=Товары` в основном запросе.

```python
ORP_SELECT_TOVARY = [
    "Ref_Key",          # FK на шапку (для join'а на стороне ClearLedger)
    "LineNumber",
    "Номенклатура_Key", # → UUID Catalog_Номенклатура
    "Количество",       # дробное (литры топлива)
    "Цена",             # за единицу
    "Сумма",            # = Количество × Цена
    "СтавкаНДС",        # Enum: НДС20 / НДС10 / БезНДС / НДС22
    "СуммаНДС",         # выделенный НДС
    "Всего",            # = Сумма (с НДС если СуммаВключаетНДС=Истина)
    "СчетУчетаНоменклатуры",   # 41.02 для розницы
    "СчетУчетаДоходов",        # 90.01.1
    "СчетУчетаНДС",            # 90.03
]
```

Сверка по строкам:
- **GROUP BY Номенклатура** на стороне ClearLedger:
  Σ Количество (л) ⇄ STS `fuel_sales[].volume_l` + `sideline_sales[].qty`
  Σ Сумма (₽ с НДС) ⇄ STS `*_sales[].amount`

#### 1.2.3 ТЧ «Оплата платёжными картами» — `_ОплатаПлатежнымиКартами`

```python
ORP_SELECT_OPLATA = [
    "Ref_Key", "LineNumber",
    "ВидОплаты_Key",    # → Catalog_ВидыОплат (Эквайринг / Карта банка / ...)
    "Сумма",
    "Эквайер_Key",      # → Catalog_Контрагенты (банк-эквайер)
    "СчетУчетаРасчетов",# 57.03 для эквайринга / 50.01 для наличных не сюда
]
```

#### 1.2.4 ТЧ «Денежные средства» / Наличные

Наличные в ОРП БП 3.0 идут отдельной ТЧ или прямо через `СуммаНаличных` шапки.
Зависит от ВидОперации. Для `ОтчетККМОПродажах` обычно:
```python
ORP_SELECT_NALICHNYE = [
    "Ref_Key",
    "СчетКассы_Key",           # Catalog_Кассы (50.01)
    "СуммаНаличными",          # Σ оплат наличными
]
```

Альтернативный способ — взять не ТЧ, а проводки документа из

Поля:

Для розничной модели ОРП (ВидОп=ОтчетККМОПродажах) ожидаем **5 проводок**:
| # | Дт | Кт | Сумма | Что |
|---|---|---|---|---|
| 1 | 90.02.1 | 41.02 | себестоимость | Списание |
| 2 | 62.Р | 90.01.1 | СуммаДокумента | Выручка с НДС |
| 3 | 57.03 | 62.Р | Σ эквайринг | Безнал |
| 4 | 50.01 | 62.Р | Σ наличные | Касса |
| 5 | 90.03 | 68.02 | round(СуммД × 22/122, 2) | Выделение НДС |

см. memory `project_orp_retail_vat_model`).

### 1.3 Ключи связи STS-смена ↔ ОРП

Приоритет ключей (от строгого к мягкому):

1. **TL_СоответствиеИсточников** (если коннектор уже работает через
   TradeLedger.cfe): запрос `?$filter=Тип eq 'retail_sale_sidegoods' and
   ИсточникUUID eq guid'<shift_id_uuid>'` → возвращает ссылку на ОРП.
   Это идемпотентный ключ, гарантирующий 1↔1.
2. **(Дата + Склад + Организация)** где Дата = `Дата(opened_at)` или
   `Дата(closed_at)`, Склад = маппинг STS.station_id → Catalog.Склады.Код
   (нужна таблица соответствия), Организация = ГИГ (Ref_Key известен).
3. **Сумма документа** (СуммаДокумента ОРП ⇄ totals.gross в STS) — для
   валидации связки, не для поиска.

### 1.4 Формулы сверки (ОРП)

| Что | Формула | Допуск |
|---|---|---|
| Общая выручка | `Σ STS *.amount` == `ОРП.СуммаДокумента` | ±0.01 ₽ |
| Σ литры топлива | `Σ STS fuel_sales[].volume_l` == `Σ ОРП.Товары.Количество WHERE Номенклатура.ВидНоменклатуры='Топливо'` | ±0.01 л |
| Σ эквайринг | `Σ STS payments WHERE type IN ('card','online')` == `Σ ОРП.ОплатаКартами.Сумма` | ±0.01 ₽ |
| Σ наличные | `Σ STS payments WHERE type='cash'` == `ОРП.СуммаНаличными` | ±0.01 ₽ |
| НДС | `ОРП.Σ Кт 68.02` == `round(ОРП.СуммаДокумента × 22/122, 2)` | ±0.01 ₽ |
| Σ Дт 62.Р == Σ Кт 62.Р | Баланс по контрагенту | ±0.01 ₽ |
| Кол-во строк по топливу | STS видов топлива == ОРП строк с Номенклатура.Топливо | ровно |

**НЕ применять** для розницы формулу `Σ(90.01.1+90.03) = СуммаДокумента` —
это B2B-формула, на рознице даёт ложное расхождение 18% (= 22/122).

### 1.5 Маппинг справочников (STS → 1С)

| Сущность STS | Справочник 1С | Ключ |
|---|---|---|
| `station_id` (208) | Catalog_Склады | `Код` или маппинг через TL_МаппингСтанций |
| `fuel_type` («АИ-95-К5») | Catalog_Номенклатура | по `Артикул` или `Код` |
| `pay_type` («card», «cash») | Catalog_ВидыОплат | через `TL_МаппингОплат` |
| Организация | Catalog_Организации | один Ref_Key (ООО ГИГ) |
| Контрагент розницы | Catalog_Контрагенты | специальный «Розничный покупатель» |

Маппинг хранится в отдельных таблицах ClearLedger (`mapping_fuel`,
`mapping_paytype`, `mapping_station`) — НЕ зашитой в коде.

## 2. ТТН ↔ ПТУ

### 2.1 Что есть в ClearLedger (источник — файл)

ТТН приходит как файл (Excel/PDF/XML 1С) из email или upload:

| Поле ТТН | Что | Источник |
|---|---|---|
| `№ ТТН` | Номер транспортной накладной | шапка ТТН |
| `Дата ТТН` | Дата отгрузки | шапка |
| `Поставщик ИНН` | ИНН грузоотправителя | шапка |
| `Поставщик название` | название | шапка |
| `Покупатель ИНН` | ИНН грузополучателя | шапка — должен совпадать с ГИГ |
| `Договор №`, `от` | реквизиты договора | шапка |
| `Позиции` | список товаров | таблица |
| `Σ с НДС` | итог | низ ТТН |
| `Σ НДС` | сумма НДС | низ ТТН |
| `Σ без НДС` | итог без НДС | низ ТТН |
| `Σ количество` | литры/тонны/штуки | низ ТТН |

Каждая позиция:

### 2.3 Ключи связи ТТН-файл ↔ ПТУ

Приоритет:

1. **Точный композитный ключ**:
   `(Поставщик.ИНН + НомерВходящегоДокумента + ДатаВходящегоДокумента + Σ с НДС)`.
   Уникальность практически гарантирована — два контрагента редко
   присылают одинаковые номера в один день на одну и ту же сумму.
2. **TL_СоответствиеИсточников** (если ТТН пришла через TradeLedger.cfe
   и БП загрузил её через расширение): `Тип='purchase'`, `ИсточникUUID`
   = guid пакета смены, в `details` ссылка на источник ТТН.
3. **Sha256 хеш файла ТТН** — отдельный индекс в ClearLedger
   `entry.metadata.file_sha256` ⇄ `ПТУ.Комментарий` (если загрузчик его
   туда положил, что не гарантировано).

### 2.4 Формулы сверки (ПТУ)

| Что | Формула | Допуск |
|---|---|---|
| Сумма документа | `ТТН.Σ с НДС` == `ПТУ.СуммаДокумента` | ±0.01 ₽ |
| Сумма НДС | `ТТН.Σ НДС` == `Σ ПТУ.Товары.СуммаНДС + Σ ПТУ.Услуги.СуммаНДС` | ±0.01 ₽ |
| Количество строк | `len(ТТН.позиции)` == `len(ПТУ.Товары) + len(ПТУ.Услуги)` | ровно |
| По строкам | `ТТН.поз[i].Количество` == `ПТУ.Товары[match].Количество` | ±0.001 |
| По строкам | `ТТН.поз[i].Цена` == `ПТУ.Товары[match].Цена` | ±0.01 ₽ |
| По строкам | `ТТН.поз[i].Σ с НДС` == `ПТУ.Товары[match].Всего` | ±0.01 ₽ |
| Контрагент | `ТТН.Поставщик ИНН` == `Контрагент(ПТУ.Контрагент).ИНН` | строгое |
| Организация | `ТТН.Покупатель ИНН` == `Организация(ПТУ.Орг).ИНН` | строгое |
| Договор | `ТТН.Договор №` ≈ `Договор(ПТУ.Договор).Наименование` | fuzzy |
| Реквизиты ТТН в ПТУ | `ПТУ.НомерВходящегоДокумента` == `ТТН.№` | строгое |
| Реквизиты ТТН в ПТУ | `ПТУ.ДатаВходящегоДокумента` == `ТТН.Дата` | строгое |
| Σ НДС == Σ Дт 19.03 | Связь с проводками | ±0.01 ₽ |
| Σ с НДС == Σ Кт 60.01 | Связь с проводками | ±0.01 ₽ |
| Счёт-фактура есть | `Document_СчетФактураПолученный WHERE ДокументОснование = ПТУ` exists | bool |
| Σ НДС в СФ == ПТУ | сверка для книги покупок | ±0.01 ₽ |

### 2.5 Маппинг строк ТТН ↔ строк ПТУ

Это самая сложная часть. Возможные стратегии:

| Стратегия | Когда работает | Точность |
|---|---|---|
| По `Артикул` (внутр.код поставщика) | Если поставщик и БП используют одинаковые артикулы | 99% |
| По `Код` (внутр.код БП) | Если в ТТН есть код БП (редко) | 99% |
| По полному совпадению `Наименование` | Не работает — разные форматы | ~30% |
| По нормализованному `Наименование` (lower, без пробелов/кавычек) | Часто работает для топлива | 70% |
| По совпадению `(Цена + Количество + СтавкаНДС)` | Слабый, ломается на одинаковых строках | 60% |
| По эвристике AI (LLM) | Универсально, но платно | 95% |

В ClearLedger делаем каскад: артикул → код → нормализованное имя →
AI-fallback (только если первых трёх нет).

```python
async def _sync_doc_lines(client, connection, doc_type, doc_ref, lines_select):
    """Тянет одну ТЧ для конкретного документа.
    
    OData URL: /Document_<Type>_<TabularName>?$filter=Ref_Key eq guid'<doc_ref>'
    """
    entity = f"{doc_type}_{tabular_name}"
    rows = await client.fetch_entity(
        entity,
        select=lines_select,
        filter_expr=f"Ref_Key eq guid'{doc_ref}'",
    )
    return rows
```

Затем в `_sync_doc_type` после создания AccountingDoc вызываем
для каждого ТЧ и складываем в `lines.tabular[<name>]`.

### 3.3 Производительность

30909 документов × 3-5 ТЧ = ~100K дополнительных запросов. На OData это
терпимо (~1-2 сек/запрос), но **не делать в одном sync_catalogs** —
расширить sync_documents в отдельный шаг или сделать ленивым (по
требованию из UI при открытии конкретного документа).

Альтернатива: `$expand=Товары,Услуги,ОплатаКартами` в одном запросе
шапки. Работает в OData 1С, но может вернуть огромные JSON.
Лучше — лениво по клику в UI на конкретный документ.

## 7a. Период и расхождения — ОБЯЗАТЕЛЬНАЯ отметка (требование МАГ)

> Каждая сменная и каждая ТТН в ClearLedger должны иметь две независимые
> отметки: **в каком периоде** документ (открытый/закрытый в бухгалтерии)
> и **есть ли расхождение** — даже минимальное (округление в 1 копейку).

### 7a.1 Зачем

- **Закрытый период** — бухгалтерия уже сдала отчётность за этот месяц.
  Любое изменение требует Корректировки/Бух.справки и отдельного
  согласования с налоговой. Микро-расхождения здесь критичнее, чем в
  открытом периоде.
- **Расхождения по округлению** (1-2 копейки) накапливаются. За год
  100 ОРП × 0.02 ₽ = 2 ₽ невидимой разницы, которая потом всплывает
  в оборотке и портит остатки счетов 90.01/90.03.
- Бухгалтер должен сразу видеть: «эта смена ОК», «эта смена ОК но
  закрытый период — глянь», «эта смена с расхождением 0.02 ₽», «эта
  смена с расхождением 450 ₽ — срочно».

### 7a.2 Состояние периода (берётся из `Period`)

Модель `Period` уже существует (`server/app/models.py:752`):
- `(company_id, year, month)` уникальный ключ.
- `status` = `open` | `closed`.
- `closure_source` = `manual` | `from_bp` (репликация из ДатЗапретаИзменения 1С).

Логика для каждого AccountingDoc:

```python
period_status = (
    (await session.execute(
        select(Period.status).where(
            Period.company_id == doc.company_id,
            Period.year == int(doc.date[:4]),
            Period.month == int(doc.date[5:7]),
        )
    )).scalar() or "open"   # период не заведён ⇒ считаем открытым
)
```

Кэшируется в `AccountingDoc.period_status` (String 10).
Пересчитывается при:
- INSERT/UPDATE документа в sync_documents.
- При смене статуса периода через `POST /api/periods/toggle` —
  массовый UPDATE документов этого периода (background-task).

### 7a.3 Состояние расхождения

```python
# AccountingDoc.discrepancy_status (String 20):
"none"      # сверка успешна, дельты ≤ 0.005 ₽ по всем формулам
"rounding"  # суммарная дельта ≤ 0.05 ₽ — округление, безопасно
"minor"     # 0.05 < дельта ≤ 1.00 ₽ — обратить внимание
"material"  # 1.00 < дельта ≤ 100 ₽ — требует объяснения
"critical"  # > 100 ₽ или критичное поле (контрагент/НДС-ставка/количество)
"unmatched" # пары в ClearLedger.DataEntry нет — не с чем сверять
"pending"   # сверка ещё не выполнена
```

### 7a.4 Двойная отметка — комбинированный приоритет

| period_status | discrepancy_status | UI бейдж | Цвет |
|---|---|---|---|
| open | none | ✓ | зелёный |
| open | rounding | ≈ | оливковый |
| open | minor | ⚠ | жёлтый |
| open | material | ⚠⚠ | оранжевый |
| open | critical / unmatched | ⛔ | красный |
| **closed** | none | 🔒✓ | зелёный + замок |
| **closed** | rounding | 🔒≈ | **янтарный** (требует внимания!) |
| **closed** | minor / material / critical | 🔒⛔ | **красный + замок** (требует Корректировки/Справки) |
| closed | unmatched | 🔒? | серый + замок |

Правило: **в закрытом периоде даже `rounding` подсвечивается как warning**,
а `minor` и выше — как error. В открытом периоде `rounding` — это норма.

### 7a.5 Поток вычисления

1. **sync_documents** создаёт/обновляет AccountingDoc — выставляет
   `period_status` (по таблице periods) и `discrepancy_status='pending'`.
2. **reconcile_period** (новая операция) для каждого AccountingDoc:
   - Ищет парную ClearLedger.DataEntry по композитному ключу.
   - Если нашёл — считает все формулы из §1.4 / §2.4.
   - Записывает `discrepancy_status` по правилам §7a.3.
   - Заполняет `discrepancy_summary` (краткое) и `discrepancy_details` (полное).
   - Если не нашёл — `discrepancy_status='unmatched'`.
3. **POST /api/periods/toggle** при закрытии периода → background-task
   пересчитывает `period_status` для всех AccountingDoc этого периода
   и **повторно запускает reconcile** (т.к. порог `rounding` для
   закрытого периода жёстче).
