# Сводка клиента для узла «Телефонии»: ответы Ядра и состояние источника

Ревизия 22.10.2026. Код — `clearledger/server/app/routers/voice_router.py`
(`POST /api/eco/ezs/customer-summary`), сборка —
`app/services/voice_support_context.py: support_tickets`,
`app/services/voice_operator_answers.py`, `app/services/process_work.py`.
Потребители: узел «Телефонии» (`node/src/adapters/core.ts`, contact-hub) и
Поддержка. Основание ревизии — аудит решения 21.10.2026, кластер R11 (остатки
C-09 и A-16 со стороны Ядра).

## Правило совместимости

**Поля только добавляются.** Выкатка Ядра идёт раньше потребителей, поэтому ни
одно прежнее поле сводки не меняет ни имени, ни набора значений. Потребитель
определяет возможность по наличию поля — так же, как он уже делает со
`strictSelection`-полями `/support/customer-context`; номера версии на проводе у
этой выдачи нет и не заводится, версия контракта — дата ревизии этого документа.

Узел прежней сборки читает ровно восемь полей заявки и `ticketAvailability`
(`summaryOf`), новые ключи просто не берёт. Это проверено настоящим адаптером
узла на настоящем ответе Ядра:
`docs/solution-audit-20261021/fixes/R11/driver/node-consumer.mjs`.

## Что добавилось

### 1. `ticketSource` — состояние источника заявок

Рядом с прежним `ticketAvailability`, который сохраняет оба своих значения и
прежнее правило («available», только если источник ответил и все его строки
прошли проверку).

```json
"ticketSource": {
  "source": "support.tickets",
  "state":  "available | empty | partial | unavailable",
  "reason": null | "<код>",
  "asOf":   "2026-10-22T06:47:16.817085+00:00",
  "total":  5,
  "shown":  5,
  "status": 503
}
```

`state` отвечает на вопрос «можно ли верить пустоте», `reason` — «почему её не
удалось подтвердить». `total` — сколько строк отдал источник, `shown` — сколько
прошло проверку. `status` появляется только тогда, когда источник ответил кодом
ошибки.

| `state` | `reason` | Что это | `ticketAvailability` |
|---|---|---|---|
| `available` | — | источник ответил, заявки есть | `available` |
| `empty` | `no_open_tickets` | источник ответил: открытых заявок нет — **подтверждённое отсутствие** | `available` |
| `empty` | `support_not_enabled` | «Поддержка» компании не подключена: заявок не бывает | `unavailable` |
| `partial` | `source_rows_dropped` | часть строк источника не прошла проверку | `unavailable` |
| `unavailable` | `support_not_linked` | карта компаний приложения не заполнена — спросить нечем | `unavailable` |
| `unavailable` | `sso_not_configured` | нет ключа подписи служебного токена | `unavailable` |
| `unavailable` | `source_timeout` | источник не ответил за отведённое время | `unavailable` |
| `unavailable` | `source_unreachable` | до источника не дошли | `unavailable` |
| `unavailable` | `source_rejected` | источник ответил кодом ошибки (`status`) | `unavailable` |
| `unavailable` | `source_unexpected_answer` | ответ не того вида | `unavailable` |

Словарь состояний тот же, что у блоков контекста обслуживания Поддержки
(`available` / `empty` / `partial` / `unavailable`), чтобы интерфейс подписывал
их одними словами.

### 2. `tickets[].answers` — три ответа Ядра по заявке

Остальные семь вопросов разговора закрывает Поддержка в своей карточке
(`scripts/lib/operator-answers.js`); форма факта и словарь состояний здесь те
же, чтобы потребителю не разбирать два словаря.

```json
"answers": {
  "done":     { "text": "…", "state": "…", "source": "core.track", "asOf": "…", "reason": null, "value": {…} },
  "delivery": { "text": "…", "state": "…", "source": "core.track", "asOf": "…", "reason": null, "value": {…} },
  "toClient": { "text": null, "code": "…", "state": "…", "source": "core.track", "asOf": "…", "reason": null, "value": {…} }
}
```

**`done` — что фактически сделано и с каким результатом.** Работа «Трека»,
заведённая процессом этой заявки, её предмет, состояние предмета и исход.
`value`: `items`, `decided`, `done`, `refused`, `open`. Работ нет — `state:
"empty"`, `reason: "no_core_work"`.

**`delivery` — применено действие или ещё доставляется.** Слова состояния общие
с Поддержкой: `applied` — применено, `pending` — ещё доставляется, `accepted` —
принято, применение не подтверждено, `error` — не доставлено, ошибка обмена.
`value`: `total`, `awaited`, `failed`, `applied`, `pending`, `accepted`. Ни одной работы,
исхода которой ждёт процесс, — `state: "empty"`, `reason: "outcome_not_awaited"`.
Текст ошибки доставки наружу не уходит: в нём бывает адрес внутреннего узла.

**`toClient` — что допустимо сообщить клиенту.** Признаком, не фразой: фразу
строит та сторона, что говорит с клиентом.

| `code` | Чем это является для разговора |
|---|---|
| `work_accepted` | работа сделана и её исход применён |
| `work_awaiting_delivery` | решение принято, применение ещё идёт |
| `work_awaiting_decision` | работа заведена, решения по ней ещё нет |
| `work_rejected` | в работе отказано либо она отменена |
| `work_delivery_failed` | обещать нечего: исход не доставлен (`state: "unavailable"`) |
| `no_core_work` | работ Ядра по заявке нет; ответ строится по карточке Поддержки |

`value.codes` — все признаки заявки, когда работ несколько; `code` — тот из них,
который в разговоре главнее (пока хоть одна работа не доведена, сказать
«принято» нельзя).

### 3. `delivery` в строке витрины работы процесса

`GET /api/eco/process/{process_id}/work` отдаёт у каждой строки
`delivery: {state, awaited, delivered_at, attempts, error}` — тот же словарь
состояний. Прежние ключи строки не менялись; Поддержка (`scripts/lib/core-work.js`)
разворачивает строку целиком и новые ключи переносит без правок.

## Граница: чего у Ядра нет

Заявок Ядро не ведёт. Ответственный, срок, эскалация, приёмка, публичные ответы
клиенту и признаки «работа передана подрядчику» и «ожидание клиента» живут в
Поддержке, и в ответах Ядра их нет — ни пустыми полями, ни догадкой. Своей у
Ядра является работа «Трека» по процессу заявки и состояние доставки её исхода;
за это и отвечают три ответа, и каждый называет свой источник (`core.track`).
