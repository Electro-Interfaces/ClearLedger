## Реализовано

- `POST /api/eco/support-context/v1/prepare`: только именной ключ с отдельным
  scope `support-context.prepare`, закреплённый за своей company/node/connector.
  Использует существующую карту компаний Support. Машинный RS256 prepare идёт
  в настроенную Поддержку. Наружу только whitelist технической квитанции 202;
  телефон не сохраняется в таблицах Core, не включается в токены/аудит.
- `admit`: буквальный C02 body `nodeId/admissionCode`; public key берётся из
  проверенного ES256 DPoP proof, а consume вызывается по фиксированному Node
  CC backchannel. Exact actor-resolve остаётся в Support. Core проверяет своего
  существующего человека, блокировку, membership, продукты и effective modules.
- `renew`: действующий scoped access + proof с ath + новый одноразовый admission;
  та же company/call/context/actor/key/assignment. Ротация атомарно закрывает
  прежний grant, проверка Core версии повторяется после HTTP.
- `introspect`: отдельный Bearer service JWT, точные keyId/company map/scopes и
  актуальный отзыв bootstrap key. Каждый запрос заново проверяет сохранённый
  token digest, Core `User.token_version`, membership/modules/object scope,
  Node assignment/status и exact Support binding/rights. Положительного кэша нет.
- `postcall`: новый ticket-only допуск по сохранённому grantId + свежий proof
  исходного private key без ath. Истёкший live access не открывает live context.
  Node подтверждает endedAt и отсутствие explicit revoke; Support подтверждает
  связь заявки и текущее назначение. Новый `scp=ticket_postcall`, только
  `ticket.read/ticket.append`, одна ticketRef и маска assigned_ticket/vendor.
  Hard deadline сохраняется на исходном grant и ограничен context TTL и
  `endedAt + postcallMaxSec`; повторы не продлевают его.
- `POST .../revoke`: Core session actor или администратор своей компании,
  body `{version,schemaVersion,grantId}`. Работает и для истёкшего access;
  отзыв postcall закрывает его исходное основание и последующие производные.
  Выдача, настройка и отзыв оставляют штатный Core аудит без досье.
- RS256 с точными issuer/audience/kid/typ/scp/claims и TTL <=120 секунд;
  ES256 DPoP htm/htu/ath/jkt/iat/jti; неизвестный kid и legacy bearer не подходят.
  Replay proof фиксируется в PostgreSQL до ответа, между процессами.
- HTTP выполняется без DB row locks; после него перечитываются локальные
  права. Допущенный бизнес-эффект принадлежит транзакции Support после online
  introspection: распределённая атомарная отмена не заявляется.

Личные `read/details/select-object/actions/receipt` идут из iframe непосредственно
в `/support/api/v1/support-context/v1/*` по новому DPoP grant, как требует C02.
Core не проксирует досье через КЦ и не добавляет альтернативный personal API.
Таблицы `support_context_bindings/grants/replays` additive, регистрируются до
штатного `create_all`; существующие таблицы и авторизация не переопределены.

## Подключение без изменения работающих стеков

По умолчанию новая функция выключена: отсутствие per-company настройки — отказ.
Никакие runtime environment/production credentials этим изменением не выставлены.

1. Штатным `/api/inbound-keys` администратор выдаёт отдельные именные ключи
   `support-context.prepare` для Node и `support-context.introspect` для Support.
   Старому `voice.identify` новые возможности автоматически не добавляются.
2. Должны быть включены `voice` и `support`, существовать канонический
   `AppCompanyLink` и явно настроенный Support `internalUrl` в CompanyApp/App.
   Ни default internal URL, ни чужие credentials при отсутствии настройки не берутся.
3. `PUT /api/eco/support-context/v1/config?company_id=<Core UUID>` требует
   обычную Core session и существующее право администратора компании. Body:

   ```json
   {
     "version": "support-context/1", "schemaVersion": 1,
     "config": {
       "enabled": false,
       "publicOrigin": "https://space.example.invalid",
       "introspectionKeyId": "20000000-0000-4000-8000-000000000002",
       "requireMfa": true, "postcallMaxSec": 3600,
       "nodes": [{
         "nodeId": "synthetic-node-a",
         "connectorId": "30000000-0000-4000-8000-000000000003",
         "admissionBaseUrl": "https://node.example.invalid",
         "prepareKeyId": "40000000-0000-4000-8000-000000000004"
       }]
     }
   }
   ```

   Это вымышленные ссылки: API проверяет существование, scope, company и отзыв
   каждого keyId. Настройка сохраняется в существующий
   `CompanyApp(voice).config.supportContext`. GET того же пути доступен тому же
   администратору. NodeId должен однозначно выбирать company/node/connector;
   конфликтующая конфигурация не используется для admission.
4. Support получает service JWT через `POST .../service-token`, body только
   version/schemaVersion и свой `X-Cloud-API-Key`; ответ
   `token/tokenType=Bearer/expiresIn=120`. Токен закреплён company/keyId и может
   использоваться повторно в свои 120 секунд, каждый introspection проверяет отзыв.
5. Node origin используется только для фиксированных
   `/cc/v0/support-context/v1/admission/{consume,status}`. Scope service JWT
   `support-context.admission`, audience `node-support-admission`, company/node
   pinned; у status также полный callRef. Consume ещё не знает callRef.
   Browser Host/Forwarded заголовки не определяют canonical DPoP URL.

Секреты задаются владельцами соответствующих приложений вне публичного репозитория.
Это инструкция поставки исходников, не разрешение включать feature на рабочих стеках.
Выключение сохраняет durable links/grants для поздних фактов и аудита. Очистка
bindings/grants может выполняться только после context/postcall retention;
преждевременное удаление закрывает допуск. Просроченный replay чистится при вставке.

## Конечный источник данных Core

Сохранены прежние `/api/eco/identify` и `/api/eco/support/customer-context`, legacy
body/ответы по умолчанию совместимы. Добавлен opt-in `strictSelection:true`:
возвращает candidates/identityState/historyIdentity, не выбирает первый результат;
выбранный ref проверяется среди кандидатов именно этого поиска и компании.
Для выбранного человека зарядки берутся только по доказанной связи владельца,
не объединяются с историей всех кандидатов общего номера. Phone history явно
обозначена отдельно; последняя станция не становится подтверждённым объектом.

В строгом режиме `counts.totalSessions/failedSessions/sessions30d` содержат source,
UTC period/timeField, identity, definition и complete. Источник не складывает
разных провайдеров. `details.total` считает всю выборку, не длину страницы.
При `detail:true` возвращаются `details.nextCursor/hasMore/asOf`; cursor передаётся
следующим запросом в body. Он подписан и связан с company/нормализованным поиском/
выбранным ref/asOf; keyset `(started_at,id)` предотвращает дубли страниц.
Смена выбора/поиска или повреждение даёт 409 cursor_stale. Legacy лимит страницы
до 1000 не является потолком всей истории; Support personal details ограничивает
страницу своим контрактом до 100 и оборачивает source cursor своей ссылкой.
Core leaf выполняет только SQL, не вызывает обратно Support.

Introspection передаёт effective Core objectScope и ownOrganizationId.
Существующая `resolve_object_scope` сохранена, включая legacy нормализацию []:
в транспорт уходит уже вычисленный результат. Support сопоставляет Core object
refs со своей проекцией. У ServiceLocation нет канонического собственного
Organization UUID: owner/owner_id внешнего реестра не подставляются вместо него;
неразрешимая ownOrg-часть остаётся permission_denied/partial.

## Проверки и пределы доказательств

Изолированный локальный PostgreSQL 16: собственный контейнер
`core-support-context-i11-pg`, loopback port 29561, только синтетические записи.
Обычный DATABASE_URL, существующие контейнеры/DSN и production не использованы.
Все команды из `clearledger/server`, окружение `../../.venv` создано из
`requirements-test.txt`. TEST_DATABASE_URL ниже содержит только тестовые значения:

```sh
TEST_DATABASE_URL=postgresql+asyncpg://i11_test:synthetic-i11@127.0.0.1:29561/core_support_context_i11 \
  ../../.venv/bin/python -m pytest \
  tests/test_support_context_v1.py tests/test_support_context_source_v1.py \
  tests/test_voice_tokens.py tests/test_voice_core.py \
  tests/test_voice_support_context.py tests/test_voice_connections.py \
  -q --disable-warnings --maxfail=1
```

Результат: **73 passed**, 2 предупреждения зависимостей.
После добавления cursor проверка source выполнена отдельно: **1 passed**.
Повтор scoped набора: **52 passed**. После последних правок административного
формата и отзыва targeted config/revoke/DPoP: **3 passed**, включая отклонение
того же proof в новом Python-процессе с отдельным engine и общей PostgreSQL.
`git diff --check` и компиляция новых Python-модулей проходят.

Новый набор поднимает настоящий Core Uvicorn на TCP, подписывает настоящие
RS256/ES256 JWT и использует PostgreSQL. Проверены две компании, чужие
company/call/context/operator/audience/issuer/kid/scope, MFA, истечение и отзыв,
смена назначения/прав, DPoP replay/key/URL/ath/method, ограниченный положительный
object scope, wrapup deadline, expired-live → assigned-ticket postcall,
vendor ticket mask, сохранённый hard deadline и отказы upstream/таймаут.
Барьер HTTP доказывает отказ при Core revoke во время introspection и отсутствие
положительного кэша следующей операции.

Node и Support в этом наборе — отдельный TCP protocol peer, проверяющий реальные
service подписи и DTO. Это **не** доказательство готовности их бизнес-транзакций,
устойчивого Node admission store, внешнего tracker, реальной iframe цепочки или
всей матрицы A01–A18. Совместные реальные приложения, local edge/CSP, браузер,
досье/эффекты/командные квитанции и distributed race linearization проверяет V20.
Полный backend-набор всех продуктов и CI GitHub здесь не объявляются зелёными.
