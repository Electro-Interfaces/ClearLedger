# Повтор подготовки контекста, support-context/1

Нормативное уточнение §4 C02 от 21.10.2026 по реальному V18
(Core08e04, Support2f08, Node d8dc8e6). Это additive уточнение квитанции
prepare; JWT, права, body запроса и namespace C02 не меняются.

Первый вызов атомарно создаёт контекст в preparing. Повтор того же канонического
callRef/phone/startedAt/direction не создаёт новый контекст и возвращает
сохранённые contextRef/preparedAt/expiresAt с актуальными contextVersion/state.
Допустимые непогашенные состояния ответа 202:

- preparing;
- ready;
- partial;
- unavailable.

Их смысл совпадает с read. Core принимает их как действительную квитанцию связи,
а не как данные клиента и не как доказательство полноты контекста. Неизвестное,
expired или неверный тип state отклоняется. Истёкший expiresAt также отклоняется
независимо от state. TTL не продлевается повтором. Все прочие строгие проверки
callRef/company/node, version/schema, contextRef, contextVersion, времён и
ограниченных whitelist полей остаются в силе. Конфликт привязки не маскируется.

Core повторно использует прежний binding, Node сохраняет тот же contextRef.
Нельзя заставлять Support бесконечно сообщать preparing, пересоздавать контекст
или переименовывать готовый ответ в ошибку ради первого HTTP прохода.

Основание: msg_b459a1b19fc4, evidence/V18/prepare-replay-defect.json.
Реальный повтор после build показал Support202 partial с прежними ref/TTL,
но Core503 upstream_invalid при неизменных единичных строках обеих БД.
Исправление принадлежит R11 Core; проверка V18 затем повторяется с новым immutable
commit. Полный приём UI и сценарий потери ответа/рестарта узла остаются V20,
пока не получено отдельное прямое доказательство.
